## 1. 원안을 왜 기각했나

상위 계획서 §3.6은 「재고를 직접 쪼개는 작업이라 실수 가능성이 높아 되돌리기를 1차 범위에 포함」이라고
판단했다. 2026-08-27 사용자와 그 전제를 따져 **기각**했다.

### 되돌리기가 없어도 되는 이유

**역방향 재포장이 정식 우회로다.** 결과(20kg×3)를 다시 소스로 골라 원래 규격으로 합치면 된다.
`getRepackSources`는 `repackId`를 **아예 보지 않으므로**(조건 = 가용>0 + 품종 + 동질성)
재포장 결과 행도 그냥 소스가 된다. 막혀 있지 않다.

처음엔 이 경로를 「행이 늘어나 지저분하다」고 봤으나 **그 근거 하나가 틀렸다** —
소진된 행은 목록에서 아예 빠진다(`packages.ts:204` `if (available <= 0) return []`).
화면상으로는 지저분해지지 않는다.

**되돌리기가 유효한 창이 애초에 짧다.** `cancelRepack`은 결과 행에 movement가 하나라도 있으면 거부한다.
그런데 **재포장한 것을 다시 재포장하는 건 정상 동선이다**(톤백 → 20kg → 5kg — 실물 작업과 일치).
20kg을 5kg으로 쪼개는 순간 20kg에 REPACK movement가 붙어 첫 재포장은 되돌릴 수 없게 된다.
즉 되돌리기는 「재포장 직후 ~ 팔리거나 다시 재포장되기 전」의 짧은 구간에서만 쓸 수 있다.

**빈도가 낮다.** 되돌릴 일 = 실수·착오. 아주 가끔 일어난다(2026-08-27 사용자).

**이력 배지도 함께 기각.** 추적은 로트로 이미 된다. 배지의 실제 쓸모는 「되돌릴 대상 찾기」였으므로
되돌리기를 안 만들면 배지도 의미가 없다. 둘은 한 덩어리다.

### 결정 #57 — `cancelRepack`은 남기되 화면을 붙이지 않는다

액션(`repack.ts:461`)은 R1에서 이미 검증됐다. 지우지 않고 **의도적 미연결** 상태로 둔다.
다음에 읽는 사람이 「왜 안 쓰이지」 하지 않도록 함수 주석에 이 결정을 적는다.
실사용에서 실수가 잦아지면 그때 화면만 붙이면 된다.

## 2. 대신 고칠 것 — 재포장이 만든 정합성 구멍

원인은 하나다. **재포장 결과 행이 원본의 `batchId`를 승계하는데(`repack.ts:394`),
그 행을 「원래 생산물」과 구별하지 않는 곳이 있다.**

`batchId` 승계 자체는 옳다 — 로트·농가·품종을 이어받으려면 필요하다(상위 계획서 §3.4).
문제는 읽는 쪽이다.

### 🔴 결정 #58 — 생산 통계에서 재포장 결과를 제외한다

**이미 틀어져 있다.** 2026-08-27 Neon 실측:

```
Repack 2건 · 결과 6행(전부 batchId 보유) · 이중 계상 85kg
규격별: 10kg 50 · 4kg 24 · 5kg 10 · 1kg 1
```

| 위치 | 무엇이 틀어지나 |
|---|---|
| `app/actions/output-statistics.ts:97` | 총 생산량 + **규격별 집계**(톤백을 쪼갠 20kg이 「20kg 생산」으로 잡힌다) |
| `app/actions/dashboard.ts:32` | 총 생산량 + **수율 분자** — 산출이 부풀면 수율이 100%를 넘을 수 있다 |

톤백 1,004kg을 생산하고 1,000+4로 재포장하면 **생산 2,008kg**으로 집계된다.
체인이 길수록 배로 커진다(톤백→20kg→5kg이면 같은 쌀이 3번). **잔량 7톤 정리를 시작하면 7톤이 통째로 이중 계상된다.**

→ 두 쿼리의 `where`에 **`repackId: null`** 을 더한다.

- **재포장은 생산이 아니라 재배치다.** 도정에서 나온 것만 생산으로 센다
- 원본(톤백)은 소진돼도 생산 통계에 남는다 — 실제로 생산했으니 맞다. `repackId: null`이 정확히 그렇게 가른다
- **백필 불필요** — 쿼리 시점 조건이라 기존 데이터가 자동으로 정상화된다
- 트레이드오프: 「지금 20kg이 몇 개 있나」는 생산 통계로 알 수 없게 된다. **그건 재고 목록의 일**이다

**영향 없는 곳**(확인함): 제품재고 목록(가용 0 제외) · 발주서 차감(`productTypeId` + movements) ·
`admin.ts:126`·`product-type.ts:215`(존재 확인 count) · `package-movement.ts:44`(단건 조회).
오직 **「batch로 긁어 totalWeight를 합산하는」 두 곳**만 문제다.

### 🔴 결정 #61 — `batch.outputs`를 만지는 곳을 전수 정리한다 (공용 상수)

**#58을 고치고 나서 더 큰 게 나왔다.** 첫 조사는 `millingOutputPackage`를 **직접** 조회하는 곳만
훑었는데, `millingBatch`를 조회하며 **`outputs` 관계로 접근**하는 경로가 따로 있었다.
그쪽이 더 많고 더 위험했다. 사용자가 lint 결과를 그냥 넘기지 않아 드러났다.

#### 가장 심각 — 포장 수정이 이미 막혀 있다

```ts
// milling.ts:440 updatePackagingLogs
await tx.millingOutputPackage.deleteMany({ where: { batchId } })   // repackId 조건 없음
```

포장 다이얼로그 저장은 **그 배치의 outputs를 전부 지우고 다시 만든다.**
재포장 결과는 `batchId`를 승계하므로 여기 휩쓸린다. `PackageMovement.package`의 `onDelete`가
Prisma 기본값 **`Restrict`**라 두 갈래로 갈린다.

| 원본/결과에 movement | 결과 |
|---|---|
| 있음 | **FK 위반 → 트랜잭션 실패. 포장 수정이 통째로 막힌다** (사용자는 이유를 모른다) |
| 없음 | 재포장 결과가 **조용히 삭제**된다 → 원본은 소진된 채 남아 재고 증발 |

**실측 (2026-08-27 Neon) — 이미 발생 중:**

```
배치 #102 · #140 · #145 · #56
각각 REPACK movement가 붙은 원본 1행 → deleteMany가 FK로 막힘 → 포장 수정 불가
```

#### 전체 영향

| 위치 | 증상 |
|---|---|
| `milling.ts:440` `updatePackagingLogs` | 🔴 위 표. **최우선** |
| `milling.ts:293` `getMillingLogs` | 재포장 결과가 도정 포장으로 **다이얼로그에 복원됨** + 수율 필터 오판정 |
| `statistics.ts:336` | 통계 요약 `totalOutputKg` · `avgYieldRate` 부풀림 |
| `statistics.ts:451` | 버킷 × 품종별 집계 부풀림 |
| `milling-excel.ts:113` | 수율 필터 오판정 → 엑셀이 화면과 어긋남 |
| `dashboard.ts` 9번 `outputs` | **수율 분자** 부풀림 — 실측 배치 #145 63.50% → 62.67% |
| `dashboard.ts:63` | 최근 도정 10건 목록에 재포장 결과가 섞여 표시 |
| `milling.ts:649` `_count` | 배치 삭제 가능 판정에 재포장 결과가 포함 |

⚠️ **`dashboard.ts` 3번(`totalOutputWeight`)은 수율 분자가 아니다.** 1차 수정 때 주석에 그렇게
적었는데 틀렸다 — 그 값은 카드의 총 생산량 전용이고, 수율은 9번 쿼리가 따로 계산한다. 주석을 정정했다.
(`totalInputWeight`는 쿼리만 하고 **아무 데도 쓰이지 않는다** — 별건으로 남긴다)

#### 해법 — 공용 상수 (2026-08-27 사용자 확정)

지점마다 손으로 `repackId: null`을 붙이면 **또 누락된다**(이번에 두 번 놓쳤다).
`lib/batch-outputs.ts`에 조각을 하나 두고 모든 지점이 그것을 쓴다.

```ts
/** 도정 산출만 — 재포장 결과는 batchId를 승계하므로 걸러야 한다 */
export const MILLED_OUTPUT_ONLY = { repackId: null }
/** batch.outputs 관계에 스프레드해서 쓴다 */
export const MILLED_OUTPUTS = { where: MILLED_OUTPUT_ONLY }
```

스키마에서 관계를 둘로 가르는 안(`outputs` / `repackOutputs`)이 누락을 타입으로 막아 근본적이지만,
마이그레이션 + 기존 코드 전수 수정이 필요해 이번에는 택하지 않는다.

### 결정 #59 — 재포장 결과 행은 일반 삭제를 막는다 (저비용 방어)

`deleteMiscPackage`(`packages.ts:647`)는 결과 행만 지우고 **원본의 REPACK movement는 그대로 둔다.**
원본은 영원히 소진 상태로 남고 결과는 사라져 **재고가 증발한다.** `deleteMiscPurchase`(`:991`)도 같다.

**단, 실질 위험은 낮다**(2026-08-27 재평가):

```
전체 제품재고 — 벼 613행 712,772kg / 잡곡 1행 100kg
재포장 결과 6행 — 전부 RICE/MILLED
```

삭제는 **잡곡 탭에만** 있고(벼 탭은 행 삭제 기능 자체가 없다) 잡곡 재고는 1행뿐이다.
「잡곡을 재포장하고 → 그 결과를 잡곡 탭에서 삭제」해야 닿는 경로다.

그래도 막는 이유: **조건 한 줄이면 되고**, 잡곡 재고가 늘면 실제 위험이 된다.
차단 메시지로 역방향 재포장을 안내한다(되돌리기 화면이 없으므로 그게 정식 경로다).

```
재포장으로 만든 재고는 삭제할 수 없습니다.
되돌리려면 이 재고를 다시 재포장해 원래 규격으로 합쳐주세요.
```

### 결정 #60 — 되돌리기 거부 메시지를 정확히 (미연결이므로 보류)

`cancelRepack:491`은 movement가 있으면 「이미 **차감**된 재고가 있어」라고 하는데,
실제로는 **다시 재포장된 것**일 수도 있다(#57에서 본 정상 동선). `movement.type`으로 갈라 말해야 맞다.
**다만 화면이 없어 볼 일이 없으므로 이번에는 고치지 않는다.** 화면을 붙이는 날 함께 고친다.
