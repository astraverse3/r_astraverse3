# 계획서 — 제품재고 차감 테스트 데이터 정리

- **작성일**: 2026-09-09
- **요청**: 「제품재고에서 차감 테스트한 거 다 되돌릴 수 있나? 지금까지 한 건 다 테스트다」
- 🔴 **대상이 실서버 DB다**(로컬=실서버 같은 Neon — [[deployment_db_infra]]). 되돌리기 어려운 작업이다.

---

## 1. 목표

제품재고 차감·재포장으로 쌓인 **테스트 데이터를 전부 지우고**, 시스템을
「재고가 나간 적 없는」 상태로 되돌린다.

## 2. 현황 (2026-09-09 실측)

| 대상 | 건수 | 화면 되돌리기 | 비고 |
|---|---|---|---|
| `PackageMovement` REPACK | 31건 | 🔴 **막힘** | `Repack` 10건에 딸린 소스 |
| `PackageMovement` OTHER | 14건 | 가능 | `기능 오픈 전 일괄차감`, 2,840개 |
| `PackageMovement` SALE | 1건 | 가능 | `차감 테스트` 이마트 2,000개 |
| `Repack` | 10건 | — | 결과 재고 **23행** 생성 |
| `MillingOutputPackage` (repackId≠null) | 23행 | 🔴 **막힘** | 재포장으로 생긴 행 |

- 발주서 경로 차감(`orderItemId`) **0건** — 발주서 69건은 재고에 손대지 않았다.
- 결과 행을 참조하는 발주서 라인 **0건**.
- 제품재고 전체 **659행** 중 `repackId` 있는 행이 **23행** — 위 결과 수와 일치한다(교차 검증 통과).

### 🔴 연쇄 1건

`Repack #3`의 결과 `pkg#1356`(4kg×2)이 **`Repack #4`의 소스**로 쓰였다(`mv#18`).
따라서 재포장을 하나씩 되돌리려면 **#4 → #3 순서**여야 한다.
(아래 방식은 movement를 통째로 먼저 지우므로 순서 문제가 사라진다.)

## 3. 사용자 결정

- **「기능 오픈 전 일괄차감」 14건도 지운다** — 605행 소급 정리에 해당할 수 있다고 알렸고,
  그럴 경우 **소급 정리를 처음부터 다시 하게 된다**는 점을 확인한 뒤 「지운다」로 결정.
- **발주서 69건은 그대로 둔다** — 재고에 영향이 없고 D2 개발 시 테스트 데이터로 쓸 수 있다.

## 4. 왜 화면 기능으로는 안 되는가

`cancelMovement`는 `repackId !== null`을 **거부한다**(`REPACK_CANCEL_BLOCKED`).
재포장 소진분만 지우면 **원본은 복원되는데 결과 행이 남아 재고가 이중 계상**되기 때문이다.
`lib/package-guard.ts`도 반대편에서 결과 행 삭제를 막는다(`REPACK_DELETE_BLOCKED`).

> 🔴 **가드가 막으려던 사고를 스크립트가 스스로 지켜야 한다** —
> movement(소진)와 결과 행을 **반드시 짝으로 함께** 지운다. 한쪽만 지우면 재고가 증발하거나 두 배가 된다.

정식 우회로인 **역방향 재포장**은 10건을 손으로 되돌려야 하고 `lossKg`·행 구성이 정확히 복원되지 않는다.
전량 삭제가 목적이므로 **일회성 스크립트**로 처리한다.

## 5. 실행 순서

`scripts/cleanup-test-movements.ts` (신규, 일회성)

1. **백업** — 지울 3종을 JSON으로 덤프(`docs/backup/` 아님, 저장소 밖 스크래치 + 콘솔 출력).
   되돌릴 수 있는 유일한 수단이므로 **덤프 실패 시 즉시 중단**한다.
2. **사전 검증** — 아래가 모두 참이어야 진행한다. 하나라도 어긋나면 중단.
   - 발주서 경로 movement가 0건
   - `repackId≠null` 재고 행 수 == `Repack.results` 합계
   - 결과 행을 참조하는 발주서 라인 0건
3. **삭제** (한 트랜잭션)
   1. `PackageMovement` **전건 삭제**(46건) — 연쇄 순서 문제가 여기서 사라진다
   2. `MillingOutputPackage` 중 `repackId≠null` **23행 삭제**
   3. `Repack` **10건 삭제**
4. **감사로그 1건** — 요약(건수·대상)을 `AuditLog`에 남긴다. 46건 개별로는 남기지 않는다.
5. **사후 검증** — `PackageMovement` 0 · `Repack` 0 · 제품재고 **636행**(659−23) ·
   `repackId≠null` 0행.

> 트랜잭션 타임아웃 주의 — Neon 왕복이 250~300ms다. **루프 안 개별 삭제 금지**,
> `deleteMany` 3회로 끝낸다([[project_order_sales_feature]]의 적재 타임아웃 교훈).

## 6. 삭제 후 상태

- 원본 제품재고의 **가용재고가 자동 복원**된다 — 공식이 `count - SUM(movements.count)`이고
  원본 행의 `count`는 건드리지 않았기 때문이다.
- 재포장으로 생긴 23행은 사라진다. 소스가 복원되므로 **중량은 보존**된다.
- 시스템은 다시 「재고가 나간 적 없다」고 믿는 상태가 된다.

## 7. 🔴 원물·도정 관계는 끊어지지 않는다 (사용자 질문)

**「원물 → 도정 → 포장」 체인은 손대지 않는다.** 지우는 23행은 그 체인 **끝에 덧붙은
재포장 파생분**이다.

지울 23행도 `batchId`·`stockId`를 물려받아 갖고 있다. 예: `pkg#1324 batch=145 stock=746`.
그러나 이것은 **자식이 부모를 가리키는 참조**다 — 자식을 지운다고 부모(도정 배치·원물 재고)가
사라지지 않는다. 배치 145도, 원물 746도, 그 배치에서 나온 **원래 포장 행도 그대로 남는다.**

실측으로 확인:
- 남을 **636행 중 632행이 `batchId` 보유** — 도정 계보 그대로다.
- 재포장 **소스였던 원본 30행은 전부 남는다.** movement만 지워지므로 가용재고가 복원된다.
- 지울 23행을 가리키는 외부 참조는 `PackageMovement` **1건뿐**(연쇄분 `mv#18`, 같이 지워진다).

## 8. 롤백

JSON 덤프로 역순 복원(`Repack` → 결과 행 → `PackageMovement`).

⚠️ **id가 바뀐다** — `@default(autoincrement())`라 복원 시 새 id가 붙는다.
다시 이어야 하는 것은 **되살린 것들끼리의 연결**이다(movement ↔ 결과 행 ↔ `Repack`).
`batchId`·`stockId`는 **덤프 값 그대로 넣으면 된다** — 배치와 원물은 지워지지 않으므로
그 번호가 계속 유효하다. **완전한 원상복구는 아니다**(id·생성시각이 달라진다).

## 9. 확인이 필요한 사항

- 실행 시점에 **다른 사람이 앱을 쓰고 있지 않아야** 한다(차감이 동시에 들어오면 덤프와 어긋난다).

### 🔴 실행 후에 겪은 것 — 화면이 안 바뀐다

지우고 나서 **차감 이력이 0건인데 ⋮ 메뉴가 그대로 떴다.**

- **원인은 캐시다.** 스크립트는 `revalidatePath('/packages')`를 거치지 않는다 —
  그건 앱 액션(`cancelMovement` 등)에만 붙어 있다. Next가 들고 있던 **삭제 전 스냅샷**이
  계속 그려졌고, 그 스냅샷은 `qty > available`이라 메뉴 조건(`hasDeductionHistory`)을 만족했다.
- **다이얼로그는 비어 있었다** — 열 때 서버에 새로 조회하기 때문이다. 목록(캐시)과
  다이얼로그(실시간)가 어긋나 보인 것이지 데이터는 처음부터 정상이었다.
- **해결**: 브라우저 새로고침. 스크립트 마지막에 안내 문구를 넣어 뒀다.

> **교훈**: DB를 직접 고치는 일회성 스크립트는 **화면 캐시를 못 턴다.**
> 「데이터가 안 지워졌나?」로 의심하기 전에 **새로고침부터** 해 본다.
> 목록과 다이얼로그가 서로 다른 말을 하면 대개 한쪽이 캐시다.
