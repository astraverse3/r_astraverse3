> **1차판(3모드 매트릭스)은 폐기됐다.** 같은 날 오전에 쓴 §5(모드 판정)·§6(전치·카드 렌더)은
> 실측 밀도 분석으로 뒤집혔다 — 택배는 67건이지만 규격이 안 겹쳐 **주문 밀도 5.6%**(94.4%가 빈 칸),
> 급식·이마트·시아스는 밀도가 높지만 **건이 1~3개**라 나란히 볼 상대가 없다.
> 매트릭스의 가치는 「건끼리 나란히 보는 것」인데 실데이터에 그 중간이 없어, **3모드 판정 자체가 불필요**해졌다.
> 폐기 대상은 문서뿐이다 — **코드는 0줄 쓰였다**(§2.3).

## 3. 🔴 지시서 2차판과 코드가 어긋나는 3건

1차판 오류 6건은 반영됐다. 대조에서 **새로 나온 3건**:

### A. `listPurchaseOrders` 액션은 **필요 없다**

지시서 §2가 「`getUploadMatrix`에서 파생」이라 적었는데, **파생이면 액션을 추가할 이유가 없다.**
`page.tsx:20`이 이미 `getUploadMatrix` 한 번으로 `BuildMatrixInput` 전부를 클라이언트에 내려주고,
`buildMatrix().rows`가 건 목록에 필요한 걸 다 갖고 있다:

| §3.1 요구 | `MatrixRow` |
|---|---|
| `o.vendorName` | `row.vendor` (⚠️ 필드명 다름) |
| 수령인 | `row.recipient` |
| 라인수 | `cells`의 `itemIds` 합 |
| 주문/차감 | `orderedQty` / `allocatedQty` |
| 상태 점 | `row.status` (`ROW_STATUS_ORDER` 판정) |
| 필터 `작업 필요 41` | `row.needsWork` · `totals.needsWorkRows` |

→ **액션·쿼리 추가 없이** 같은 데이터를 리스트로 그리기만 한다. 서버 왕복 0.

### B. §7 검토 게이트도 **신규가 아니라 확장**

`review-gate-dialog.tsx`가 이미 `previewBatch`/`confirmBatch`를 해석하고
**4갈래 구성**(정상/부분/**재고없음**/실패)을 갖고 있다 — 이 4갈래는 실측에서 얻은 것이라
(부족 18라인이 전부 가용 0) 새로 지으면 **「부분 차감」이라 거짓말하는 화면**으로 되돌아간다.

지시서 §7이 더하는 건 **선택 UI**(전부 체크 기본 · 그룹 해제 · 제외 행 `opacity-45`)뿐이다.
→ §4.0과 **같은 논리로 확장**한다. 새 파일 `review-gate.tsx`를 만들지 않는다.

### C. 🔴 `DetailLine`에 **규격 중량이 없다** — §4.1 푸터를 계산할 수 없다

`purchase-order.ts:138`의 `DetailLine`에는 `unitWeightKg`가 **없다**(`grep` 0건).
그런데 §4.1 푸터는 `남은 kg = (주문−차감) × 규격중량`을 요구한다.

- 일반 규격은 `normalizeSpec(packageType).weightKg`로 클라이언트에서 뽑을 수 있다(순수함수)
- 🔴 **톤백은 못 뽑는다.** 자루중량은 규격 문자열이 아니라 **라인 필드**(`PurchaseOrderItem.unitWeightKg`, #34)이고,
  `DetailLine`이 그걸 안 싣는다 → 시아스(톤백 1건) 건상세의 kg이 **통째로 틀린다**
- 같은 이유로 §8-1의 「단위 없는 `500`」 배지도 판단 근거가 없다

→ **`OrderDetail`에 `unitWeightKg`를 싣거나, 건상세를 `BuildMatrixInput`에서 파생**한다(§4 단계에서 결정).

#### C-2. 곁가지 — `getPurchaseOrderDetail`은 라인당 쿼리 2회다

`purchase-order.ts:186~` `Promise.all` 안에서 라인마다 `allocatedQtyOfItem` + `loadAvailablePackages`.
16라인이면 **32왕복**이다. 지금은 패널을 한 번 열 때뿐이라 문제가 없었지만,
§4.2 「다음 건 ›」으로 **67건을 연속으로 넘기면** 그 왕복이 건마다 쌓인다.

📌 이 프로젝트에서 이미 같은 모양으로 터졌다 — 적재 트랜잭션 타임아웃(루프 안 쿼리, Neon 왕복 250~300ms).

→ 건상세도 `BuildMatrixInput` 파생으로 가면 **왕복이 0**이 된다(FIFO 추천은 시트가 열릴 때
`getCellAllocation`이 따로 주므로, 건상세 본문에 필요한 값은 이미 클라이언트에 다 있다).

## 4. 구현 단계

### M1-1. 건상세 데이터 원천 = B안 파생 ✅ **완료 (2026-09-18)**

두 안 중 하나를 고른다. **§3-C와 C-2를 동시에 푸는 건 B안이다.**

| | A안 — `OrderDetail` 확장 | B안 — `BuildMatrixInput` 파생 |
|---|---|---|
| 톤백 kg | `unitWeightKg` 필드 추가 | `items[].unitWeightKg` 이미 있음 |
| 「다음 건」 왕복 | 건마다 2×N 쿼리 | **0** |
| 데스크탑 패널 | 그대로 | 같이 파생으로 옮기면 판정 한 벌 유지 |
| 위험 | 왕복이 남는다 | 파생 로직을 새로 쓰는 동안 `kindOf`가 두 벌 될 수 있다 |

**B안 확정**(사용자·지시서 §2.0). `kindOf`는 **`cellStatusOf`로 흡수**했다 — 둘은 이미 같은 판정을 다른 이름으로 하고 있었다
(`UNMATCHED → SHORTAGE → PARTIAL/PENDING`, 완료 우선). 흡수는 **B안과 같은 커밋**에서 했다 —
두 벌로 굳은 기간이 0이다(지시서 §2.0.1의 선행 요구).

**한 일**

| 파일 | 내용 |

### M1-2. 건 목록 `order-list-mobile.tsx` ✅ **완료 (2026-09-18)**

- 데이터 = `buildMatrix().rows` + `sortMatrixRows`(§3-A). **새 액션 없음**
- 발주처 그룹: `row.vendor`로 묶고 **건수 내림차순**. 그룹 1개면 헤더 미렌더
- 필터 칩 `작업 필요`(기본) / `전체` — `row.needsWork`
- 행 44px · 상태 점 6px · 우측 `차감/주문`
- 🔴 터치영역은 `label`/부모 패딩으로([[mobile_hit_area_overlay]]) — absolute 오버레이 금지
- 🔴 **`row.orderId`를 키로 쓴다**(표시값을 식별자로 겸용하지 말 것 — `LotGroup.groupKey` 사고)

**계획과 달라진 것 3가지**

1. 🔴 **그룹 축은 `row.vendor`가 아니라 `nameTiersOf`의 보조 이름(tail)**이다.
   지시서 §3.1 코드(`o.vendorName`)대로 하면 **서울급식이 깨진다** — `MEAL_SEOUL`은
   `primary:'vendor'·constantSide:'recipient'`라 vendor가 은평구·서대문구로 **매 건 다르다**.
   그룹 3개 × 1건이 되어 헤더가 행 수만큼 생긴다. 채널 선언이 이미 「무엇이 반복되는 축인가」를
   알고 있으므로 보조 이름으로 묶는다 → 지시서가 의도한 결과(§3.1 괄호)가 전 채널에서 나온다.
2. **「건수 많은 발주처 먼저」는 발주처별 정렬일 때만.** 사용자가 「작업 필요 먼저」를 골랐는데
   그룹을 건수순으로 다시 세우면 고른 정렬이 사라진다.
3. **상태칩은 `ROW_STATUS_ORDER` 전체를 돈다.** 시안 ①은 완료/부분/대기/실패 4칩인데,
   실데이터(택배 260818)의 주 축은 **재고부족 20건**이었다 — 4칩만 박았으면 어느 칩에도 안 잡힌다.

**곁가지 2건**

- **상태 표기표 3벌 → 1벌**(`status-meta.ts` 신설). 판정은 `cellStatusOf` 한 벌인데 라벨·색이
  매트릭스·패널에 각각 있었고 목록이 세 번째를 만들 참이었다. 🔴 판정만 합치고 표기를 세 벌로 두면
  **사용자 눈에는 결국 세 벌**이다.
- 🔴 **하단 CTA가 `MobileNav`에 가렸다**(브라우저 확인에서 발견). `sticky bottom-0`은 뷰포트
  바닥에 붙는데 거기엔 탭바가 `fixed z-40`으로 떠 있다. 탭바 위로 올리되 **레이아웃이 본문에 주는
  하단 여백과 같은 식**을 쓴다(`layout.tsx:33`) — 한쪽만 바뀌면 다시 겹친다.

⚠️ `matrix-client.tsx`가 **949줄**(원래 913줄로 이미 800줄 상한 초과). 머리글 4행
(`MatrixHead`·`SumRow`·`HeadCorner` 약 200줄)을 떼면 맞는다 — **M1 범위 밖, 별도 작업**.

### M1-3. 건상세 확장 (`order-detail-panel.tsx`) ✅ **완료 (2026-09-21)**

§4.0의 4개 중 **3개**를 얹었다. 3번(라인 탭 → FIFO)은 시트가 M1-5라 거기서 붙인다.
**기존 구조·판정은 건드리지 않았다.**
1. ✅ 완료 그룹 1줄 접기 — `새청무 5kg 외 8건 · 전부 차감 완료 · 932kg`
   - 작업 필요가 **하나도 없으면 펴 둔다** — 그때는 완료 목록이 곧 이 화면의 내용이다
2. ✅ 푸터 `작업 필요 7라인 · 남은 401kg` + `6라인 FIFO 일괄차감`(실패 제외)
   - 🔴 라인수는 실패 **포함**, 버튼 수는 실패 **제외** — 분모가 다르다(의도)
   - 🔴 중량 `null` 라인이 섞이면 **`일부 규격 중량 미산정` 배지**(§8-1)
3. ⏸ 라인 탭 → FIFO 바텀시트 — **M1-5**
4. ✅ 「다음 건 ›」 · 마지막이면 `목록으로`

**계획과 달라진 것 3가지**

1. 🔴 **일괄차감 버튼은 신규 경로가 아니다** — `ReviewGateDialog`가 이미 `orderIds: number[]`를
   받으므로 **건 하나짜리 배열**로 그대로 연다. 건상세 전용 확정 경로를 지었으면 4갈래 구성
   (정상/부분/재고없음/실패)이 두 벌이 됐다. 패널은 **열어 둔 채**다 — 확정 결과가 패널 숫자에
   바로 반영되고 이어서 「다음 건 ›」으로 넘어가는 것이 이 화면의 흐름이다.
2. 🔴 **`siblings`는 목록을 매번 읽지 않고 「열 때 찍은 스냅샷」**이다. §4.2가 「목록의 현재
   필터·정렬 순서」라고만 적었는데, 모바일 목록의 기본 필터가 「작업 필요」라 **차감하는 순간
   그 건이 목록에서 빠지고 뒤 건이 한 칸 당겨진다** — 살아 있는 목록으로 `indexOf + 1`을 하면
   바로 다음 건을 건너뛴다. 순서를 만드는 쪽도 `shown`이 아니라 **그룹으로 묶은 뒤**의 순서다
   (발주처별 정렬은 그룹을 건수순으로 다시 세우므로 `shown`과 화면 차례가 어긋난다).
3. **건마다 `key`로 새 마운트** — 「다음 건 ›」이 스크롤·접힘 상태를 물려받으면 새 건을 중간부터
   보게 된다. 리셋을 effect로 흉내 내지 않았다.

**곁가지 — 🔴 모바일에서 게이트의 「이 줄」이 무반응이었다**

게이트의 이슈 줄을 누르면 매트릭스 셀로 스크롤하는데, **폰에는 갈 셀이 없다**
(`hidden sm:contents` = `display:none`). DOM에는 있어서 `querySelector`는 찾지만 스크롤은
아무 일도 일어나지 않는다 — D3의 `data-cell` 사고(`dc5651b`)와 **같은 증상**이다.
M1-2에서 모바일 게이트 진입이 생기며 들어왔고, M1-3이 진입점을 하나 더 늘리므로 같이 막았다.

→ 브레이크포인트를 JS에 복제하지 않고 **그 셀이 실제로 그려져 있는지**를 DOM에 묻는다
(`offsetParent !== null`). 안 보이면 그 **건의 상세**로 데려간다. `lineIndex`에 `orderId`를
같이 담았다 — `cellKey`를 쪼개 쓰지 않는다(표시·이동용 키를 식별자로 겸용하지 말 것).
데스크탑에서 셀로 갈 때는 **패널을 닫는다** — 열린 채면 오른쪽 468px이 그 셀을 덮는다.

검증: `tsc` 0 · `eslint` 0 · **test 389/389**(M1-1이 깔아 둔 `sumOrderLines` 집계 테스트를
화면이 그대로 꺼내 쓴다 — 신규 순수함수가 없어 테스트도 늘지 않았다).

⚠️ `matrix-client.tsx`가 **1022줄**(949 → 1022). 800줄 상한 초과가 더 벌어졌다 — **별도 작업**.
