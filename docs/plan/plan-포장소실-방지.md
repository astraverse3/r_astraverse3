## 1. 🔴 원인 재특정 — 「동시 편집」이 아니라 **「낡은 화면」**

어제는 후보 A를 *"둘이 같은 시간에 다이얼로그를 열어뒀을 때"* 로 좁혔다. **이 전제가 틀렸다.**

코드를 보면 포장 다이얼로그는 **열릴 때 서버를 다시 읽지 않는다.**

- [page.tsx:33](<../../app/(dashboard)/milling/page.tsx#L33>) — 페이지 로드 때 `getMillingLogs()`로 **한 번** 읽어 `logs`를 내려준다
- [milling-table-row.tsx:222](<../../app/(dashboard)/milling/milling-table-row.tsx#L222>) — 그 스냅샷을 `initialOutputs={log.outputs}`로 전달
- [add-packaging-dialog.tsx:165](<../../app/(dashboard)/milling/add-packaging-dialog.tsx#L165>) — 다이얼로그는 열릴 때 `setOutputs(restoreOutputs(initialOutputs))` — **서버 재조회 없음**

갱신 경로는 저장 성공 후의 `router.refresh()` 하나뿐이다. 즉 **페이지 탭을 켜둔 채 두기만 하면 화면이 낡는다. 두 사람이 동시에 열어둘 필요가 없다.**

그리고 낡은 화면으로 저장하면 [packaging-diff.ts](../../lib/packaging-diff.ts)가 그걸 **의도된 삭제로 읽는다** — 코드 주석에 이미 그렇게 적혀 있다:

```
// id가 없거나, 있어도 기존에 없는 행이면 새로 만든다.
// (후자는 화면이 낡은 경우다. 원래 행은 아래에서 delete 대상이 되므로 결과적으로 교체된다.)
```
```
// -- 입력에서 빠진 행 = 삭제 --
```

「화면에 없던 행」과 「사용자가 지운 행」을 서버가 구분할 방법이 없다.

### 이 가설로 재구성한 시간선

| 시각 | 실제로 일어난 일 (추정) |
|---|---|
| 14:30 | 이영명 톤백 저장 **성공**. `#1365`가 DB에 실제로 존재 → **에러가 안 뜬 게 설명된다** |
| ~16:00 | 이영명·민채 화면이 낡은 스냅샷이라 `#1365`가 안 보임 → "입력한 게 없다" |
| 16:00 | 저장 반복 실패 (**별개 원인, 미확정**) |
| 16:02:15 | 민채 4kg×267 저장 성공 → payload에 `#1365`가 없으니 **diff가 조용히 삭제** + `#1366` 생성 |
| 16:02:56 | 톤백 550 재입력 → `#1367` |

결번 `1365`가 「롤백된 INSERT」가 아니라 **「커밋된 뒤 낡은 화면이 지운 행」**으로 설명된다.
감사로그가 없어 흔적이 0인 것도 이 그림과 정확히 맞는다.

### 확정 아님 — 남는 것

- `#1365`가 실제로 커밋됐었는지는 **감사로그가 없어 증명 불가**. 다만 이 가설은 물증·증언 어느 것과도 모순되지 않는 유일한 가설이다.
- **16:00 저장 실패**는 여전히 미해결. 후보 C(`INVALID_LINE`이 새 줄 전체를 막음)가 유력하나 에러 문구를 못 들어 확정 불가. → 아래 P1(감사로그)·P5(count=0)가 다음번엔 이걸 잡는다.
- 후보 D(트랜잭션 롤백)는 약함: `updatePackagingLogs`에 이미 `{ timeout: 30000 }`이 걸려 있다(배송 D1b 교훈 반영분, [milling.ts:620](../../app/actions/milling.ts#L620)).

### P1. `updatePackagingLogs`에 감사로그

**문제**: [milling.ts:449](../../app/actions/milling.ts#L449) `updatePackagingLogs`는 감사로그를 **하나도** 남기지 않는다.

**검증**: 저장 1회 후 감사로그에 삭제 스냅샷이 실제로 남는지 (사용자 브라우저 + 활동로그 화면)

### P4. B안 — baseline 충돌 감지 (사용자 결정, 2026-09-01)

**설계**: 다이얼로그가 P3 재조회로 받은 **행 id 집합(baseline)** 을 기억했다가 저장 시 함께 보낸다.
서버는 baseline과 현재 DB 행 집합을 맞대어, **내가 못 본 행이 DB에 있으면 저장을 거부**한다.

| | 동작 |
|---|---|
| baseline ⊇ 현재 DB 행 | 정상 저장 |
| DB에만 있고 baseline에 없는 행 존재 | **거부** + 무엇이 추가됐는지 알림 |

**변경**:
- 시그니처 `updatePackagingLogs(batchId, outputs, baselineIds: number[])`
  - 🔴 **선택 인자로 두지 않는다.** `undefined`면 기존 동작으로 빠져 구멍이 그대로 남는다.
    호출처 3곳(`handleSave`·`handleCloseBatch`·`handleClearPackaging`)을 모두 고친다
- 서버: `rows` 조회 후 `rows.filter(r => !baselineIds.includes(r.id))` 가 비어있지 않으면 거부
  - 새 에러코드 `STALE_BASELINE` — `lib/packaging-diff.ts`에 넣을지 액션에 둘지는 구현 시 결정
    (diff는 순수함수라 테스트가 붙는다 — **diff 쪽이 낫다**)
  - 거부 응답에 **서버 최신 행 목록을 함께 실어 보낸다** (화면 병합용)

**거부됐을 때의 화면 — 배너 + 자동 병합 + 새 줄 하이라이트** (2026-09-02 결정)

확인 모달은 **쓰지 않는다.** 모달이 화면을 가려 정작 무엇이 들어왔는지 못 보게 하고,
「예」를 누르는 게 확인이 아니라 반사 클릭이 된다. 토스트도 몇 초 뒤 사라져 현장에서 놓친다.
Jira·Confluence가 쓰는 **안 사라지는 배너** 방식으로 간다.

```
┌─────────────────────────────────────────────┐
│ ⚠ 이영명님이 톤백 550kg × 1을 추가했습니다.  │  ← 안 사라지는 배너
│   아래에 반영했습니다. 확인 후 저장해 주세요. │
├─────────────────────────────────────────────┤
│  4kg   × 267                                │  ← 내가 입력한 것, 그대로
│  톤백  550kg × 1              [새로 들어옴] │  ← 하이라이트
└─────────────────────────────────────────────┘
                              [저장]  ← 다시 누르면 통과
```

**저장을 다시 누르는 것 자체가 확인 단계다.** 모달을 또 끼우면 확인을 두 번 시키면서
첫 번째 확인은 내용을 가린 채 받게 된다.

**🔴 필수 조건 — 「저장 차단」이 「입력 날림」이 되면 안 된다**

어제 결정의 핵심 조건이고, 오늘 사고 후반부가 정확히 그것이었다. 거부 시:

1. **화면 입력값을 절대 초기화하지 않는다** — `setOutputs([])`·`restoreOutputs(initialOutputs)` 재실행 금지
2. 응답에 실려온 **남의 줄을 화면에 합쳐서** 보여준다
   (예: *"이영명님이 톤백 550kg × 1을 추가했습니다. 확인 후 다시 저장해 주세요."*)
3. 사용자가 확인하면 **baseline을 갱신**하고, 다시 저장을 누르면 통과

즉 거부는 **한 번뿐인 확인 단계**여야 하며, 재입력을 요구해선 안 된다.

### P5. `count = 0` 줄을 조용히 버리지 않는다

**문제**: [add-packaging-dialog.tsx:226](<../../app/(dashboard)/milling/add-packaging-dialog.tsx#L226>)·[:361](<../../app/(dashboard)/milling/add-packaging-dialog.tsx#L361>) `outputs.filter(o => o.count > 0)`.
수량이 안 채워진 줄은 **경고 없이** payload에서 빠지고, 그게 기존 행이었으면 **삭제까지 된다.**

**변경**:
- **기존 행(`id` 있음)이 `count === 0`** → 저장 중단 + `toast.warning('N번째 줄(규격) 개수를 입력해 주세요.')`
  (조용히 지우는 것보다 못 저장하는 게 낫다)
- **새 줄(`id` 없음)이 `count === 0`** → 지금처럼 버리되, 버렸다는 것을 알린다

※ 톤백은 `addToGroup`에서 `count: 1`로 시작하므로 이 경로에 안 걸린다. **잔량·일반 줄이 대상.**

### P4가 못 잡는 것 (알고 간다)

baseline은 **「내가 못 본 행」만** 잡는다. 둘이 **같은 행을 동시에 고치면**(예: 둘 다 4kg 줄의
개수를 수정) baseline에 그 id가 있으니 통과되고 **나중에 저장한 쪽이 이긴다**(last-write-wins).

이번 사고는 「행이 통째로 사라짐」이었고 그게 훨씬 위험하므로 여기부터 막는다.
같은 행 동시 수정은 P1 감사로그가 들어가면 최소한 **추적은 된다.** 필요하면 별도 항목으로.

## 7. 적용 범위 — 왜 포장 다이얼로그만인가 (전수 조사, 2026-09-02)

> 나중에 「다른 화면은 왜 안 했지?」로 다시 헤매지 않도록 근거를 남긴다.

위험한 것은 **「목록을 통째로 보내 안 보낸 것은 삭제」** 하는 저장 방식뿐이다.
`app/actions/` 전체의 `deleteMany` 호출을 전수로 훑은 결과:

| 위치 | 무엇을 지우나 | 위험 |
|---|---|---|
| [milling.ts:577](../../app/actions/milling.ts#L577) | 포장 내역 diff | 🔴 **이것 하나. P3·P4 대상** |
| [milling.ts:722](../../app/actions/milling.ts#L722)·[:805](../../app/actions/milling.ts#L805) | 배치 통째 삭제 | ❌ 「이 배치 삭제」를 명시적으로 누른 것 |
| [repack.ts:510](../../app/actions/repack.ts#L510) | 재포장 취소 | ❌ `repackId` 지정 = 명시적 |
| [purchase-order.ts:549](../../app/actions/purchase-order.ts#L549)·[:586](../../app/actions/purchase-order.ts#L586) | 차감 취소·업로드 삭제 | ❌ 명시적 |
| [release.ts:214](../../app/actions/release.ts#L214) | 출고 내역 삭제 | ❌ `ids` 목록 = 사용자가 고른 것만 |

나머지는 전부 **「이것을 지워라」로 대상을 지정**해서 받는다. 포장만 **「이게 전부다」** 라고
목록을 통째로 선언하는 방식이라 안 보낸 것이 삭제로 해석된다.

- **P3·P4 → 포장 다이얼로그만.** 다른 곳은 막을 것이 없어 코드만 늘어난다
- **P1(감사로그) → 위 삭제 경로들은 이미 `recordAuditLog`가 붙어 있다.**
  `updatePackagingLogs`만 빠져 있었고 그것이 이번 추적을 막았다

### 남는 낮은 위험 (지금은 안 건드림)

단건 수정 다이얼로그들도 낡은 스냅샷을 보여줄 수 있다. 다만 **내가 고친 값만 덮어쓰므로
행이 사라지지 않는다** — 최악이 「남이 고친 비고를 내 낡은 값으로 되돌림」 수준이다.
재고 수량이 틀어지는 것과 심각도가 다르다.
