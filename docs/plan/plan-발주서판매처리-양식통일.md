# 계획서 — 통일 양식 확정 + 묶음 단위 재정렬 + 톤백 규격 (단계6 D0·D1 재구성)

_작성: 2026-08-19 · 상위: `docs/plan/plan-발주서판매처리-단계6.md` · 도메인 원본: `docs/plan/plan-발주서판매처리.md` §2.2_

## 1. 배경

단계6 진행 중 **표준 양식이 두 갈래로 갈려** 있었고(템플릿 vs 현장 실파일), 협의 과정에서 실무 운영 방식과 **톤백 규격 문제**가 추가로 드러나 **결정 #26의 일부를 개정**하게 됐다.

| 행 | 구 템플릿 (구 #26) | 현장 실파일 `공장동06.19` |
|---|---|---|
| 1 | 날짜 + 품종·도정(병합) | 날짜 + 품종·도정(병합) |
| 2 | 포장지 | 농가명 *(구 양식 잔재)* |
| 3 | 중량 | 포장지 |
| 4 | `발주처` \| `수령인` | 중량 |
| 5 | 데이터 시작 | 소계 |
| 6 | — | `(발주처)` \| `(수령인)` |
| 7~ | — | 데이터 시작 |

**2026-08-19 새 템플릿 수령** — `docs/resources/발주서-통일양식-템플릿.xlsx`가 확정 양식(#27)으로 갱신됐다. 시트 5장: `이마트_260819` · `택배_260818` · `서울급식_060818` · `해남급식_260821` · `시아스_260811`.

추가로 드러난 현장 사실:
- 실파일은 **한 통합문서에 주차별 시트 50장**이 누적되는 업무 관리 파일이다. 공장동 시트는 학교별 시트를 참조한다(`='학교별08.21'!C22`) — 시스템이 읽을 대상은 **공장동**.
- **채널이 다른 발주는 같은 시점에 함께 발생**한다.
- **톤백은 자루당 중량이 로트마다 다른데**(실측 147종), 발주서는 `1,000kg`·`200kg`처럼 중량을 지정해 주문한다.

## 2. 확정 사항 (2026-08-19 협의 — 결정 #27~#34)

### #27 통일 양식 행 구조

```
1행  날짜/제목(A열)          | C열~ 품종+도정명 (규격 그룹 병합)
2행  A='포장지'              | C열~ 포장지명 (빈칸 허용 = 기본 포장지, #21)
3행  A='중량'                | C열~ 규격 (10kg / 1kg / 420g …)
4행  A='소계' (A:B 병합)     | C열~ 열별 합계
5행  A='(발주처)'  B='(수령인)'
6행~ 데이터 (A=발주처, B=수령인, C열~ 주문 수량)
```

- **농가명 행 폐기**(구 양식 잔재). 농가·로트는 시스템이 배분한다.
- A열 라벨은 **괄호·공백 무관**하게 인식(`(발주처)` = `발주처`). 소계 라벨은 `소계` **포함**이면 인정(`품목별 소계`·`택배 소계`).
- 소계 행이 **없는 시트도 허용**(구 템플릿 하위호환). 있으면 검증에 쓴다.
- **품목명 칸의 빈 괄호는 파서가 제거**한다. 실셀이 `유기농⏎백미⏎천지향5세⏎(         )`(농가명 기입란 잔재)라 그대로 정규화하면 `유기농 백미 천지향5세 ( )`가 되어 품종 매칭이 깨진다. 양식 정리로 사라질 예정이지만 들어와도 견디게 한다.
- **1행 A열 제목은 사람 확인용**. 파서는 발주일 기본값 추측·교차확인에만 참고한다(#31).

### #28 음수 조정 행 금지 → 비고란 사용

현장 파일에 상시 존재했던 패턴:

```
7행  해남급식 | 싱싱유통   62     ← ='학교별06.19'!C22
8행  해남급식 | 급식센터   15
12행 해남고등학교 | 보관요청  -50 ← ★음수 조정 행
소계 = 62+15+0+0-50 = 27
```

현재 파서는 `qty > 0`만 담아 −50을 버리므로 **77개로 읽어 50개 과차감**이 된다.

→ **발주서엔 실제 출고 수량만. 음수 금지.** 보관요청·후입고 같은 조정 사유는 시트별 비고(#30)에 적는다.
→ 파서는 음수를 만나면 **무시하고 경고**를 남긴다(조용한 누락 금지).

### #29 소계 = 파싱 검증에 활용

열별 `Σ(데이터 행 수량)`과 소계 셀을 대조해 다르면 경고(차단 아님). 수식 오류·행 누락·#28의 음수 행을 업로드 시점에 드러내는 안전망.

- 소계 셀은 **4~5행 세로 병합**(`C4:C5`)인 시트가 있다 → 라벨 행에서 병합 펼치기로 읽으면 소계값이 잡히므로, 규격·수량은 **직접 값**으로만 읽는다.
- 데이터 행 아래 부속 행(단가 47000 / 금액 `=C14*C5`)은 **A열이 비어 파서가 이미 건너뛴다**. 결정 #25(금액 미관리)와 충돌 없음.

### #30 묶음 단위 = 「파일」에서 「시트」로 (구 #26 「파일 1개 = 채널 1개」 폐기)

```
구:  파일 1개 = 묶음 1개 (채널 1개 강제, 섞이면 업로드 거부)
신:  시트 1장 = 묶음 1개 (채널·발주일·비고가 시트 단위)
     파일 하나에서 3시트 체크 → 묶음 3건 생성
```

- 구 #26이 채널을 하나로 묶은 취지는 「매트릭스(행=수령처 × 열=규격)가 성립하려면 묶음이 단일 채널」이었다. **묶음 단위를 시트로 내리면 그 취지를 그대로 지키면서** 다채널 동시 업로드가 풀린다. 채널 혼합 거부 로직은 삭제.
- 같은 채널의 시트 여러 장도 별개 묶음으로 허용(지난주 누락분 동반 업로드).
- **비고·발주일은 시트(=묶음) 단위**로 갖는다.

### #31 업로드 2단계 + 시트 선택 UI

```
파일 선택 → [서버] 파싱만 → 시트 목록 + 시트별 요약
          → 체크 + 채널·발주일·비고 확인 → [서버] 선택 시트만 적재
```

- 파싱 결과를 클라이언트가 들고 있다가 되돌려주는 방식은 **쓰지 않는다**(값 조작 가능 — 시스템 경계). 적재 시 **파일을 한 번 더 전송**하고 서버가 재파싱한다(실파일 363KB, 부담 없음).
- **시트 인식 판정 = 헤더 구조**(`포장지`·`중량` 라벨 존재)로 한다. 시트명 규칙은 필수가 아니다.
  - 학교별 시트는 헤더에 `포장지` 라벨이 없어 **자동으로 인식 불가** 처리 → 「공장동만 올리기」가 별도 작업 없이 해결.
- **채널·발주일은 시트명에서 추측하고, 못 뽑으면 화면에서 지정**한다(구 #26의 `채널_YYMMDD`는 강제 규칙 → 자동 채움 힌트로 완화).
  - 채널: 시트명 prefix 4종 화이트리스트 일치 시 자동, 아니면 드롭다운 선택(직전 선택 기억)
  - 발주일: 시트명 끝 `YYMMDD` → `MM.DD` → 1행 A열 제목(`26/08/18 (화)`) 순으로 추측
  - **시트명 날짜와 1행 제목 날짜가 어긋나면 경고**. 실제로 새 템플릿에 `서울급식_060818`(2006년으로 읽힘, 제목은 `26/08/18`) 오타가 있었다.
- 혼동 방지: 행마다 채널·발주일·수령처 수·라인 수를 확인하고 올린다 + 「선택한 n개 시트 → **묶음 n건**이 만들어집니다」로 결과를 미리 못 박는다.

업로드 모달 형태:

| ☑ | 시트 | 채널 | 발주일 | 내용 | 비고 |
|---|---|---|---|---|---|
| ☑ | `공장동08.21` | 해남급식 ▾ | 2026-08-21 | 수령처 4곳 · 12라인 | ⌨ |
| ☑ | `이마트_260819` | 이마트 *(자동)* | 2026-08-19 | 수령처 3곳 · 7라인 | ⌨ |
| ☐ | `학교별08.21` | — | — | 인식 불가 (발주서 양식 아님) | |
| ☐ | `공장동08.14` | 해남급식 ▾ | 2026-08-14 | 수령처 4곳 · 10라인 | ⌨ |

### #32 일반기업(CORPORATE) 시트 = 발주처·수령인 열 없음

`시아스_260811`은 다른 채널과 구조가 다르다.

```
r0: 8/11(화)⏎오후상차 | 유기농⏎가바백미 | · | 유기농⏎가바현미 | ·
r1: 포장지  | 톤백    | 톤백  | 톤백    | 톤백
r2: 중량    | 1,000kg | 200kg | 1,000kg | 200kg
r3: 소계    | 1 | 1 | 1 | 1
r4: 시아스  | 1 | 1 | 1 | 1     ← 라벨 행 없이 바로 데이터
```

- `(발주처)`/`(수령인)` **라벨 행이 없고**, 그래서 **규격 열이 B열부터** 시작한다(다른 채널은 C열).
- → 파서는 `FIRST_SPEC_COL = 2` 하드코딩을 버리고 **규격 열 = 중량 행에 값이 직접 있는 열**로 판정한다.
  - 다른 채널의 B열은 `중량` 라벨의 A:B 병합에 속해 직접 값이 없으므로 자동 제외된다.
- → 라벨 행이 **없으면** 데이터 시작 = 소계 행 + 1, **수령인 = 발주처 복사**.
- → 시트 인식 판정에서 `발주처` 라벨은 **필수가 아니다**(`포장지`·`중량`만 필수).

### #33 규격(중량) 표기 정규화

새 템플릿의 중량 표기가 갈렸다. 원인은 **엑셀 셀 서식**이다.

| 시트 | 셀 원시값 | 표시 텍스트 | 비고 |
|---|---|---|---|
| 서울급식 | `1` (숫자) | `1 kg` | 서식 코드 `0\ "kg"` — **단위가 서식에 있다** |
| 이마트 | `"1 kg"` (문자) | `1 kg` | 문자열에 공백 |
| 시아스 | `"1,000kg"` | `1,000kg` | 콤마 |
| 나머지 | `"10kg"` | `10kg` | 정상 |

- 파서는 지금 `cell.v`(원시값)만 읽어 서울급식을 단위 없는 숫자로 봤다 → **중량 셀은 `cell.w`(표시 텍스트) 우선, 없으면 `cell.v`**로 읽는다. 기본 read 옵션에서도 `w`가 생성되는 것을 확인했다.
- 정규화: **공백·콤마 제거**(`1 kg`→`1kg`, `1,000kg`→`1000kg`). 단위는 양식에서 필수로 요구하고, 정규화 후에도 단위가 없으면 **매칭 실패 + 경고**.

### #34 톤백 = 요구 자루중량을 라인에 보관 + 수동 로트 지정

**문제** — SKU 규격은 `톤백` 한 덩어리인데, 자루당 중량은 재고 행마다 다르다(실측). 발주서는 중량을 지정해 주문한다.

```
DB 실측: packageType='톤백' 출력 199건 / 서로 다른 중량 147종
         (1003 · 3012 · 788 · 1078 · 460 … 규격이 아니라 실측값)

SKU: CJ6 / 백미 / 톤백  (SKU는 12개뿐)
 ├ #1277  자루당 1004kg  ×4자루
 ├ #1284  자루당  500kg  ×1자루
 └ #1283  자루당  100kg  ×1자루

발주서(시아스): 톤백 1,000kg ×1 / 톤백 200kg ×1
```

규격을 실측 중량으로 바꾸면 **SKU가 147개로 폭발**하므로 배제. 확정 방향:

- SKU 매칭은 **규격 `톤백`으로 성공 처리**한다(포장지가 `톤백`인 라인은 규격을 `톤백`으로 치환).
- 발주서의 중량(`1,000kg`)은 **`PurchaseOrderItem.unitWeightKg`에 요구 자루중량으로 저장**한다.
- **톤백류는 자동 FIFO 배분을 거치지 않는다.** 매트릭스 셀 팝오버에서 재고 행 목록(자루 중량 표시, 요구 중량 근접 순)을 보여주고 **사람이 선택**한다.
- SKU 체계·재고 구조는 **무변경**. 발주 라인에 필드 하나 추가가 전부다.

### #35 박스 환산표 = 시스템이 생성 (2026-08-20 추가)

이마트 시트 하단에 있던 **박스 환산표**는 현장에서 포장·출고 작업에 쓰는 자료다. 지금은 사람이 매주 손으로 채운다.

```
r10    · | 현미1kg | 가바4kg | 가바1kg | 천지향4kg | 귀리420g …   ← 별도 표 헤더
r11    여주(이마트) | · | · | 7박스 | 6박스 | 1박스 | 14박스 | 1파렛
```

→ **엑셀에 없어도 시스템이 만들어 준다.** 발주 수량을 SKU별 입수로 나눠 박스 수를 계산한다.

**입수는 규격이 아니라 SKU 속성이다** — 실파일 역산으로 확인:

| SKU | 발주 수량 → 박스 | 입수 |
|---|---|---|
| 가바백미 1kg **자연주의** | 112→7 · 32→2 · 96→6 | **16개/박스** |
| 가바현미 1kg **PET** | 10→1 | **10개/박스** |
| 천지향 4kg 자연주의 | 24→6 · 24→6 · 16→4 | 4개/박스 |
| 귀리쌀 420g PET | 20→1 · 40→2 | 20개/박스 |

같은 `1kg`인데 포장지에 따라 16 / 10으로 갈린다 → 규격 단위 하드코딩으로는 성립하지 않는다.

확정:

- **입수는 SKU 마스터에 둔다** — `ProductType.unitsPerBox Int?` 신설. 이미 있는 `/admin/product-types` 관리화면에 입력칸을 추가한다. 코드 하드코딩은 마스터 이중화(SKU 추가마다 코드 수정·배포)라 배제.
- 박스 수 = `ceil(주문 수량 / unitsPerBox)`. 행별 **합계 박스**도 함께 낸다.
- `unitsPerBox` 미입력 SKU는 박스 칸을 **빈칸**으로 두고 경고. 계산이 틀린 값을 내놓지 않는다.
- **파렛은 자동 계산하지 않는다.** 실파일 기준이 규칙적이지 않고(14박스→1파렛 · 13박스→1파렛 · 8박스→빈칸) 현장 판단이라 **사람이 비고에 적는다**.
- 적용 채널은 **이마트**. 다른 채널에도 필요해지면 같은 계산을 그대로 쓴다(입수가 채워진 SKU만).
- 출력 위치는 **D5 엑셀 내보내기**(원본 양식 복원 시 이마트 시트 하단에 재생성)가 기본. 화면 표시는 D2 매트릭스에서 별도 검토.
- 파서는 엑셀에 이 표가 있어도 **읽지 않는다**(§3.2 「하단 별도 표 종료」). 진실 원천은 시스템 계산값이다.

- **낱개는 없다**(2026-08-20 사용자 확인) — 이마트 발주는 항상 박스 단위로 떨어진다. 실파일 8건도 전부 정확히 나눠떨어졌다(112/16 · 24/4 · 40/20 …). `6박스+4개` 같은 혼합 표기는 만들지 않는다. 다만 계산은 `ceil`로 두어 예외가 들어와도 박스 수가 모자라지 않게 한다.

## 6. 리스크 / 확인 필요

1. **파일 2회 전송** — preview·upload에서 각각 파싱. 실파일 363KB라 문제없지만, 더 큰 파일이 들어오면 `validateExcelUpload`의 크기 상한을 재확인한다.
2. **원본 파일 보관** — 현재는 파싱 후 버린다(DB에 바이너리 없음). D5 「엑셀 내보내기 — 원본 양식 복원」에서 필요할 수 있어 **D5 시점에 결정**(오브젝트 스토리지 신설 여부).
3. **품종 매칭** — 새 템플릿 품목명(`유기농 백미 천지향5세`·`유기농 찹쌀현미`·`유기농 가바현미` 등)의 매칭 성공률은 D1c 실업로드에서 확인. 실패 품목은 별칭 학습(#22)·SKU 마스터 보완으로 해소(단계6 G12).
4. **외부 참조 수식** — 서울급식은 `SUMIFS('[2]은평구08.18'!…)`, 해남급식은 `='[1]학교별08.21'!C22`로 다른 통합문서를 참조한다. 계산된 **캐시값이 셀에 남아 있어 파싱은 정상**이지만, 참조가 끊긴 채 저장된 파일이 올라오면 값이 낡을 수 있다. #29 소계 검증이 1차 방어선이 된다.
5. **톤백 요구 중량과 실재고 괴리** — 1,000kg 주문에 1,004kg 자루뿐인 상황이 정상이다. 수동 지정(#34)이라 시스템이 막지는 않지만, 매트릭스에 요구 중량 대비 실제 중량을 함께 보여줘 사람이 판단하게 한다.

## 7. 미결 — 재고 분할 차감 (2026-08-19 보류, 나중에 협의)

#34는 「1,004kg 자루를 **통째로** 1개 차감」까지만 정한 것이다. **자루를 쪼개 쓰는 경우가 남아 있다.**

```
주문: 톤백 1,000kg ×1
재고: 자루당 1,004kg ×1
→ 1,000kg만 내보내고 4kg는 남기려면?
```

- 현재 차감 모델 `PackageMovement.count`는 **개수(정수)만** 갖는다. 부분 중량 차감을 표현할 수 없다.
- 생각해볼 방향(아직 어느 것도 선택 안 함):
  - `PackageMovement`에 중량 필드를 추가해 kg 단위 차감을 허용
  - 자루를 쪼갤 때 재고 행을 분할(1,004kg ×1 → 1,000kg ×1 + 4kg ×1)하는 「재포장/분할」 액션을 두기
  - 남는 소량은 `잔량` 규격으로 넘기기(도정산의 잔량 처리 방식과 통일)
- 잡곡·일반 규격 제품에도 같은 문제가 있는지(예: 10kg 20개 주문에 낱개 차감) 함께 확인해야 한다.
- **D2(매트릭스 차감) 착수 전까지는 결정해야 한다.** D0·D1a~c는 이 결정과 무관하게 진행 가능하다.
