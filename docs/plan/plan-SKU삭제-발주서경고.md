# SKU 삭제 시 발주서 매칭 경고

> 상태: ✅ 완료 (브라우저 확인 1~3 통과 2026-09-28) · 작성 2026-09-28 · 보고서 `docs/report/report-SKU삭제-발주서경고-2026-09-28.md`
> 발단: `docs/report/report-발주서-도정접두분리-2026-09-28.md` §3 — 9/23 SKU 58 삭제로 #15 택배 2품목이 조용히 매칭실패가 됐다

## 1. 무슨 일인가

`ProductType`(SKU)을 가리키는 것은 **두 개**다.

| 참조자 | 관계 | 지울 때 |
|---|---|---|
| `MillingOutputPackage.productTypeId` (제품재고) | 옵셔널 | ✅ 가드가 막는다 — 「포장 n건에서 사용 중」 |
| `PurchaseOrderItem.productTypeId` (발주서 품목) | 옵셔널 · `onDelete` 미지정 = **SetNull** | ❌ **가드가 안 센다 → 조용히 null = 매칭실패** |

삭제 가드(`deleteProductType`)는 발주서가 들어오기 전(2026-06-17)에 만들어졌고, 발주서 품목이
**두 번째 참조자**로 붙을 때 가드가 같이 늘지 않았다. 품종 삭제 가드가 SKU를 안 셌던 것(2026-09-16)과 같은 모양이다.

🔴 차감된 품목은 안전하다 — 차감했다면 그 SKU의 제품재고가 있으니 첫 번째 가드가 막는다.
**구멍은 「매칭은 됐는데 아직 차감 안 한 품목」**이다. 9/23 사고가 정확히 그 경우였다(차감 이력 0건).

## 2. 방향 — 막지 않고 알린다

막으면 안 되는 이유: SKU 정리(PET → 땅끝미가처럼 포장지를 바꾸는 것)는 정상 업무고,
풀린 품목은 **재매칭 한 번**이면 다른 SKU로 다시 붙는다(9/28 #15에서 실증).
문제는 삭제가 아니라 **삭제한 사람이 그 결과를 모른다**는 것이다.

## 3. 변경

**파일**: `app/actions/product-type.ts` · `app/(dashboard)/admin/product-types/product-type-page-client.tsx`

1. **`getProductTypeUsage(id)` 액션 신설** — 삭제 버튼을 누른 순간 조회한다(페이지 로드 값은 낡을 수 있다)
   - `packages`: 제품재고 수
   - `orderItems`: 이 SKU에 붙은 발주서 품목을 **시트별로** 묶은 목록 `[{ sheetName, count }]`
2. **삭제 확인창**
   - 제품재고가 있으면 → 확인창 없이 **바로 안내**(지금은 확인창을 띄운 뒤에야 서버가 거절한다 — 확인하고 나서 거절당하는 순서가 이상하다)
   - 발주서 품목이 있으면 → 확인창에 경고를 붙인다:
     > 발주서 **2품목**이 이 SKU에 붙어 있어요(택배_260818 2). 삭제하면 **매칭실패**로 돌아가요.
     > 대신할 SKU가 있으면 그 시트에서 **재매칭**하면 다시 붙어요.
   - 없으면 → 지금 확인창 그대로
3. **감사로그** — `제품유형 삭제: id=58 (발주서 2품목 매칭 해제)`. 나중에 「왜 풀렸지」를 로그로 찾을 수 있게
4. 서버 가드(`deleteProductType`의 제품재고 검사)는 **그대로 둔다** — 클라이언트 사전 조회는 안내일 뿐, 최종 판정은 서버다

## 4. 하지 않는 것

- **삭제 후 자동 재매칭** — 어느 SKU로 붙을지 사용자가 보고 결정하는 게 맞다(기본 SKU 지정 순서에 따라 결과가 달라진다)
- **비활성화 경고** — 비활성화는 기존 매칭을 안 건드린다(매처가 새 매칭에서만 거른다). 지금 동작이 맞다

## 5. 단계

1. 액션 + 확인창 + 감사로그
2. `tsc` · `eslint` · `npm test`
3. **사용자 브라우저**: 제품유형 관리 → 발주서에 붙은 SKU의 삭제 버튼 → 경고 문구만 보고 **취소**
   (실제로 지우지 않는다 — 발주서에 붙은 SKU가 뭔지는 구현 후 DB에서 뽑아 알려 준다)
