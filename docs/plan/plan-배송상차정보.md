## 1. 작업 목표

발주서 묶음에 **무엇이 언제 어떻게 나가는지**를 붙인다. 상차 정보를 시스템이 관리하려는 게 아니라,
목록에서 한눈에 보이게 해서 **먼저 나갈 것이 먼저 포장되도록** 순서를 잡는 게 목적이다.

시안이 근거로 삼은 세 가지 사실:

| 사실 | 설계에 미치는 영향 |
|---|---|
| 날짜는 알아도 **시각은 대개 미정** | 시각을 필수 입력칸으로 만들지 않는다. 「시간 미정」이 기본 선택 |
| 배송방법은 **90% 이상 채널과 함께 고정** | 채널 기본값으로 자동 채우고 예외만 고친다 |
| 실제 전달은 **구두** | 화면이 구두를 대체하려 들지 않는다 |

### 하지 않는 것 (시안 명시)
- 기사 연락처·차량번호·하차지 주소 필드 — 발주서에 없어서 손으로 채워야 하고, 그런 칸은 비어 있게 된다
- 최근 이력에서 배송방법 자동 추론 — 예외 한 번에 기본값이 오염된다
- A1의 배송 문구("화물 배차 예정" 등) 화면 노출 — 파싱 힌트로만 쓴다

## 2. 확정된 결정

### 결정 #36 — 배송방법은 enum이 아니라 마스터 테이블
시안은 `enum 7종`을 제안했으나 **관리자 페이지에서 목록을 관리**하는 방식으로 바꾼다.
수출건은 그때그때 컨택된 업체라 enum으로는 담기지 않고, 관리자 페이지에서 먼저 등록해서 쓴다.

초기 등록 7종: `경동화물 · 대신화물 · 전국화물 · 해남원형화물 · 롯데택배 · 직접배송 · 방문수령`

### 결정 #37 — 상차 정보는 전부 nullable
상차일·상차시각 모두 비워도 등록된다. 목록에 「배차 미정」으로 남아서 오히려 채워진다.
필수로 만들면 배차 안 정해진 날 아무거나 채워두고 끝까지 안 고친다.

### 결정 #38 — 채널별 기본 배송방법은 `SystemConfig` 재사용
도정유형별 기준 수율(`yield_rate_*`)과 같은 key-value 패턴을 쓴다. 새 테이블을 만들지 않는다.

### 결정 #39 — 배송방법은 삭제가 아니라 비활성
과거 묶음이 참조하고 있어서 하드 삭제하면 이력이 깨진다. `active=false`로 목록에서만 숨긴다.

### 결정 #40 — 설정 화면은 `/admin/settings` 한 곳에 섹션으로 쌓는다
배송방법 관리를 별도 라우트로 빼지 않고 수율 화면 안에 섹션으로 넣는다.
앞으로 설정 아이템이 더 생길 것을 전제로, 화면을 늘리는 대신 **한 화면에 섹션을 추가하는 구조**로 간다.

### 결정 #41 — 차량 톤수는 다루지 않는다
시안 목록 예시의 `오늘 14:00 · 5톤`은 반영하지 않는다. 상차 열에는 **배송방법 이름**만 붙인다.

## 3. 데이터 모델

```prisma
// 배송방법 마스터 — 화물사·직접배송·방문수령, 수출건 임시 업체도 여기 등록 (결정 #36)
model ShippingMethod {
  id        Int      @id @default(autoincrement())
  name      String   @unique   // '경동화물'
  sortOrder Int      @default(0)    // 목록 표시 순서
  active    Boolean  @default(true) // 안 쓰는 업체는 숨김 — 과거 묶음은 유지 (결정 #39)
  uploads   PurchaseOrderUpload[]
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}

// 상차 시각 — 대개 미정이라 UNKNOWN이 기본값 (결정 #37)
enum LoadingTimeSlot {
  UNKNOWN
  AM
  PM
  EXACT // loadingTime에 'HH:mm'이 들어있을 때만
}

model PurchaseOrderUpload {
  // ... 기존 필드
  shippingMethodId Int?
  shippingMethod   ShippingMethod? @relation(fields: [shippingMethodId], references: [id])
  loadingDate      DateTime?       // 상차일 — 비면 「배차 미정」
  loadingTimeSlot  LoadingTimeSlot @default(UNKNOWN)
  loadingTime      String?         // 'HH:mm' — slot이 EXACT일 때만

  @@index([loadingDate]) // 상차 임박순 정렬
}
```

**시안과 다른 점**: 시안은 `loadingTimeSlot (UNKNOWN | AM | PM | HH:mm)` 한 필드로 표현했지만,
DB에서는 enum + 시각 문자열을 분리한다. 한 필드에 섞으면 조회할 때마다 파싱해야 한다.

**채널 기본값** (`SystemConfig`, 결정 #38):
`default_shipping_method_DELIVERY` → `"3"` (ShippingMethod.id를 문자열로)

## 4. 구현 단계

### S1. 스키마 + 마이그레이션 + 시드
- `ShippingMethod` 모델, `LoadingTimeSlot` enum, `PurchaseOrderUpload` 필드 3개 추가
- 마이그레이션 생성 후 **Neon 클라우드 DB에 적용** (로컬 `.env`가 직접 클라우드를 봄)
- 배송방법 7종 시드 — 기존 시드 스크립트 패턴 따름
- 산출: `prisma/schema.prisma`, `prisma/migrations/...`, 시드 스크립트

### S2. 관리자 화면 — 배송방법 관리
- 서버 액션: 목록 조회 / 추가 / 이름·순서 수정 / 비활성 토글, 채널 기본값 조회·저장
- 권한: 조회는 `requireSession`, 변경은 `requireAdmin` (기존 `settings.ts` 패턴과 동일)
- 화면: `/admin/settings`에 **배송방법 섹션**을 추가 (결정 #40). 기존 수율 섹션과 나란히 놓고,
  `settings-client.tsx`가 커지면 섹션별 컴포넌트로 분리한다
- 채널 기본값은 채널 5종 × 배송방법 드롭다운 한 줄씩
- 산출: `app/actions/shipping-method.ts`, 관리자 화면 파일

### S3. 발주서 등록 2단계 모달 — 시트 행에 배송 블록
- `previewPurchaseOrder` 응답에 배송방법 목록 + 채널 기본값을 실어 보낸다
  (모달이 열릴 때 이미 채워져 있어야 하므로 별도 왕복을 만들지 않음)
- 시트 행 아래 배송 블록: `배송 방법` 드롭다운(채널 기본값 자동 선택) · `상차일`(비워도 됨) · `상차 시각` 토글
- 시각 토글은 「시간 미정 / 오전 / 오후 / 직접 입력」, **기본 선택은 「시간 미정」**
- 채널을 바꾸면 배송방법도 그 채널 기본값으로 따라 바뀐다 (사용자가 직접 고른 뒤에는 건드리지 않음)
- `UploadSelection`에 배송 3필드 추가 → `uploadPurchaseOrder`가 묶음에 저장
- 산출: `app/(dashboard)/sales/upload-dialog.tsx`, `app/actions/purchase-order-upload.ts`

### S4. 묶음 목록 — 「상차」 열
- 열 추가: `오늘 14:00 · 경동화물` / `내일 · 롯데택배` / `배차 미정` / `8/18 상차 완료`(흐리게)
- **기본 정렬을 상차 임박순으로.** 업로드 시각순은 사람이 신경 쓰는 순서가 아니다
- 상차일이 없는 묶음은 뒤로 보내고, 그 안에서는 업로드 최신순
- 「배차 미정」은 그 자리에서 눌러 채우는 버튼 — 모달을 다시 열지 않는다 (`updateUploadNote`와 같은 결의 인라인 수정 액션)
- 산출: `app/(dashboard)/sales/upload-table.tsx`, 액션 1개 추가

## 5. 리스크

| 수준 | 내용 | 대응 |
|---|---|---|
| 중 | `upload-dialog.tsx`가 이미 441줄. 배송 블록을 넣으면 800줄 제한에 근접 | `SheetRow`를 별도 파일로 분리 (S3에서 같이) |
| 중 | 기본 정렬이 업로드순 → 상차 임박순으로 바뀜. 기존 묶음은 상차 정보가 전부 비어 있음 | 상차일 null은 뒤로 → 기존 묶음은 지금과 같은 순서로 보임 |
| 낮 | 상차 완료 판정 | 별도 플래그 없이 **상차일이 오늘보다 과거면 완료**로 본다. 필드를 늘리지 않는다 |
| 낮 | 배송방법을 지우려는 시도 | 비활성만 제공, 삭제 버튼 없음 (결정 #39) |

## 6. 채널별 기본 배송방법 초기값 (제안)

채널명과 배송방법이 **이름으로 맞물리는 둘만** 시드에 넣고, 나머지는 비워둔 채 시작한다.
근거 없이 채워두면 그게 기본값으로 굳어져 틀린 채로 등록된다 — 비어 있으면 첫 등록 때 사람이 고르고,
그 값을 관리자 화면에서 확정하면 된다.

| 채널 | 기본 배송방법 | 근거 |
|---|---|---|
| 택배 `DELIVERY` | 롯데택배 | 채널 성격과 1:1 |
| 해남급식 `MEAL_HAENAM` | 해남원형화물 | 지역이 일치 |
| 이마트 `EMART` | (비움) | 어느 화물사인지 알 수 없음 |
| 서울급식 `MEAL_SEOUL` | (비움) | 〃 |
| 기업별 `CORPORATE` | (비움) | 건마다 달라 기본값이 성립하지 않음 |

비어 있어도 등록은 막히지 않는다(결정 #37). 목록에서 배송방법 없이 상차일만 보이는 상태가 된다.
