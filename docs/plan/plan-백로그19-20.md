## 2. 조사 결과 — 백로그가 적어둔 것과 다른 점

### 2.1 🔴 §19는 벼만의 문제가 아니었다

백로그 §19는 「차감된 **벼** 포장의 단중·포장지」라고 적혀 있다. 실제로는 **잡곡도 같은 구멍**이다.

`guardIdentityChange`는 `packageType`·`varietyId` 둘만 본다(`lib/package-guard.ts:95`).
그런데 잡곡 수정 액션 둘 다 `weightPerUnit`을 입력으로 받는다:

| 액션 | 스키마 | 지금 검사 |
|---|---|---|
| `updateMiscPackage` (`packages.ts:560`) | `packageType` · **`weightPerUnit`** · `count` | packageType만 |
| `updateMiscPurchase` (`packages.ts:987`) | 매입처 · 품종 · 매입일 · `packageType` · **`weightPerUnit`** · `count` | packageType · varietyId만 |

즉 **결정 #70(A안)이 「품종·규격」이라 부른 정체(identity)에 단중이 빠져 있었다.**
1kg × 100을 10개 판 뒤 단중을 10kg으로 바꾸면 팔린 물건의 중량이 소급해 바뀐다 — 벼와 완전히 같은 사고다.

→ **#72: 정체 = 품종 · 규격 · 단중 · 포장지.** 네 축을 한 함수가 함께 본다. 벼·잡곡 구분 없이.

### 2.2 §20의 실제 지점은 4곳이 아니라 6곳 + 로컬 헬퍼 1개

백로그가 적은 4곳 외에 `packages.ts`에 로컬 `toGuarded`(`:31`)가 이미 있고, `purchase-order.ts:136`에 aggregate 판이 하나 더 있다.

| # | 위치 | 모양 | 조치 |
|---|---|---|---|
| 1 | `milling.ts:517` | 인라인 `movedCount` | 헬퍼로 |
| 2 | `packages.ts:42` (`toGuarded`) | 로컬 헬퍼 — **파일 밖에서 못 쓴다** | `lib/`로 승격 |
| 3 | `packages.ts:229` | 인라인 `available` (목록 필터) | 헬퍼로 |
| 4 | `purchase-order.ts:66` | 인라인 `available` (FIFO 배분) | 헬퍼로 |
| 5 | `repack.ts:74` (`availableOf`) | 로컬 헬퍼 | 헬퍼로 |
| 6 | `purchase-order.ts:136` | `packageMovement.aggregate` (DB 집계) | **손대지 않음** — 아래 |

**#73: DB 집계(aggregate)는 통합 대상이 아니다.** `purchase-order.ts:136`·`package-movement.ts:51,75`는 행을 로드하지 않고 DB에서 합을 낸다. 같은 공식이지만 **계산 위치가 다르다** — 메모리 헬퍼로 바꾸면 왕복이 늘거나 전 행을 끌어와야 한다. 공식이 어긋날 위험은 주석으로 연결한다.

## 3. 변경 설계

### 3.1 §19 — `guardIdentityChange` 확장

**#74 GuardedPackage에 파생 속성을 얹는다.** `weightPerUnit`·`packagingId`를 **옵셔널**로 추가한다.
호출부가 안 넣으면 그 축은 검사하지 않는다 — 잡곡 매입처럼 포장지 개념이 없는 경로를 억지로 고치지 않기 위해서다.

```ts
export type GuardedPackage = {
  id: number
  packageType: string
  count: number
  movedCount: number
  repackId?: number | null
  weightPerUnit?: number      // 신규
  packagingId?: number | null // 신규
}
```

**#75 부동소수는 EPSILON으로 비교한다.** `weightPerUnit`은 클라이언트 계산값이 섞인다
(`packaging-diff.ts`가 `totalWeight`에 이미 `EPSILON = 1e-6`을 쓴다). 같은 상수를 `package-guard.ts`로 옮기고 diff가 import해 쓴다 — 두 곳에 두면 어긋난다.

**#76 차단 문구는 헤더만 늘린다.** 지금 `IDENTITY_BLOCKED_HEADER`는 「품종·규격을 바꿀 수 없어요」다.
→ 「**이미 판매·재포장된 포장은 품종·규격·중량·포장지를 바꿀 수 없어요.**」
행별 이유(`describeDeduction`)는 그대로다. 어느 축이 걸렸는지까지 쓰면 문장이 길어지는데, 사용자가 할 일(판매 취소·재포장 정리)은 어느 축이든 같다.

**호출부 3곳:**

| 파일 | 넣을 축 |
|---|---|
| `lib/packaging-diff.ts` | `weightPerUnit` · `packagingId` (규격은 화면 경로 없지만 서버는 함께 막는다) |
| `packages.ts` `updateMiscPackage` | `packageType` · `weightPerUnit` |
| `packages.ts` `updateMiscPurchase` | `packageType` · `varietyId` · `weightPerUnit` |

**#77 diff의 차단 코드에 `IDENTITY_BLOCKED`를 추가한다.** `PackagingDiffErrorCode`에 한 줄, `formatPackagingDiffErrors`에 블록 하나. 삭제·축소와 **문구가 달라야** 사용자가 무엇을 되돌릴지 안다.

🔴 **회귀 위험 — 유효성과 같은 함정.** `d18487e` 때 「전 줄 유효성」이 배치 #73을 통째로 잠갔다.
같은 실수를 피하려면 **정체 검사도 `written`(실제로 쓰는 줄)에만** 걸어야 한다.
현재 `diffPackaging`은 `unchanged`면 `continue`하므로 안 바뀐 줄은 애초에 검사에 안 닿는다 — **그 순서를 지킨다**(정체 검사는 `unchanged` 판정 **뒤**).

### 3.2 §20 — `lib/package-available.ts` 신설

```ts
// select 조각 — 호출부가 이걸 펼쳐 넣는다
export const MOVEMENT_COUNT_SELECT = { movements: { select: { count: true } } } as const

type WithMovements = { count: number; movements: { count: number }[] }

export function movedCountOf(row: { movements: { count: number }[] }): number
export function availableOf(row: WithMovements): number
export function toGuarded<T>(row: ...): GuardedPackage   // packages.ts 로컬에서 승격
```

**#78 `toGuarded`는 `package-available.ts`에 둔다.** 규칙(guard)과 계산(available)을 분리하고, available → guard 단방향 의존만 남긴다(순환 없음). `packages.ts`의 로컬 정의는 지운다.

**동작은 바뀌지 않는다.** 순수 치환이다.

## 7. 확인이 필요한 사항

1. **차감된 잔량 행의 단중 정정이 실무에 필요한가?** 막으면 판매 취소·재포장이 유일한 경로가 된다. 정합성 우선으로 잡았으나, 실무에서 「잔량 무게 오타」가 잦다면 예외 설계가 필요하다.
2. `packagingId` 축은 **벼에만** 건다(잡곡은 SKU 연동이 매입 sentinel 위주). 잡곡까지 필요하면 알려줄 것.
