# 발주서 매트릭스 — 포장지·규격 수정 + 재매칭 확장

작성 2026-10-01 (제품판매 실사용 첫날)

## 발단

사용자, 실제 발주서를 처음 올려 보고:

1. 「엑셀에 포장지를 잘못 등록해서 발주서 전체를 삭제하고 다시 올렸어. 차감 전에 발견했지만, 작업 중에 포장지나 규격을 바꿀 일이 생기면 모두 취소하고 다시 올려야 해. 매트릭스에서 포장지나 규격을 클릭해서 팝업으로 수정할 수 있으면 좋겠어.」
2. 「기본 포장지를 인식하지 못해서 그런 건데, 담당자가 SKU에서 기본 포장지를 바꿨거든. 그런데 그 경우에 재매칭이 안 되더라고.」

## 원인 (코드 확인)

- 엑셀 포장지 칸이 비어 있으면 매처가 (품종·도정·규격) SKU 중 **기본 포장지**를 고른다(`lib/purchase-order-matcher.ts:250-255`).
- 기본 포장지가 틀려 있었으므로 그 줄은 매칭실패가 아니라 **틀린 SKU에 붙은 상태**가 됐다.
- 재매칭(`rematchUpload`)은 `productTypeId = null`인 줄만 다시 본다(`app/actions/purchase-order-assign.ts:201-203`). 그래서 기본 포장지를 고쳐도 이미 붙은 줄은 따라오지 않았다.

## 사용자 결정 (2026-10-01)

| 항목 | 결정 |
|---|---|
| 수정 범위 | 머리글을 눌러 **그 열(규격) 또는 묶음(포장지) 전체**를 바꾼다. 칸 하나 단위는 하지 않는다 |
| 고를 값 | **등록된 활성 SKU에 있는 값만** 버튼으로 고른다. 직접 입력은 없다 |
| 재매칭 | **이미 붙었지만 차감 안 된 줄**도 다시 본다 |

## 9/16 「수동지정 철회」와의 관계

9/16에 철회한 건 **매칭실패 줄에 SKU를 손으로 붙이는** 기능이었다. 철회 이유는 「입구가 둘이면 별칭이 중구난방이 된다」와 「실패의 절반은 SKU 카탈로그 빈칸이라 지정으로 안 풀린다」였다.

이번 건은 다르다.
- **고치는 대상**: SKU가 아니라 엑셀에서 읽은 **원본 값**(`packageType`, `rawPackaging`)을 고친다. 바꾼 뒤 매처가 SKU를 정한다. 그래서 SKU를 정하는 경로는 여전히 매처 하나다.
- **대상 줄**: 이미 매칭된 열만 다룬다. 매칭실패 열은 지금처럼 안내 팝업 → 마스터 보완 → 재매칭으로 푼다.
- **별칭**: 학습하지 않는다.

## 변경 ① 재매칭 확장

`rematchUpload`의 대상을 **「차감이 하나도 없는 줄」 전부**로 넓힌다(매칭 여부와 상관없이).

| 줄 상태 | 매처 결과 | 처리 |
|---|---|---|
| 매칭실패 | 붙음 | 그 SKU로(지금과 같다) |
| 매칭됨 | 다른 SKU | **새 SKU로 옮긴다** (기본 포장지·별칭 수정이 반영됨) |
| 매칭됨 | 같은 SKU | 그대로 |
| 매칭됨 | 실패 (예: SKU 비활성화) | **그대로 둔다**. 매칭 상태를 해제하지 않고, 결과에 「확인 필요 N줄」로 센다 |
| 차감 있음 | — | 건드리지 않는다. 결과에 「차감돼서 그대로 둔 줄 N」으로 센다 |

- 판정은 순수 함수 `planRematch()`(`lib/`)로 빼고 테스트한다. 위 표 그대로를 테스트 케이스로 쓴다.
- 쓰기는 지금처럼 SKU별 `updateMany`로 한다. 조건에 「그 사이에 차감이 생기지 않았는지」(`movements: { none: {} }`)를 넣어 경합을 막는다.
- 화면 토스트: `재매칭: 새로 붙음 N · 옮김 M` + (있으면) `차감돼서 그대로 K` · `확인 필요 J`
- 클라이언트 반영은 기존 `applyMatchPatches`로 한다. 이전 SKU와 상관없이 `productTypeId`를 덮어쓰기 때문에 열 이동이 그대로 처리된다.

## 변경 ② 매트릭스 머리글 수정 팝업 (PC)

- **2행 포장지 칸 클릭** → 「포장지 바꾸기」 팝업. 대상은 그 묶음(품종·도정·포장지)에 속한 **모든 규격 열의 모든 줄**이다.
  - 선택지: 같은 품종·도정의 활성 SKU에 있는 포장지들이다.
  - 그 묶음의 규격 중 하나라도 해당 포장지 SKU가 없으면 버튼을 비활성으로 두고 「5kg 없음」처럼 이유를 적는다. 이때 제품유형 관리 링크를 같이 보여준다.
- **3행 규격 칸 클릭** → 「규격 바꾸기」 팝업. 대상은 그 열의 모든 줄이다.
  - 선택지: 같은 품종·도정·포장지의 활성 SKU에 있는 규격들이다.
  - 경고 문구: 「주문 개수는 그대로예요(10kg 2개 → 20kg 2개)」
- **팝업에 보여줄 것**: 지금 값, 바뀌는 범위(N수령인 · M줄 · 합계 개수)
- **막는 경우**:
  - 범위 안에 **차감된 줄이 하나라도 있으면** 수정 버튼을 막는다. 「차감 N줄 — 먼저 차감을 취소하세요」라고 안내한다(일부만 바뀌면 같은 엑셀 열이 둘로 갈린다).
  - **톤백 열**(자루중량 축)은 이번 범위에서 뺀다. 머리글을 눌러도 아무 일도 없다.
  - **매칭실패 열**도 클릭 대상이 아니다(기존 안내 팝업 유지).
  - **읽기 전용**(권한 없음, §60)이면 클릭이 안 된다.
- **서버**: `editColumnRaw({ itemIds, field: 'packaging' | 'packageType', value })`
  1. 권한 `OPERATION_MANAGE`
  2. 줄들이 한 묶음/열인지, 차감이 없는지 확인
  3. 원본 값을 바꾼 결과로 매처를 돌린다. 하나라도 실패하거나 줄마다 결과 SKU가 다르면 **거부**한다(아무것도 안 바꿈)
  4. 트랜잭션 안에서 `packageType`/`rawPackaging`와 `productTypeId`를 같이 쓴다. 조건은 `movements: { none: {} }`
  5. 감사로그에 이전 값 → 새 값, 줄 수를 남긴다
  6. `MatchPatch`(+원본 값)를 돌려준다 → 클라이언트 `applyMatchPatches`로 반영
- `MatchPatch`에 선택 필드 `raw?: { packageType: string; rawPackaging: string | null }`를 추가한다. `applyMatchPatches`가 이 값도 반영한다(테스트 추가).
- 수정한 값은 DB에만 남는다. 같은 엑셀을 **다시 올리면 엑셀 값으로 돌아간다**. 팝업에 한 줄로 안내한다.

## 단계

1. `planRematch` + 테스트 → `rematchUpload` 확장 → 토스트
2. `MatchPatch.raw` + 테스트
3. `getColumnEditOptions`·`editColumnRaw`
4. 팝업 + 머리글 클릭
5. 검증: `npm test` · `tsc` · `eslint .` → 🖐 사용자 브라우저 확인
   - 재매칭: SKU 기본 포장지를 바꾼 뒤 재매칭하면 열이 옮겨 가는지
   - 포장지 칸 클릭 → 바꾸기 → 열이 새 묶음으로 가는지 · 차감 있는 묶음은 막히는지
   - 규격 칸 클릭 → 바꾸기
