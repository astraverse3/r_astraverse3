## 1. 작업 목표

**품종 별칭을 화면에서 보고 고칠 수 있게 한다.** 지금은 수동지정의 「학습」으로 쌓이기만 하고
확인도 삭제도 못 한다. 잘못 학습되면 이후 **모든 업로드가 조용히 오매칭**되는데 손쓸 방법이 없다.

`aliases`를 읽는 코드는 매처와 마스터 로더뿐이다. **화면에는 어디에도 안 나온다.**

### 2.2 🔴 권한이 어긋나 있다 — 이번 설계의 핵심

| 사용자 | 권한 |
|---|---|
| 임승원 · 민채 · 이영명 | **`OPERATION_MANAGE`만** |
| 이민화 · 윤상훈 · 정윤미 | 셋 다 |
| 땅끝황토친환경 | `SUPPLY_MANAGE` + NOTICE |
| 문희준 | ADMIN |

- 발주서 수동지정(`assignUnmatchedColumn`)은 **`OPERATION_MANAGE`** → 위 3명이 **별칭을 만들 수 있다**
- 품종 관리 액션(`createVariety`·`updateVariety`)은 **`SUPPLY_MANAGE`** → 그 3명은 **고칠 수 없다**

🔴 **「만들 수는 있는데 되돌릴 수는 없는」 상태다.** 이게 이번 작업이 풀어야 할 진짜 문제다.

### 2.3 화면 구조

- `/admin/varieties` — 목록 `No / 품종명 / 곡종 / 수정`, 다이얼로그 폼은 `name` + `type` 뿐
- **페이지 자체에는 권한 가드가 없다**(`getVarieties`는 `requireSession`). 사이드바 링크도 조건 없이 노출.
  등록·수정·삭제 **버튼만** `canManage`(SUPPLY_MANAGE)로 가린다 → **별칭만 다른 권한으로 여는 게 가능하다**
- `VarietyFormData = { name, type }` · 액션은 `app/actions/admin.ts`

## 3. 설계 결정

### 결정 U — 자리는 품종 관리 화면

별칭은 **품종 속성**이다(`Variety.aliases`). 서농22호의 「가바」는 그 품종의 SKU 14개 전체에 적용된다.
제품유형 쪽에 두면 같은 품종 14줄에 같은 칸이 생겨 어디에 넣을지 모호하고, 서로 다른 값이 들어가면
화면과 실제 저장이 어긋난다. (사용자가 「SKU 항목에서」를 제안했으나 이 이유로 품종 쪽으로 정함)

### 결정 V — 🔴 별칭 편집 권한은 `OPERATION_MANAGE` (품종의 다른 항목과 다르게)

§2.2 그대로다. **학습이 이미 `OPERATION_MANAGE`로 열려 있으므로 보기·지우기도 같아야 앞뒤가 맞는다.**
별칭은 품종의 본질 속성이 아니라 **「발주서 품목명을 어떻게 읽을지」의 규칙**이고, 그건 발주서를 다루는
사람의 일이다. 품종명·곡종은 그대로 `SUPPLY_MANAGE`.

- 신규 액션 `updateVarietyAliases(id, aliases)` — `OPERATION_MANAGE`
- `VarietyFormData`에는 **넣지 않는다**(넣으면 `SUPPLY_MANAGE` 액션에 섞여 권한이 뒤엉킨다)
- 화면: 별칭 칸은 `OPERATION_MANAGE`일 때 편집, 아니면 **읽기 전용으로 보이기만**

### 결정 W — 입력은 칩(태그) 방식

쉼표 한 줄보다 낫다 — 개별 삭제가 명확하고, 거절 사유를 **그 별칭에** 붙여 보여줄 수 있다.
학습으로 계속 쌓이는 값이라 나중엔 여러 개가 된다.

- 기존 별칭은 칩 + `×`, 아래에 입력칸 + [추가]
- 추가할 때 즉시 검증 → 통과하면 칩으로, 아니면 입력칸 아래 빨간 사유
- [저장]에서 한 번에 `updateVarietyAliases` (칩 목록 전체를 보낸다)

### 결정 X — 🔴 검증은 순수 lib 하나로, 학습과 화면이 **같은 규칙**을 쓴다

지금 가드는 `learnVarietyAlias` 안에만 있다. 화면을 그냥 열면 **결정 S·T가 화면으로 우회된다.**
판정만 `lib/variety-alias.ts`(순수)로 빼고 양쪽이 부른다.

| 거절 사유 | 근거 |
|---|---|
| 빈 값 | — |
| 그 품종의 이름과 같음 | 별칭이 필요 없다 |
| 같은 품종에 이미 있음 | 중복 |
| **다른 품종의 이름·별칭과 같음** | 결정 S — 매처가 먼저 만난 쪽을 집어 엉뚱한 품종에 붙는다 |
| **도정 단어(백미·현미·오분도미·칠분도미)가 섞임** | 결정 T — 도정이 품종 기본값으로 굳어 조용한 오매칭 |

비교는 매처와 같은 규칙(**공백 무시**)으로 한다. 도정 검사는 `hasMillingToken` 재사용
(위탁가공 별도품종 `발아현미`·`흑미`를 먼저 걷어내는 그 함수 — 안 그러면 `가바발아현미`가 막힌다).

### 결정 Y — 목록에 별칭 열

`No / 품종명 / **별칭** / 곡종 / 수정`. 없으면 빈칸, 여럿이면 칩 나열.
🔴 **한눈에 보이는 게 이번 작업의 절반이다** — 잘못 학습된 별칭을 발견하려면 목록에서 보여야 한다.

### 범위 밖 (백로그)

- **별칭 영향 미리보기** — 이 별칭을 넣으면 지금 매칭실패인 어느 라인이 붙는지. 유용하지만 발주서 조회가 섞여 범위가 커진다
- 매트릭스 팝오버에서 별칭 화면으로 바로 가기 — D2e에서 링크를 뺀 판단과 같이 본다
- 별칭 변경 이력 조회(감사로그에는 남는다)

## 6. 리스크

| 수준 | 내용 | 대응 |
|---|---|---|
| 중 | 별칭을 지우면 **다음 업로드부터 그 품목이 매칭실패**로 돌아간다 | 삭제 시 확인 문구. 되돌리려면 다시 추가하면 되므로 파괴적이지는 않다 |

## 7. 검증

1. `npx tsc --noEmit` · `npm run lint` · `npm test`
2. 기존 별칭 6종이 새 검증을 통과하는지 스크립트로 전수 확인
3. 브라우저(사용자)
   - 품종 목록에 별칭 열이 뜨고 6종이 보이는지
   - 찰보리 열기 → 「보리」 칩 확인 → 새 별칭 추가·삭제 → 저장 → 새로고침 후 유지
   - 거절 확인: 다른 품종 이름(예: 「흑미」) 입력 · 도정 단어 섞인 값(「백미 천지향5세」) 입력
   - `OPERATION_MANAGE`만 가진 계정으로 별칭 편집이 되는지, 품종명 수정은 막히는지
4. 별칭 추가 후 발주서 매트릭스에서 「재매칭」 → 실제로 붙는지

## 8. 확인 필요 (사용자)

① **결정 V 동의 여부** — 별칭 편집만 `OPERATION_MANAGE`로 여는 것. 근거는 §2.2(학습이 이미 그 권한).
   품종 마스터를 발주서 담당이 건드리는 게 불편하면 `SUPPLY_MANAGE`로 통일할 수도 있으나,
   그러면 포장담당 3명은 **자기가 만든 별칭을 못 지운다.**
② 별칭 열을 **목록에 항상** 보일지, 수정 다이얼로그 안에만 둘지. 추천은 목록 표시(결정 Y).
