## 4. 🔴 정규화 — 결함 1건 + 결함인 줄 알았던 1건

### 결함 A — 브랜드 접두를 한 번만 뗀다

```js
// lib/purchase-order-matcher.ts:90  stripBrandPrefix
for (const p of BRAND_PREFIXES) {
  if (name.startsWith(p + ' ')) return name.slice(p.length).trim()  // ← 첫 매칭에 return
}
```

`BRAND_PREFIXES = ['프로틴 라이스', '자스민 라이스', '유기농']`인데
**「유기농 프로틴 라이스 IPS」는 `유기농`만 떨어지고 「프로틴 라이스 IPS」가 통째로 품종토큰**이 된다.
주석의 「긴 것 먼저(부분일치 방지)」는 *중첩* 접두를 고려한 말이 아니다.

- 고침: **더 못 뗄 때까지 반복**(`while` — 접두는 3종뿐이라 비용 무시 가능)
- 효과: 품종토큰 `IPS` → 품종 해석 성공(id=7). 단 **907g SKU가 없어 `sku_unresolved`로 바뀐다** —
  라인이 바로 풀리진 않지만 **사유가 정확해지고** SKU만 등록하면 풀린다
- 🔴 **`자스민 라이스`도 같은 구멍** — 지금 데이터에 없을 뿐이다

### 결함 B — ~~`(친환경)` 접미가 안 떨어진다~~ → **결함이 아니다. 손대지 않는다.**

처음엔 「녹두 (친환경)」이 `variety_unresolved`인데 품종 「녹두」(id=42)가 실제로 있어
**정규화가 괄호를 안 뗀다**고 봤다. 사용자 확인(2026-09-17)으로 뒤집혔다 —

> 🔴 **`품종(친환경)` · `품종(일반)`은 매입 잡곡의 명칭 체계다.** 괄호는 꾸밈말이 아니라
> **품종명의 일부**다. 「율무」와 「율무(친환경)」이 별개 품종으로 둘 다 있고 SKU가 친환경
> 쪽에만 붙어 있던 것이 그 증거였다.

따라서 **정규화에서 괄호를 떼면 안 된다** — 떼는 순간 「율무 (친환경)」이 율무(id=41)로 붙어
**율무(친환경)(id=52)의 SKU를 못 쓴다.** 조용히 다른 품종의 재고를 차감하게 된다.

**코드 수정 없이 품종 등록만으로 풀린다.** 매처가 `stripSpaces`로 공백을 전부 지우고 비교하기
때문이다(`resolveVariety`) — 엑셀의 `녹두 (친환경)`은 `녹두(친환경)`으로 정규화돼 품종명과 붙는다.

```
varietyToken 「녹두 (친환경)」 → stripSpaces → 「녹두(친환경)」
품종명       「녹두(친환경)」   → stripSpaces → 「녹두(친환경)」   ✅
```

🔴 **실증**: D4-1 시험 차감 정리 때 「율무 (친환경)」 1kg 2개가 **이미 정상 매칭돼 차감까지 돼 있었다**
(#18 서울급식). 괄호를 뗐다면 율무(id=41, SKU 0개)로 붙어 **잘 되던 것이 깨졌을 것**이다.

📌 **이 판단을 코드에 남긴다** — `BRAND_PREFIXES` 근처에 「괄호 접미는 품종명의 일부이므로
제거하지 않는다」를 주석으로 박는다. 안 그러면 다음에 또 「떼면 되잖아」가 나온다.

## 6. 결정 기록

### 결정 ㉮ — `(친환경)` 접미 → **B안 확정(품종 등록), 코드 수정 없음** (사용자 2026-09-17)

🔴 **`품종(친환경)`·`품종(일반)`은 매입 잡곡의 명칭 체계**다. 괄호는 품종명의 일부이므로
정규화가 건드리면 안 된다(§4 결함 B). 「녹두(친환경)」을 품종으로 등록하면 코드 수정 없이 붙는다.
### 결정 ㉯ — 「혼합곡」은 ㉮와 같은 건이었다 · 「누룽지」는 **품종 등록**(사용자 2026-09-17)

- **「혼합곡 (친환경)」** — 원본이 `(친환경)` 형태이므로 **㉮와 같은 매입 잡곡 명칭**이다.
  따로 고민할 항목이 아니었다 → **품종 등록**.
- **「누룽지」**(2라인 20개, #15 택배) — 괄호가 없다. **우리 공장 부산물을 제조업체에 주고
  완제품으로 받아와 파는 가공품**이다.
  - **품종으로 등록한다.** 선례가 있다 — 발아현미(id=47)·흑미가 「품종이 아닌데 품종으로
    등록된」 위탁가공 별도품종이고(결정 #24), 매처에도 `NON_MILLING_TAILS`로 박혀 있다.
    `SourceType.GERMINATION`(도정한 현미를 발아업체에 위탁 → 발아현미로 입고)이 **구조가 같다.**
  - `type = PURCHASED` → `category = MISC_GRAIN` 파생 → **잡곡 탭에 얹힌다.**
  - 🔴 **정확한 분류는 「가공품」 탭이지만 지금 만들지 않는다** — 가공품이 누룽지 한 종뿐이라
    `StockCategory` enum 확장 + 패널 신설 + 분기 전수 점검을 할 값이 아니다(사용자 판단).
    **미뤄도 비용이 안 늘어난다** — 나중에 품종 type 한 칼럼만 바꾸면 제품재고가 통째로
    새 탭으로 간다(§42 흑미 사고가 그 메커니즘을 이미 보여줬다. 거기선 사고, 여기선 의도).
    지금 치르는 값은 **잡곡 목록에 누룽지 한 줄이 섞이는 것**뿐. → **백로그 §44**
  - ⚠️ **부산물이 얼마나 나갔는지는 여전히 모른다** — 발아위탁은 `Stock.rawWeightKg`로 원물을
    남기는데 누룽지는 제품재고로 바로 들어와 그 연결이 없다. D4 범위 밖(백로그 §44).
