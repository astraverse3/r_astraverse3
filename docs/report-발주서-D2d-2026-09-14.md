## 주요 결정 (계획서 그대로 + 구현에서 정한 것)

- **F 완료 판정은 자루 개수 그대로, 초과 차단만 푼다.** 985kg 자루를 통째 낸 셀이 영원히 「부분」이 되는 걸 피한다. `guard:'open'`은 서버가 라인의 `unitWeightKg`로만 켠다 — 클라이언트 `bulk` 플래그를 믿지 않는다.
- **G 넘치는 자루는 마지막 라인에.** 2자루/라인1 → 라인1에 2 · 2자루/라인2 → 1씩 · 3자루(한 행)/라인2 → 1+2(같은 packageId는 한 건으로 합쳐 `applyAllocations` 왕복을 아낀다).
- **H 쪼개기 = `createRepack` 그대로.** `results` 둘 다 `packageType:'톤백'`·`packagingId:null` → 서버가 톤백 포장지를 강제하고 같은 SKU로 돌아온다. `confirmDialog`로 「되돌리기 없음」을 먼저 알린다. 결과 행 id가 안 돌아와서 **재조회 후 「그 중량·`repackId` 최신」으로 찾아 자동 체크** — 못 찾으면 체크 없이 목록만 갱신.
- **후보 정렬 기준 = 남은 요구 kg**(요구 − 기차감). 이미 넘겼으면 0 근처(작은 자루 우선).
- **차이 표시 임계 ±1%**(§40 예시). 색만 바꾼다. 587+450 두 자루(+37, +3.7%)도 확정된다.
- 팝오버 껍데기(Popover·Head)는 D2c 것을 그대로 쓴다. `tonbag-popover.tsx` ↔ `cell-allocation-popover.tsx`가 서로 import(TonbagBody / CancelButton·ActiveCell)한다 — 함수 선언이라 ES 모듈 순환에 문제없지만, 다음 팝오버(D2e)가 붙을 때 공용 조각을 `cell-popover-parts.tsx`로 빼는 게 낫다.

## 🔴 구현 후 정정 — 근접순 → kg FIFO (`2efc798`)

사용자 지적: **쪼개기가 있는 이상 「근접순」은 의미가 없다.** 어느 자루를 고르든 딱 안 맞으면 쪼개고 나머지는 남으니 정렬이 결과를 바꾸지 않는다.
근접순은 「1,005를 통째로 보내는 게 기본」(#34·§40)이라는 전제를 따른 건데, 그 전제와 쪼개기 기능이 서로 어긋나 있었다.
→ **「원칙대로 오래된 것부터, 자루가 여러 개 쓰여도」**로 확정.

- `lib/purchase-order-bulk.ts` — `sortBulkCandidates` 삭제, **`suggestBulkAllocation(requiredKg, bagsFIFO)`** 신설(통째 자루 목록 + 쪼갤 자루 하나 + 부족 kg). 테스트 7건(실데이터 pt18: 587+332+81 · 딱 맞음 · 첫 자루가 큼 · count>1 · 부족 · 요구 0 · 가용 0)
- `getBulkCellOptions` — 후보를 `sortFifo`로. 근접 기준(`targetKg`) 제거
- `tonbag-popover.tsx` — 추천이 **기본 체크**로 뜬다. 쪼갤 몫은 그 자루 행 아래 「확정 때 81kg만 쪼개 씀 · 369kg 남김」 체크로 보이고, 끄면 그 자루는 안 쓴다(통째로 쓰려면 위 체크).
  **확정 한 번**: 쪼갤 몫 켜짐 → confirm → `createRepack` → 재조회로 새 자루 찾기 → `confirmCell`. 가위(수동 즉시 쪼개기)는 남기고, 나눈 뒤 추천을 새로 낸다
- 확인 항목 1·3·4가 바뀐다 — 아래 표 참조

| 확인 | 정정 후 |
|---|---|
| 1 | 가바백미 1,000kg 셀 → **587·332 체크 + 450 행에 「81kg만 쪼개 씀」**이 기본으로 떠 있는지 → 확정 → confirm → 3자루 1,000kg 차감 · `/packages`에 369kg 톤백 생김 |
| 3 | (자동 쪼개기가 1번에 포함) 가위로 수동 나누기도 되는지 |
| 4 | 추천을 지우고 587+450 통째 체크 → 확정이 막히지 않고 +37(+3.7%) 주황 |
| 2 | 200kg 셀 → 587 행에 「200kg만 쪼개 씀 · 387 남김」이 기본(FIFO라 203이 아니라 587이 먼저) |
