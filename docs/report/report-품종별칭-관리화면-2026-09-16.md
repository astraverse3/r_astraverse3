## 1. 변경 사항 요약

별칭이 **쌓이기만 하고 볼 수도 고칠 수도 없던** 상태를 끝냈다. 품종 관리 화면에서 보이고,
`SUPPLY_MANAGE` 보유자가 칩으로 추가·삭제한다.

| 파일 | 변경 |
|---|---|
| `lib/variety-alias.ts` | **신규** — `normalizeAlias` · `validateAlias` · `validateAliasList` |
| `lib/variety-alias.test.ts` | **신규** — 11건 |
| `lib/purchase-order-matcher.ts` | `stripSpaces` export (비교 규칙 단일 원천) |
| `app/actions/admin.ts` | `updateVariety`가 별칭을 함께 저장 + 전수 재검증 + 감사로그 |
| `.../varieties/alias-editor.tsx` | **신규** — 칩 편집기 (결정 W) |
| `.../varieties/variety-dialog.tsx` | 별칭 편집기 삽입 · 열 때 상태 리셋 · `flex flex-col` |
| `.../varieties/variety-list-client.tsx` | 별칭 열 + 모바일 카드 (결정 Y) |
| `.../varieties/page.tsx` · `variety-page-wrapper.tsx` | `aliases` 타입 전달 |

`variety-page-client.tsx`는 별칭을 안 만지므로 손대지 않았다(계획서 예상 8개 중 1개 감소,
대신 `purchase-order-matcher.ts` 1개 추가 → 실제 9개).

## 2. 주요 결정 사항

### 🔴 별도 액션을 만들지 않고 `updateVariety`에 합쳤다 (계획서 A2가 열어 둔 판단)

계획서는 `updateVarietyAliases(id, aliases)` 신규를 적었지만, **「`VarietyFormData`에 넣을지는
A2에서 판단」**이라고 열어 두었다. 합치는 쪽을 골랐다.

- 저장 버튼은 **하나**다. 액션이 둘이면 앞은 성공 뒤는 실패인 **부분 저장**이 생긴다
- 결정 V′로 권한이 `SUPPLY_MANAGE` 하나가 됐으므로 나눌 이유가 사라졌다(계획서도 「섞어도
  뒤엉키지 않는다」고 명시)
- `updateVariety` 호출부는 `variety-dialog.tsx` 하나뿐이라 파급이 없다
- `aliases`는 **선택 필드**다. 미전달(등록 모드·다른 호출부)이면 기존 값을 건드리지 않는다

### 읽기 전용 표시는 목록 열이 담당한다

결정 V′는 「`SUPPLY_MANAGE`가 아니면 별칭 칸을 읽기 전용으로 보이기만」이라고 했다.
그런데 **수정(연필) 버튼 자체가 이미 `canManage`일 때만 뜬다** — 다이얼로그는 권한자만 연다.
따라서 읽기 전용 경로는 **목록의 별칭 열**(결정 Y, 권한 무관하게 모두에게 보임)이 충족한다.
`AliasEditor`에 `readOnly`를 만들지 않았다.

### 🔴 다이얼로그를 열 때 상태를 현재 값으로 되돌린다 (계획서에 없던 추가)

`useState` 초기값은 **최초 마운트 때만** 먹는다. 저장 후 `router.refresh()`로 목록이 갱신돼도
다이얼로그 컴포넌트는 재사용되므로 상태가 낡은 채 남는다. 기존 `name`·`type`에도 있던 문제인데,
별칭은 **배열을 통째로 덮어쓰므로** 낡은 목록으로 저장하면 그 사이 추가된 별칭이 조용히 사라진다.
([[incident_packaging_loss_2026_09_01]]과 같은 구조 — 「동시 편집」이 아니라 **「낡은 화면」**)

### 그 밖

- **`stripSpaces`를 export**했다. 검증이 「매처와 같은 규칙」이어야 하는데(결정 X), 따로 구현하면
  공백만 다른 값이 화면엔 두 칩인데 매처엔 같은 값이 된다
- **`flex flex-col max-h-[88vh]`** — 별칭 편집기가 붙어 다이얼로그가 길어졌다. 기본 `grid`는
  푸터가 잘린다(계획서 A3 경고)
- **모바일은 별칭을 품종명 아래 줄**에 둔다. 옆에 붙이면 이름이 밀려 잘린다
  ([[mobile_card_font_no_increase]] — 가독성은 폰트가 아니라 배치로)
- **삭제 확인은 문구로**(리스크 §6). 칩마다 `confirm`이 뜨면 번거롭고, 저장 전이라 되돌리기 쉽다.
  하나라도 지워지면 「다음 업로드부터 매칭실패로 돌아갑니다」 경고가 편집기 아래에 뜬다

## 4. 확인이 필요한 사항 (사용자 브라우저 — 계획서 §7)

1. `/admin/varieties` 목록에 **별칭 열**이 뜨고 6종이 보이는지 (모바일 카드도)
2. 찰보리 열기 → 「보리」 칩 확인 → 새 별칭 추가·삭제 → 저장 → **새로고침 후 유지**
3. 거절 확인
   - 다른 품종 이름 입력 (예: 서농22호에 「흑미」) → 「「흑미」이(가) 이미 쓰는 이름입니다.」
   - 도정 단어 (예: 「백미 천지향5세」) → 「백미·현미 같은 도정 단어는 별칭에 넣을 수 없습니다.」
4. `OPERATION_MANAGE`만 가진 계정(임승원·민채·이영명)에서 **별칭 열은 보이되 수정 버튼은 없는지**
5. 🔴 **별칭 추가 → 발주서 매트릭스에서 「재매칭」 → 실제로 붙는지**
   — 이 경로가 이제 매칭실패를 푸는 **유일한 길**이다

## 5. 브라우저 확인 중 나온 후속 (사용자 확인 완료)

§4 확인은 전부 통과. 확인 과정에서 사용자가 던진 두 질문이 결함 4건을 드러냈다.

### 5.1 곡종 라디오가 2줄로 넘치고 유독 커 보였다 (`883cd43`)

`<span>메벼</span>`에 **크기 지정이 아예 없어** body 기본 16px를 상속하고 있었다. 같은
다이얼로그의 Label·Input은 `text-sm`(14px), 다른 화면 라디오는 12.5px. 거기만 16px이라
커 보였고 7개가 한 줄에 안 들어갔다. → `text-sm` + 간격 축소(`gap-x-4`→`3`, `space-x-2`→`gap-1.5`).

### 5.2 🔴 삭제 가드가 제품유형(SKU)을 안 세고 있었다 (`883cd43`)

**사용자 질문: 「품종이 삭제되면 어떻게 돼? 제약이 없지?」**

`ProductType.varietyId`는 2026-06-17 제품유형 마스터가 들인 **세 번째 참조자**인데,
`checkVarietyReferences`는 Stock·MillingOutputPackage 둘만 셌다(주석도 「두 모델에 의해
참조됨」인 채였다). FK가 `Restrict`라 데이터는 안 깨졌지만, **가드를 통과한 뒤 delete에서
터져 「품종 삭제에 실패했어요」만 뜨고 이유를 알 수 없었다.**

실측: **검정보리·칼슘찹쌀** 2종이 재고 0 / SKU 1개 — 정확히 이 구멍에 빠져 있었다.

📌 **교훈: 참조자가 늘면 가드도 같이 늘어야 한다.** 마스터를 새로 만들 때 기존 삭제 가드를
훑는 절차가 없었다.

### 5.3 별칭이 품종과 함께 조용히 사라졌다 (`883cd43`)

별칭은 품종 행에 얹혀 있어서 품종을 지우면 같이 없어진다. 확인 문구가 「정말 삭제하시겠습니까?」
뿐이라, 그 이름으로 오던 발주서 품목이 다음 업로드부터 매칭실패로 돌아가는 게 안 보였다.
→ 단건·일괄 삭제 모두 별칭을 나열해 경고. 일괄 문구도 「재고/포장」→「재고 · 포장 · 제품유형」.

### 5.4 🔴 이름이 다른 품종의 별칭을 가로채는 걸 아무도 안 막았다 (`2ca3ed6`)

**사용자 질문: 「품종명을 수정할 때는 제약이 맞게 되어 있나?」**

매처 `resolveVariety`는 **name 정확일치를 먼저** 보고 실패해야 aliases를 본다. 그래서 아무
품종 이름을 「보리」로 바꾸는 순간 찰보리의 별칭 「보리」가 죽는다 — **`efdbeb7`에서 겪은
그 일을 개명으로 다시 만들 수 있었다.** A1에서 만든 `validateAlias`는 「별칭 → 다른 품종의
이름·별칭」 **한 방향만** 막고 있었다.

→ `validateVarietyName` 신규(같은 파일 — 이름과 별칭은 **같은 네임스페이스를 공유**한다).
거절 4종: 빈 값 · 다른 품종 이름 · **다른 품종이 별칭으로 쓰는 이름** · **자기 자신의 별칭**.

**공백만 다른 이름도 막는다** — DB의 `name unique`는 「서농 22호」와 「서농22호」를 다른 값으로
보지만 **매처는 같은 값으로 본다**(`stripSpaces`). 실측으로 기존 41종에 그런 쌍이 0건이라 회귀 없음.

⚠️ `updateVariety`는 이름·별칭 검증이 **서로를 본다**(이름은 「자기 별칭과 겹치나」, 별칭은
「품종명과 같나」). 순환을 끊으려고 **이번에 저장될 별칭을 먼저 깔고 이름부터 정한다.** 조회도 1회.

### 5.5 ⚠️ 로트 품목코드가 품종명 문자열로 정해진다 (`2ca3ed6`)

`getProductCode`가 `varietyName.includes(...)`로 코드를 고른다. 「검정보리」→「블랙보리」면
`215`가 `21`로 **조용히** 바뀐다. 실측 **41종 중 18종이 이름에 의존**.

막을 일은 아니라(정당한 개명일 수 있다) 저장 전에 「백미 215 → 21」을 보여 주고 확인만 받는다.
곡종도 코드를 가르므로 **이름+곡종 전후를 같이** 비교한다. 이미 만들어진 로트는 문자열로
저장돼 있어 그대로.

⚠️ 브라우저 확인 때 「검정보리쌀」로 바꾸니 경고가 안 떴는데 **정상**이다 — '검정'과 '보리'를
둘 다 품고 있어 코드가 `215` 그대로다. 경고가 뜨는 건 '검정'이나 '보리'가 빠지는 이름.
