## 1. 원인 재특정 — 「동시 편집」이 아니라 「낡은 화면」

9/1에는 후보 A를 *"둘이 같은 시간에 다이얼로그를 열어뒀을 때"* 로 좁혔다. **그 전제가 틀렸다.**

사람 확인(2026-09-02)으로 좁혀진 사실:

| 질문 | 답 | 영향 |
|---|---|---|
| 동시에 열어뒀나 | **아니오** | A의 「동시」 전제가 깨짐 |
| 14:30 저장 때 에러가 떴나 | **안 떴다.** 정상 입력했는데 나중에 없었다 | C(유효성 차단)·D(롤백)는 「사라짐」의 원인이 아님 |

코드를 보니 포장 다이얼로그는 **열릴 때 서버를 다시 읽지 않았다.**
`page.tsx`가 페이지 로드 때 한 번 읽은 스냅샷(`initialOutputs`)만 봤고, 갱신은 `router.refresh()` 뿐.
→ **탭 하나만 오래 켜두면 화면이 낡는다. 두 사람이 동시에 열어둘 필요가 없다.**

그리고 낡은 화면으로 저장하면 `diffPackaging`이 그것을 **의도된 삭제로 읽는다** — 코드 주석에 이미
그렇게 적혀 있었다(`// 입력에서 빠진 행 = 삭제`). 「화면에 없던 행」과 「사용자가 지운 행」을
서버가 구분할 방법이 없었다.

### 재구성된 시간선

| 시각 | 추정 |
|---|---|
| 14:30 | 이영명 톤백 저장 **성공**. `#1365`가 실제로 존재 → **에러가 안 뜬 것이 설명된다** |
| ~16:00 | 화면이 낡은 스냅샷이라 `#1365`가 안 보임 → "입력한 게 없다" |
| 16:02:15 | 민채 4kg×267 저장 → payload에 `#1365`가 없으니 **diff가 조용히 삭제** + `#1366` 생성 |

결번 `1365`가 「롤백된 INSERT」가 아니라 **「커밋된 뒤 낡은 화면이 지운 행」**으로 설명된다.

**확정은 아니다** — `#1365`가 커밋됐었는지는 감사로그가 없어 증명할 수 없다. 다만 물증·증언과
모순되지 않는 유일한 가설이고, 이번 수정은 이 경로를 실제로 막는다.
**16:00 저장 실패는 여전히 미해결**(에러 문구를 못 들음). 앞으로는 P1 감사로그가 잡는다.

## 2. 구현 — P1~P5 + 실사용 중 발견 1건

### P1. `updatePackagingLogs` 감사로그 (추적 불가 문제의 뿌리)

[app/actions/milling.ts](../../app/actions/milling.ts)

- 커밋 후 트랜잭션 **밖**에서 `recordAuditLog` 1건
- 🔴 **삭제 행은 되살릴 수 있을 만큼 통째로** — 규격·단중·개수·총중량·stockId에 더해
  `lotNo`·`productCode`·`productTypeId`까지. 조회 select에 이 3개를 일부러 추가했다
- 스냅샷은 **삭제를 실행하기 전에** 뜬다(`buildPackagingAudit`) — 지운 뒤엔 근거가 없다
- `수정`은 before/after를 같이 남긴다
- **차단된 저장도 남긴다** — 「저장이 반복 실패했다」를 다음엔 로그로 확인한다
- 변경 0건도 남긴다 — 「저장했는데 아무것도 안 바뀌었다」 자체가 추적에 필요한 사실이다

### P2. 서버 `isClosed` 검증

다른 액션들은 이미 막고 있었는데(`:65`·`:340`·`:857`) 여기만 없었다.
결번 `1368`은 마감(16:02:56) **이후**에 발급됐다 — 마감된 배치에 저장이 들어갔다는 뜻이다.
throw가 아니라 이유를 돌려준다(결정 #63과 같은 결).

### P3. 다이얼로그 열 때 서버 재조회 🔴 근본

- 새 액션 `getBatchOutputs(batchId)` — **select·필터·정렬을 `getMillingLogs`의 `outputs`와 일치**시켰다
  (어긋나면 화면에 없는 행을 지우게 된다 — 결정 #61이 경고한 그것)
- 다이얼로그는 열릴 때 이걸 호출해 최신으로 교체. `initialOutputs`는 깜빡임 방지용 첫 표시로만 남았다
- 🔴 **조회 실패를 조용히 넘기지 않는다** — 토스트 + **쓰기 버튼 3개 전부 비활성**.
  (기존 `listPackagings`가 `if (!res.success) return`으로 조용히 넘어가던 것과 같은 실수를 반복하지 않는다)
- ⚠️ deps에서 `initialOutputs`를 뺐다 — 열려 있는 동안 prop이 갱신되면 **입력 중인 값을 덮어써서**
  그게 또 「입력 날림」이 된다

### P4. baseline 충돌 감지 (사용자 결정 B안)

- `lib/packaging-diff.ts`에 `STALE_BASELINE` + `mergeUnseenRows` (둘 다 순수 함수 · 단위테스트)
- 액션 시그니처 `updatePackagingLogs(batchId, outputs, baselineIds)` — 🔴 **선택 인자로 두지 않았다.**
  `undefined`면 옛 동작으로 빠져 구멍이 남는다. 호출처 3곳 모두 갱신
- 충돌이면 **서버 최신 행을 응답에 실어 보낸다**(`conflict`) — 화면이 병합할 수 있어야 한다
- 🔴 **거부가 입력 날림이 되지 않는다**: 내 입력은 값도 순서도 그대로, 남의 줄만 뒤에 붙이고,
  baseline을 갱신해 **다시 저장을 누르면 통과**한다. 거부는 한 번뿐인 확인 단계다

**UI = 배너 + 자동 병합 + amber 강조** (확인 모달·토스트는 기각):
모달은 무엇이 들어왔는지 가리고, 토스트는 현장에서 놓친다. 안 사라지는 배너 + 합쳐진 줄 강조.

### P5. `count = 0` 줄을 조용히 버리지 않는다

- 기존 행(`id` 있음)이 `count=0` → **저장 중단** + "…줄의 개수를 입력해 주세요. 지우려면 휴지통을 눌러 주세요."
- 새 줄이 `count=0` → 버리되 "개수가 없는 N줄은 저장하지 않았습니다."

### 🔴 실사용 중 발견 — 마지막 한 줄을 지울 수 없었다

테스트 중 사용자가 발견. **기존부터 있던 결함이고 이번 변경과 무관**하지만, P5가 넣은
「지우려면 휴지통을 눌러 주세요」 안내와 정면으로 모순돼 함께 고쳤다.

| 버튼 | 전 | 후 |
|---|---|---|
| 기록 저장 | 화면이 비면 무조건 비활성 | **화면에도 서버에도** 없을 때만 비활성 |
| 포장 초기화 | 화면(`outputs`) 기준 | **서버(`serverOutputs`) 기준** — 지울 대상은 DB에 있다 |

화면을 다 비우고 저장하면 "포장 기록을 모두 지웁니다. 계속할까요?" 확인 한 번으로 진행된다.
실수로 전부 날리는 것은 그 확인이 막고, 의도적으로 지우는 길은 열렸다.

### 덤 — 마감 판정 기준 교정

`handleCloseBatch`의 "변경됐나?" 비교 대상을 낡은 prop이 아니라 **서버에서 마지막으로 받은 값**
(`serverOutputs`)으로 바꿨다. 안 그러면 P3 재조회로 화면이 갱신된 것만으로 「변경됨」이 돼
마감할 때마다 불필요한 저장이 한 번 더 돈다.

## 5. 확인이 필요한 것 / 남은 것

1. **삭제 스냅샷 상세 확인** — 활동로그 목록의 문서 아이콘을 눌러 `details.deleted`에 지워진 행의
   규격·개수·`lotNo`가 실제로 들어있는지 한 번 봐 두면 좋다. 복구 가능성이 P1의 핵심이다
2. ~~`add-packaging-dialog.tsx`가 861줄~~ → **분리 완료** (§6)
3. **배너에 작성자 이름을 못 넣었다** — `MillingOutputPackage`에 작성자 필드가 없다.
   대신 "톤백 × 1이(가) 새로 추가되었습니다"처럼 규격·수량으로 표시하고 그 줄을 강조한다.
   이름이 필요하면 스키마에 `createdBy` 추가가 선행이다
4. **16:00 저장 실패의 정체는 미해결** — 다음에 재발하면 P1 감사로그의 「차단」 기록으로 잡는다
5. **P4가 못 잡는 것** — 같은 행을 둘이 동시에 고치면 baseline에 id가 있어 통과되고
   나중에 저장한 쪽이 이긴다(last-write-wins). 행 소실보다 위험도가 낮아 범위 밖으로 뒀다
6. **적용 범위는 포장 다이얼로그 하나** — `app/actions/` 전체 `deleteMany` 전수 조사 결과
   「목록 통째 대체」 패턴은 여기뿐이다 (계획서 §7에 근거 보존)
7. **탭 복귀 시 재조회**(`visibilitychange`)는 선택 항목으로 남겼다. 타임아웃 방식은 기각
   (거짓 양성이 곧 「입력 날림」이라 9/1 사고를 시스템화한다)
