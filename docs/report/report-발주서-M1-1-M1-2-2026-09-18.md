## 2. 방향 전환 — 3모드 매트릭스 폐기

세션 초반에 쓴 1차 M1 계획서(3모드 매트릭스: 카드/전치/표준)는 **같은 날 폐기**됐다.
근거는 디자이너의 밀도 실측이다.

| 시트 | 건 | 규격 | 주문 밀도 |
|---|---|---|---|
| 택배 | 67 | 25 | **5.6%** |
| 이마트 | 3 | 4 | 75% |
| 서울급식 | 3 | 17 | 47% |
| 시아스 | 1 | 4 | 100% |

매트릭스의 가치는 **건끼리 나란히 보는 것**인데 실데이터엔 그 중간이 없다 —
택배는 67건이지만 규격이 안 겹쳐 94.4%가 빈 칸이고, 나머지는 밀도가 높아도 건이 1~3개라
나란히 볼 상대가 없다. **3모드 판정 자체가 불필요**해졌다.

📌 폐기 비용은 0이었다 — 계획서만 쓰이고 **코드는 한 줄도 없었다**.
(지시서 1차판은 `mobile-matrix.tsx` 삭제를 지시했지만 그런 파일은 존재한 적이 없다.)

## 3. M1-1 — 건상세 데이터 원천을 파생으로 (B안)

### 3.1 문제

`DetailLine`에 **규격 중량이 없었다**(`unitWeightKg` grep 0건). 일반 규격은 문자열에서
뽑을 수 있지만 **톤백은 못 뽑는다** — 자루중량은 규격 문자열이 아니라 라인 필드(#34)다.
푸터 「남은 n kg」을 계산할 근거가 없었다.

곁가지로 `getPurchaseOrderDetail`은 `Promise.all` 안에서 **라인당 쿼리 2회**를 돌았다.
16라인이면 32왕복. 「다음 건 ›」으로 67건을 연속 이동하면 건마다 쌓인다
(이 프로젝트에서 이미 같은 모양으로 터졌다 — 적재 트랜잭션 타임아웃).

### 3.2 한 일

`BuildMatrixInput`에서 파생(B안). `page.tsx:20`이 이미 전 라인을 내리고 있었다.

| 파일 | 내용 |
|---|---|
| `lib/purchase-order-matrix.ts` | `buildOrderLines`·`sumOrderLines` + `OrderLine` (530→666줄) |
| `order-detail-panel.tsx` | 서버 호출 → prop 파생. **`kindOf` 삭제** |
| `matrix-client.tsx` | `detailLines` useMemo 파생 |
| `app/actions/purchase-order.ts` | **106줄 삭제**(`getPurchaseOrderDetail`·`DetailLine`·`OrderDetail`) |

**결과**: 톤백 kg 정확 · 왕복 0 · 차감 즉시 숫자 일치(예전엔 「열 때마다 다시 읽기」로 막던 것).

### 3.3 판정 통합

`kindOf`(패널)와 `cellStatusOf`(매트릭스)는 **같은 판정을 다른 이름으로** 하고 있었다.
B안과 **같은 커밋**에서 흡수 — 두 벌로 굳은 기간이 0이다.

테스트가 이를 고정한다: `buildOrderLines`가 낸 줄 상태와 `buildMatrix` 셀 상태가
한 글자라도 다르면 실패한다.

### 3.4 브라우저 검증 — 톤백 환산이 맞다는 증거

시아스(톤백) 건상세:

| 라인 | 매트릭스 가용(kg) | 패널 가용(자루) | 검산 |
|---|---|---|---|
| 서농22호 1,000kg | 7,780 | 7 | 7.78 → 내림 ✓ |
| 서농22호 200kg | 7,780 | 38 | 38.9 → 내림 ✓ |
| 현미 1,000kg | 1,207 | 1 | 1.207 → 내림 ✓ |
| 현미 200kg | 1,207 | 6 | 6.035 → 내림 ✓ |

같은 SKU라도 자루중량에 따라 가용 개수가 달라진다. **A안이었으면 이 네 줄이 전부 틀렸다.**

## 4. M1-2 — 모바일 건 목록

`sm:hidden` / `hidden sm:contents`로 갈랐다. **데이터·정렬·상태는 매트릭스와 같은 것**
(`matrix`·`rows`·`sortMatrixRows`)을 쓰고 화면 모양만 다르다.

### 4.1 🔴 그룹 축 — 지시서와 달리 갔다

지시서 §3.1은 `o.vendorName`으로 묶으라 했으나 **서울급식이 깨진다**.
`MEAL_SEOUL`은 `constantSide: 'recipient'`라 **vendor가 매 건 다르다**(은평구·서대문구).
그대로 묶으면 그룹 3개 × 1건 = 헤더가 행 수만큼.

→ **`nameTiersOf`의 보조 이름(tail)**으로 묶었다. 채널 선언이 이미 「무엇이 반복되는 축인가」를
알고 있다:

| 채널 | 행 제목 | 그룹 | 결과 |
|---|---|---|---|
| 택배 | 수령인 | 발주처 | 네이버스토어 21건… 그룹 섬 |
| 서울급식 | 발주처 | 수령인(상수) | 그룹 1개 → 헤더 없음 |
| 이마트·해남 | 수령인 | 발주처(상수) | 그룹 1개 → 없음 |
| 기업별 | 단일 | 없음 | 그룹 없음 |

지시서가 **의도한 결과**(§3.1 괄호의 「이마트·급식·시아스는 헤더가 노이즈」)가 전 채널에서 나온다.

### 4.2 그 밖에 달리 간 것

- **「건수 많은 발주처 먼저」는 `sort==='vendor'`일 때만.** 「작업 필요 먼저」를 고른 사용자의
  정렬을 그룹 재배열이 덮어써선 안 된다.
- **상태칩은 `ROW_STATUS_ORDER` 전체.** 시안 ①은 4칩(완료/부분/대기/실패)인데 실데이터
  택배 260818의 주 축은 **재고부족 20건**이었다 — 4칩만 박았으면 어느 칩에도 안 잡힌다.

### 4.3 브라우저 확인에서 나온 결함

🔴 **「작업 필요 61건 검토」 버튼이 아예 안 보였다.**
`sticky bottom-0`은 뷰포트 바닥에 붙는데 거기엔 `MobileNav`가 `fixed z-40`으로 떠 있어
**버튼이 탭바 뒤에 숨었다**.

→ 탭바 위로 올리되 **레이아웃이 본문에 주는 하단 여백과 같은 식**을 쓴다
(`layout.tsx:33`의 `calc(60px+env(safe-area-inset-bottom)+1.5rem)`). 한쪽만 바뀌면 다시 겹친다.

## 5. 곁가지 — 상태 표기표 3벌 → 1벌

판정은 `cellStatusOf` 한 벌인데 **라벨·색이 매트릭스와 패널에 각각** 있었고,

## 6. 지시서 오류 10건 — 공통 원인 하나

1·2차판 9건은 디자이너가 문서에 반영했고(부록 A·B), 3차판에서 1건이 더 나왔다.

| 차수 | 오류 | 정정 |
|---|---|---|
| 1차 | `order-detail-panel.tsx` "손대지 말 것" | 확장이 맞다(8할 완성돼 있었다) |
| 1차 | `mobile-matrix.tsx` 삭제 | 그런 파일이 없다 |
| 1차 | 권한 `SUPPLY_MANAGE` | `OPERATION_MANAGE` |
| 1차 | 경로 `sales/[uploadId]/` | `sales/purchase/[uploadId]/` |
| 1차 | "규격 kg 1,000배 틀어짐" | 파서는 이미 변환한다. 진짜 위험은 **단위 없는 값이 `null`로 빠지는 것** |
| 1차 | 소계 자체 누적 | `buildMatrix().columns`에서 파생 |
| 2차 | `listPurchaseOrders` 추가 | **필요 없다** — `rows`로 전부 충당 |
| 2차 | 검토 게이트 「신규」 | 380줄이 이미 있다(4갈래 구성은 실측의 산물) |
| 2차 | 푸터 kg을 `DetailLine` 기준으로 | 중량 필드가 없다 → B안 |
| **3차** | **그룹 축 `o.vendorName`** | **`nameTiersOf` 보조 이름**(§4.1) |

> 📌 공통 원인: **이미 있는 것**(화면·판정 함수·데이터·채널 선언)을 반복해서 과소평가했다.
> 새로 지으려는 것이 있으면 **그 앞에** 기존 코드를 전수로 본다.
