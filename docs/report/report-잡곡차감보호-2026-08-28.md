## 1. 무엇을 고쳤나

벼는 제품재고에 수정·삭제 UI가 없고, 도정관리 포장 수정은 diff로 막았다.
**잡곡은 `/packages` 잡곡 탭에서 아무 때나 수정·삭제할 수 있었다.**

| 액션 | 작업 전 | 작업 후 |
|---|---|---|
| `deleteMiscPackage` | 재포장 결과만 막음. 차감은 **FK가 "삭제 실패"로만** | 차감·재포장 결과를 **이유와 함께** 차단 |
| `deleteMiscPurchase` | 같음 + **트랜잭션 밖** | 같음 + 트랜잭션 안으로 |
| `updateMiscPackage` | 🔴 **아무 검사 없음** | 재포장 결과·축소·규격 변경 차단 |
| `updateMiscPurchase` | 🔴 **재포장 결과조차 안 봄**. 품종까지 바꿈 | 재포장 결과·축소·품종/규격 변경 차단 + 트랜잭션 |

### 특히 수정이 위험했다

UPDATE는 참조 무결성과 무관해 FK가 개입하지 않는다.

> 10개 중 3개를 팔았는데 `count`를 2로 줄이면 → **가용재고 = 2 − 3 = −1**

그리고 [packages.ts](../../app/actions/packages.ts)의 목록 필터가 `available <= 0`이면 행을 제외하므로,
**깨진 행이 화면에서 사라진다.** 에러 하나 없이 조용히 틀어지는 게 가장 나빴다.

## 3. 결정별 결과

### #66 — 차감 규칙은 한 곳에서만

`lib/package-guard.ts` 신설. `guardDelete` · `guardUpdate` · `guardCountChange` · `guardIdentityChange`
+ 문구 상수. **단건 액션(잡곡)과 배열 diff(벼)가 같은 것을 쓴다.**

`batch-outputs.ts`(#61) 때 지점마다 손으로 붙이다 두 번 놓쳤던 전례를 따르지 않기 위해서다.

**리팩터가 동작을 안 바꿨다는 증거 — 기존 `packaging-diff.test.ts` 33개를 한 줄도 고치지 않고 통과시켰다.**

### #67 — 삭제는 FK가 아니라 규칙으로

FK(`Restrict`)는 **최후 방어선으로 남기고**, 그 앞에서 이유를 적어 막는다.

```
이미 판매·재포장된 포장은 지울 수 없어요.
  · 서리태 5kg × 10 (10개 중 3개 차감됨)
포장을 되돌리려면 판매를 취소하거나 재포장을 정리해 주세요.
```

### #68 — 차감량 밑으로는 축소 불가

벼(#63)와 **같은 규칙·같은 문구**다. 늘리는 것은 자유.

### #69 — 재포장 결과는 수정도 막는다

삭제만 막고 수정은 열려 있던 비일관을 없앴다. 문구는 삭제와 다르다 — 되돌리는 방법이 다르기 때문:

- 삭제: 「재포장으로 만든 재고는 삭제할 수 없어요. 되돌리려면 이 재고를 다시 재포장해 원래 규격으로 합쳐주세요.」
- 수정: 「재포장으로 만든 재고는 수정할 수 없어요. 고치려면 이 재고를 다시 재포장해 주세요.」

### #70 — 차감 뒤 품종·규격 변경 금지 (A안, 사용자 확정)

**품종·규격만** 막는다. 매입처·매입일·수량 증가는 계속 정정할 수 있다 —
오타 하나 못 고치게 만들 이유가 없다.

### #71 — 화면 배지 없음

서버가 이유를 말하는 것으로 충분하다. R3 #57의 판단을 유지했다.

## 4. 계획과 달라진 것

### 🔴 계획서의 「벼도 같은 구멍」은 절반만 맞았다

초안에 「벼(#65)도 규격 변경을 허용하니 같은 구멍」이라고 적었는데, 확인해 보니
**서버는 허용하지만 화면에 그 입력이 없다** — 규격은 버튼으로 새 행을 만들 때만 정해지고,
기존 행의 규격을 바꾸는 함수 자체가 없다.

**대신 진짜 구멍이 다른 데 있었다.** 차감된 벼 16개 배치는 전부 `잔량` 줄인데,
잔량·톤백은 [단중 입력칸이 열려 있다](../../app/\(dashboard\)/milling/add-packaging-dialog.tsx#L637).

| 필드 | 벼 UI | 서버 |
|---|---|---|
| `packageType` | **없음** | 허용 |
| `weightPerUnit` | **톤백·잔량만 있음** 🔴 | 허용 |
| `packagingId` | 있음 🔴 | 허용 |
| `count` | 있음 | ✅ 축소 거부 |

재포장이 3kg를 소진해 간 잔량 행의 중량을 10kg으로 바꿀 수 있다 — 중량 보존이 깨진다.
**백로그 §19**에 기록하고 이 작업 범위 밖으로 뒀다(사용자 확정).

### 트랜잭션 경계를 넓혔다

`deleteMiscPurchase`·`updateMiscPurchase`는 조회가 트랜잭션 밖이었다.
검사와 쓰기 사이에 차감이 끼어들 수 있어 안으로 넣었다. `updateMiscPurchase`는
품종 조회(`findOrCreatePurchaseVariety`)가 쓰기를 동반할 수 있어 트랜잭션 앞에 두고,
**트랜잭션 안에서 행을 다시 읽어** 최신 차감량으로 판정한다.

## 6. 확인이 필요한 사항

1. **브라우저 — 기존 동작이 안 깨졌는지**가 핵심이다. 차감 없는 행은 예전처럼 자유로워야 한다:
   - 잡곡 제품재고 **#1327 찰보리 1kg × 100** 수정 → 저장되는지
   - 잡곡 매입 등록 후 수정·삭제 → 되는지
2. **차단 동작을 실제로 보려면 차감을 만들어야 한다** — 잡곡을 재포장하면 원본에 REPACK movement가 붙는다.
   그 원본을 수정·삭제해 보면 이유가 뜬다. 다만 **실데이터가 바뀌므로** 할지 말지는 판단이 필요하다
   (역방향 재포장으로 되돌릴 수는 있다).
3. **`app/actions/packages.ts`가 1,258줄** — 파일 800줄 원칙 초과. 이번 작업 전에도 1,190줄이었다.
   분리는 별도 작업으로 제안한다.
