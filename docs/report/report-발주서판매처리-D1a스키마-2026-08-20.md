### 1.4 액션 시트 단위화 ([app/actions/purchase-order.ts](../../app/actions/purchase-order.ts))

`sheetName`·`channel`이 NOT NULL이 되면서 「파일 1개 = 묶음 1개」 코드는 더 이상 성립하지 않아 시트 단위로 고쳤다.

- `insertSheetBundle()` 헬퍼 신규 — 시트 1장을 묶음+건+라인으로 적재. `uploadPurchaseOrder`는 인식된 시트마다 이 헬퍼를 호출한다(단일 트랜잭션).
- `UploadResult`가 `uploadId` 단수 → `bundles: UploadedBundle[]` + 합산 `summary`로 바뀌었다. **화면 호출부가 아직 없어**(`uploadPurchaseOrder` 참조 0건) 깨진 곳은 없다.
- 라인 저장에 `unitWeightKg` 연결 — D0에서 파서가 넘기기만 하고 버리던 값이다.
- 감사로그는 묶음별 1건씩 기록(시트명 포함).
- 파서 경고(`warnings`)를 업로드 결과에 시트명 접두로 실어 반환 — 조용한 누락 금지(#28·#29·#33).
- `listPurchaseUploads()` 반환에 `sheetName`·`channel`·`note` 추가 (단계6 갭 G5 해소).

## 2. 주요 결정 사항

1. **묶음 중복은 강제진행(force)을 없앴다.** DB unique와 같은 키라 force로 밀어넣어도 제약에 걸린다. 「기존 묶음을 삭제하고 다시 올려주세요」 안내로 바꾸고 `uploadPurchaseOrder`의 `opts.force` 파라미터를 제거했다. 단계6 계획서 D1의 "중복경고 force 분기"는 **D1c 업로드 모달 설계 때 재검토**한다(삭제 후 재적재를 모달에서 대행할지 여부).
2. **구 `@@index([fileName, orderDate])`는 제거.** 새 unique의 선두 컬럼이 `fileName`이라 조회를 그대로 커버한다.
3. **`unitsPerBox` 입력칸은 D1c**(`/admin/product-types`)에서. D1a는 컬럼만 뚫었다.
4. **`updateUploadNote` 액션은 D1c**로 미뤘다. `note` 컬럼만 있고 아직 쓰는 화면이 없다.

## 4. 확인이 필요한 사항

1. **`orderDate`가 null인 시트는 DB unique가 안 잡는다.** PostgreSQL에서 NULL은 서로 같지 않아 `(파일명, 시트명, NULL)`은 몇 번이든 들어간다. 앱의 `bundleDuplicateKey`는 null을 빈 문자열로 다뤄 잡아내므로 현재 경로는 방어되지만, **DB 제약만 믿으면 안 된다.** D1b에서 발주일을 사용자가 반드시 확정하게 하면(#31 시트선택 UI) 이 구멍이 닫힌다.
2. **업로드 화면 실검증은 아직 못 했다.** `uploadPurchaseOrder`를 부르는 화면이 없어 D1a 단계에서는 스키마·타입·순수로직까지만 확인했다. 실파일 왕복 검증은 D1b(액션 2단계) → D1c(모달)에서.
3. 🔴 **미결 유지 — 재고 분할 차감**(1,004kg 자루에서 1,000kg만 빼기). D2 착수 전 결정 필요. 계획서 §7 참고.
