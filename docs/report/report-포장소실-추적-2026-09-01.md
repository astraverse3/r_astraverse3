## 4. 원인 후보 (미확정, 내일 검증 대상)

### A. 낡은 화면 덮어쓰기 — 「사라짐」쪽 유력
diff는 *"payload에 없는 기존 행 = 삭제"* ([lib/packaging-diff.ts](../../lib/packaging-diff.ts) `-- 입력에서 빠진 행 = 삭제 --`).
서버는 두 경우를 구분하지 못한다:
- 사용자가 화면에서 그 줄을 **지웠다** → 삭제가 맞음
- 화면을 연 뒤 **다른 사람이 추가**해 애초에 화면에 뜬 적 없다 → 삭제하면 안 됨

이영명이 14:30에 톤백 저장(`#1365`) → 그 전에 다이얼로그를 열어둔 사람이 나중에 저장하면 `#1365`가 **경고 없이 삭제**된다.
※ 단 `d18487e` 이전(전삭제+재생성)에도 결과는 같았음 → **이번 리팩터링이 만든 새 버그는 아닐 가능성이 높다.**

### B. `count = 0` 줄 조용한 누락
[add-packaging-dialog.tsx:361](<../../app/(dashboard)/milling/add-packaging-dialog.tsx#L361>), [:219](<../../app/(dashboard)/milling/add-packaging-dialog.tsx#L219>) 이 `outputs.filter(o => o.count > 0)`.
수량 미입력 줄은 **경고 없이** payload에서 빠지고, 기존 행이었다면 삭제까지 된다.
※ 톤백 줄은 `addToGroup`에서 `count: 1`로 시작하므로 이 경로엔 안 걸림. **잔량/일반 줄이 대상.**

### C. 유효성 에러로 저장 전체 차단 — 「저장 안 됨」쪽 유력
diff의 `INVALID_LINE`은 **새 줄(id 없음)이면 무조건** 검사한다.
화면에 값이 안 채워진 줄이 하나라도 있으면 **저장 전체가 막힌다**
(톤백은 `weightPerUnit: 0`으로 시작 → 중량 미입력 시 `"N번째 줄(톤백): 단위 중량을 입력해 주세요."`).
→ 16:00경 "저장이 안 된다"의 정체일 수 있음. **에러 토스트가 실제로 떴는지 확인 필요.**

### D. 트랜잭션 롤백
`createMany`까지 갔는데 커밋 실패(Neon 연결 끊김/타임아웃) → 시퀀스만 소비되고 행 없음 = 결번.

## 6. 결정 — 동시 편집 대응은 **B안(충돌 감지)** (2026-09-01, 문희준)

다이얼로그가 **열릴 때 받은 행 id 집합(baseline)** 을 기억했다가 저장 시 함께 전송한다.
서버는 baseline과 현재 DB 행 집합을 맞대어, **내가 못 본 행이 생겼으면 저장을 거부**한다.

| | 동작 |
|---|---|
| baseline == 현재 DB | 정상 저장 (기존과 동일) |
| baseline ≠ 현재 DB | **저장 거부** + 누가 무엇을 추가/변경했는지 알림 |

A안(못 본 행은 안 지우고 저장 통과, 중복 허용)은 기각 — 중복 행이 남는 게 현장에서 더 위험하다는 판단.

### 🔴 B안의 필수 조건 — 「저장 차단」이 「입력 날림」이 되면 안 된다

오늘 사고의 후반부가 정확히 그것이었다(입력했는데 저장이 안 돼서 처음부터 다시 입력).
그래서 충돌 거부 시 **반드시** 다음을 지킨다:

1. **화면의 입력값을 절대 초기화하지 않는다** — `setOutputs([])`·`restoreOutputs(initialOutputs)` 재실행 금지
2. 서버 최신 상태를 가져와 **남의 줄을 화면에 합쳐서 보여준다**
   (예: *"이영명님이 톤백 550kg × 1을 추가했습니다. 확인 후 다시 저장해 주세요."*)
3. 사용자가 확인하면 **baseline을 갱신**하고, 다시 저장 누르면 통과

즉 거부는 **한 번뿐인 확인 단계**여야 하며, 재입력을 요구해선 안 된다.
이 조건이 빠진 B안은 오늘 사고를 그대로 재생산한다.
