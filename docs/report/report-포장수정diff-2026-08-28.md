## 1. 무엇을 고쳤나

`updatePackagingLogs`가 저장할 때마다 **배치의 포장 행을 전부 지우고 새로 만들던 것**을,
입력에 실려온 행 `id`로 **create·update·delete를 가려 반영**하도록 바꿨다.

```ts
// 전
await tx.millingOutputPackage.deleteMany({ where: { batchId } })
for (const output of outputs) { await tx.millingOutputPackage.create(...) }

// 후
const diff = diffPackaging(기존행, 입력줄)     // 순수 함수 · 단위테스트
if (!diff.ok) return { success: false, error: formatPackagingDiffErrors(diff.errors) }
deleteMany(toDelete) → update(toUpdate, 바뀐 줄만) → createMany(toCreate)
```

포장 내역을 「배치에 딸린 단순 값」으로 본 초기 설계였는데, 그 뒤 `PackageMovement`(판매·재포장 차감)·
`productTypeId`(SKU)·`Repack`이 이 행을 **참조**하기 시작하면서 전제가 깨져 있었다.

## 3. 결정별 결과

### #62 — id로 매칭한다

**UI는 바꿀 게 없었다.** `restoreOutputs`가 `{ ...o }`로 서버 행 전체를 복사하고 있어
`id`는 이미 서버까지 흘러가고 있었다 — **타입에만 없어서 서버가 안 쓰던 것**이다.
편집 함수(`updateCount`·`setWeight`·`setPackaging`…)도 전부 `{ ...o }` 패턴이라 id가 유지되고,
새로 추가하는 줄만 id가 없다. 같은 id가 두 번 나오는 경로도 없다(확인함).

자연키 매칭은 쓰지 않는다. **id가 없으면 무조건 create** — 엉뚱한 줄을 고치는 것보다 낫다.

### #63 — 차감된 포장은 지우지도, 차감량 밑으로 줄이지도 못한다

FK 에러(원인 불명)가 나던 자리를 도메인 규칙으로 바꿨다. 실DB 배치 #13 기준 실제 출력:

```
이미 판매·재포장된 포장은 지울 수 없어요.
  · 잔량 × 1 (1개 중 1개 차감됨)
포장을 되돌리려면 판매를 취소하거나 재포장을 정리해 주세요.
```

```
잔량 × 1 → 0개로 줄일 수 없어요. 이미 1개가 판매·재포장됐습니다.
```

차단은 장애가 아니라 규칙이므로 **throw 하지 않고** `{ success: false, error }`로 돌려보낸다
(아직 아무것도 쓰지 않은 시점이다). `sanitizeErrorMessage`가 메시지를 가리지 않는다.

### #64 — 순수 함수로 분리

`lib/packaging-diff.ts`는 DB를 모른다. 액션이 조회 결과를 넣고 결과를 트랜잭션으로 실행만 한다.
`lib/repack.ts`와 같은 결이다.

### #65 — 파생 필드는 필요할 때만

| 필드 | 다시 계산하는 조건 |
|---|---|
| `lotNo` · `productCode` | `stockId`가 바뀌었을 때 |
| `productTypeId` | `packageType` 또는 `packagingId`가 바뀌었을 때 |

**바뀌지 않은 줄은 UPDATE 자체를 보내지 않는다.** 실DB 181개 배치 전부에 대해
「아무것도 안 고치고 저장」을 시뮬레이션한 결과 **쓰기 0건** — id·`createdAt`이 그대로 남는다.

## 4. 🔴 계획에 없던 발견 — 유효성 검사가 기존 데이터를 인질로 잡았다

`lib/repack.ts` 패턴을 따라 줄 유효성(규격·중량·개수) 검사를 **모든 입력 줄**에 걸었더니,
실DB 검증에서 **배치 #73이 통째로 잠겼다.**

```
도정 포장 행 613개 중 유효성 위반: 1개
  #269 배치73 잔량 0kg × 5
```

「잔량 0kg × 5」는 과거에 잘못 저장된 행이다(차감 없음). 전 줄 검사로는 **그 줄을 건드리지도 않는
저장까지** 막혀서, 그 배치의 다른 포장을 고칠 수 없게 된다. 없던 제약을 새로 만든 회귀다.

**→ 유효성은 「실제로 쓰는 줄」(create·update 대상)에만 건다.**

- 안 건드리는 줄은 값이 잘못돼도 통과한다
- 그 줄을 **실제로 고치려 할 때** 비로소 막는다 (「단위 중량을 입력해 주세요」)
- **삭제는 막지 않는다** — 잘못된 행을 정리하는 경로가 열려 있어야 한다
- 차감 규칙(#63)을 유효성보다 **먼저** 본다 — 「0개로 줄일 수 없어요」가 「개수는 1개 이상」보다 정확하다

**동작 변화 — 유지하기로 확정(2026-08-28)**: 이제 **새로 만들거나 고치는** 줄은 단위 중량이 0이면 저장이 막힌다.
톤백·잔량은 화면에서 중량 0으로 행이 추가되고 사용자가 값을 채우는 구조라,
채우지 않고 저장하면 예전엔 조용히 0으로 저장됐지만(#269가 그 결과다) 이제는 이유가 뜬다.
0kg 행은 재고·수율을 오염시키므로 막는 쪽이 맞다.

**다만 메시지가 줄을 못 짚었다** — 「17번째 줄」이라고만 나오는데, 화면은 **로트(생산자)별로 쪼개져** 있다.
배치 #73은 22줄·생산자 5명이라 그 번호로는 찾을 수 없다. **규격을 함께 내도록 고쳤다**:

```
2번째 줄(톤백): 단위 중량을 입력해 주세요.
```

## 5. 성능 — 왕복 수

배송·상차 D1b 교훈(Neon 왕복 250~300ms · 루프 안 INSERT는 20줄이 한계)을 그대로 적용했다.

| 단계 | 왕복 |
|---|---|
| 삭제 | `deleteMany` **1회** |
| 추가 | `createMany` **1회** |
| 수정 | 바뀐 줄 수만큼 (안 바뀐 줄은 0) |
| SKU 조회 | **조합별 1회** — 한 배치는 대개 품종·도정유형이 같고 규격만 달라 캐시가 잘 듣는다 |

`timeout: 30000` 유지. 계획서는 `createManyAndReturn`이었으나 **반환값을 쓰지 않아** `createMany`로 했다
(목적인 「왕복 1회」는 동일).

## 7. 브라우저 실동작 검증 — 배치 #13 (2026-08-28, 사용자 확인 완료)

**2025-10-20 · 백미 · 서농22호 · 김안순 · 투입 3,212kg** (마감 → 다시 수정으로 진입)

**① 차감 없는 줄 수정** — `4kg × 169` → `170` 저장. **성공**(경고 없이 조용히 저장).
저장 직후 실DB 상태가 이 작업의 핵심 증거를 전부 담고 있다:

```
#68 4kg  × 170   created=2026-02-23  updated=2026-08-28T07:25:57  ← 방금 고친 줄
#69 잔량 × 1     created=2026-02-23  updated=2026-03-16T07:28:36  ← movement(REPACK, repack#2) 살아있음
#70 톤백 × 1     created=2026-02-23  updated=2026-06-16T06:53:28
```

| 관찰 | 의미 |
|---|---|
| 행 id가 68·69·70 **그대로** | 전부 재생성이 아니다. 예전이면 새 id가 잡혔다 |
| `createdAt`이 셋 다 **2026-02-23** | 원래 등록일 보존. 이력이 안 날아갔다 |
| 안 고친 두 줄은 **`updatedAt`조차 안 움직임** | UPDATE를 아예 보내지 않았다는 증거 (#65) |
| `#69`의 movement가 **그대로 살아있음** | 참조 무결성 유지 |

🔴 **예전 코드였다면 이 저장은 실패했다.** `#69`를 지우려다 FK에 걸려, `4kg`를 170으로 고치는 것조차 안 됐다.

**② 차감된 줄 삭제 시도** — `잔량 3kg × 1`을 지우고 저장 → **이유가 적힌 메시지가 떴다**(FK 에러 아님).
※ 화면에서 줄을 지우기만 하면 로컬 state만 바뀐다 — **저장 버튼을 눌러야** 서버 판정이 돈다.

**③④** 차감량 밑 축소 차단 · 안 고치고 저장 시 쓰기 0건 — §6의 실DB 스크립트로 확인 완료.

> 4kg는 검증 과정에서 **169 → 170으로 남아 있다.** 되돌리려면 169로 다시 저장하면 된다.
