# 결과보고서 — 도정구분별 수율 기준값 전 화면 반영

작업일: 2026-09-10
계획서: `docs/plan/plan-수율기준값-전화면반영.md`

## 1. 무엇을 고쳤나

관리자 설정(`/admin/settings`)의 「도정구분별 수율 기준값」은 **저장은 정상이었지만
읽는 쪽이 갈라져 있어 화면에 거의 반영되지 않았다.**

- 기준값을 실제로 읽는 곳은 도정 포장 입력 다이얼로그 **한 곳뿐**이었다.
- 도정목록 PC/모바일, 통계 테이블은 `>= 70`을 **하드코딩**하고 있었다.
- 대시보드 최근 도정 내역은 DB가 아닌 `DEFAULT_YIELD_RATES` **상수**를 봤다.
- 통계는 `yield_rate_target`이라는 **존재하지 않는 키**를 조회했다(항상 68 고정 + 소비처 없음).

덤으로 배지 색 규칙이 화면마다 제각각(2단계/3단계, 임계 60·70 혼재)이라
같은 수율이 화면마다 다른 색으로 보였다.

## 3. 주요 결정 사항

### 3.1 등급 경계 — `기준 - 5`p 상대값 (사용자 결정)

| 도정구분 | 기준 | good | warn | bad |
|---|---|---|---|---|
| 백미 | 68 | 68 이상 | 63 ~ 67.9 | 63 미만 |
| 현미 | 70 | 70 이상 | 65 ~ 69.9 | 65 미만 |

고정 하한(60)이 아닌 상대값이라, 기준값을 올리면 경고선도 같이 따라 올라간다.

### 3.2 공급 경로 — layout Provider (props drilling 회피)

소비처가 전부 클라이언트 컴포넌트라 DB를 직접 못 읽는다.
`/milling`은 page → wrapper → list-client → row/card로 **4단계**라 props 전달이 지저분해진다.
소비 화면 3개가 모두 `(dashboard)` 그룹 안이므로 layout에서 **한 번만** 읽어 Context로 내려준다.

- 인증: `middleware.ts` matcher가 `/login`·정적파일을 뺀 **전 경로**를 `withAuth`로 막으므로
  layout 렌더 시점에 세션이 보장된다 → `getYieldRates()` 내부 `requireSession()` 안전.
- `useYieldRates()`는 Provider 밖에서 호출되면 `DEFAULT_YIELD_RATES`를 돌려준다.
  통계 컴포넌트가 그룹 밖에서 재사용돼도 색이 깨지지 않는다.

### 3.3 🔴 계획서에 없던 발견 — revalidate 범위

`saveYieldRates`는 `revalidatePath('/admin/settings')`만 호출하고 있었다.
기준값을 layout이 읽게 된 이상 **설정을 저장해도 다른 화면은 낡은 값을 계속 쓴다.**
`/milling`과 `/statistics/milling`은 `dynamic` 설정도 없어 캐시될 여지가 있었다.

→ `revalidatePath('/', 'layout')`으로 바꿔 루트 레이아웃 이하 전체를 갱신한다.
이 한 줄이 빠지면 이번 작업의 목표 자체가 성립하지 않는다.

## 5. 🔴 확인이 필요한 사항 (브라우저)

dev 서버 상시 기동 중이므로 `next build` 없이 화면으로 확인 부탁.

1. **배지 색이 바뀐 화면** — 승인된 변경이지만 눈으로 확인이 필요하다.
   - 도정목록 **PC**: 기존 2단계(파랑/회색) → 3단계(파랑/노랑/빨강). **회색이 사라진다.**
   - 통계 테이블: 기존 2단계(파랑/회색) → 3단계. 색상값도 `#0080c8` 직접 지정 → `primary` 토큰.
   - 도정목록 **모바일**: 3단계 유지, 단 임계가 70/60 → 도정구분별(백미 68/63)로 이동.
   - 대시보드 최근 내역: good이 `text-blue-500` → `text-primary`로 바뀐다(거의 같은 파랑).
2. **설정 저장 → 즉시 반영** — `/admin/settings`에서 백미를 예컨대 75로 올리고 저장한 뒤,
   대시보드·도정목록·통계에서 기존에 파랑이던 68~74%대 배지가 노랑으로 내려오는지.
3. **통계 화면 정상 동작** — `targetYieldRate` 제거가 화면에 영향 없는지(소비처가 없었으므로 무영향 예상).
4. **인디카 배지가 초록/파랑으로 올라오는지** — 기존에 빨강·노랑이던 인디카 배치 19건이
   good/warn으로 바뀐다(§6.5). 도정목록에서 CJ6·IPS 품종 배치를 확인.
5. **설정 화면 인디카 구역** — `/admin/settings`의 수율 카드 아래쪽에 「인디카 / 백미 61 · 현미 65」
   구역이 새로 보이는지, 값을 바꿔 저장하면 도정목록 인디카 배지가 따라 움직이는지.

## 6. 후속 확장 — 인디카 품종 축 (같은 날 추가)

### 6.1 왜 필요했나

"설정 항목에 인디카를 추가해달라"는 요청에서 출발했으나, 조사 결과
**인디카는 도정구분(millingType)이 아니라 품종 타입(Variety.type)이었다.**

실제 DB 확인:

```
MillingBatch.millingType 실제 값:  백미 173 · 현미 12 · 칠분도미 2 · 오분도미 3
                                   ('인디카'는 존재하지 않음)
type=INDICA 품종:  CJ6 · IPS · IPSA · 바스마티 · 아미향 · CJ3 · 아미면 · CJ1 · CJ4 · 케이롱 · CJ5 (11종)
```

인디카 벼도 도정하면 `millingType`은 `'백미'`다.
따라서 `MILLING_TYPES`에 '인디카'를 넣었다면 **설정 화면에 칸만 생기고 판정에는 전혀 먹지 않았을 것**이고,
그 상수를 공유하는 제품유형 마스터의 도정유형 드롭다운까지 오염됐을 것이다.

### 6.2 실적 근거

마감 배치를 dashboard.ts와 같은 안분(prorate) 방식으로 집계한 결과:

| 품종타입 | 도정 | 투입 | 실적 수율 |
|---|---|---:|---:|
| **인디카** | 백미 | 226,839kg | **61.3%** |
| 메벼(자포니카) | 백미 | 835,674kg | 67.2% |
| 찰벼 | 백미 | 19,553kg | 67.5% |
| 찰벼 | 현미 | 981kg | 76.6% |
| 메벼 | 현미 | 26,795kg | 71.2% |
| 메벼 | 오분도미 | 37,611kg | 72.8% |
| 메벼 | 칠분도미 | 1,732kg | 73.9% |

- **인디카는 메벼보다 6%p 낮다** → 별도 기준 필요 (기준값 61)
- **찰벼는 0.3%p 차이로 사실상 같다** → 별도 기준 두지 않음 (사용자 확인)
  - 찰벼 현미가 76.6%로 높지만 투입이 981kg(전체의 0.1%)뿐이라 표본이 부족하다
  - DB에 남아 있던 유령 키 `yield_rate_찹쌀 = 68`도 백미와 같은 값이었다

### 6.3 설계 — 품종 축이 도정구분보다 우선

```
getYieldTarget(millingType, rates, varietyType)

폴백 순서:  품종축 설정 → 품종축 기본 → 도정구분 설정 → 도정구분 기본 → 68
```

- 설정 키: `yield_rate_{VarietyType}_{도정구분}` (예: `yield_rate_INDICA_백미`)
  - 기존 `yield_rate_` 접두사를 공유하므로 `getYieldRates`/`saveYieldRates` 로직은 그대로 두고
    **기본값 병합만 넓혔다**
- 인디카 기본값: 백미 **61**(실적 61.3%) / 현미 **65**(실적 없음 — 메벼의 백미→현미 상승폭 +4%p 적용)
- 인디카는 오분도미·칠분도미 실적이 없어 백미·현미만 관리한다. 그 외 도정구분은 일반 기준으로 폴백
- 배치에 품종이 섞이면 대표(첫 재고) 값을 쓴다 — 화면의 도정구분 표시(`getDisplayMillingType`)와 같은 방식

## 7. 백로그로 남긴 것

- `lib/lot-generation.ts:5` 죽은 `getYieldRate` — export만 되고 호출처 없음.
  주석엔 "향후 관리자 설정 페이지에서 DB 값으로 교체 예정"이라 적혀 있으나
  그 역할은 이미 `app/actions/settings.ts`가 하고 있다. 수술적 변경 원칙상 이번엔 두었다.
- `DEFAULT_YIELD_RATES`에 남은 `'찹쌀'` 키 — `MILLING_TYPES`에서는 폐기된 값
  (찰벼는 백미/현미로 저장하고 표시만 파생, `plan-찰벼도정유형정리.md`).
- 통계 차트 **목표선 표시** — 기능 자체가 없었다. 신규 기능이라 이번 범위에서 제외(사용자 결정).
- **찰벼 품종 축** — 현재 백미 실적이 메벼와 0.3%p 차이라 넣지 않았다. 실적이 쌓여 갈리면
  `VARIETY_YIELD_TYPES`에 `'GLUTINOUS'`, `DEFAULT_VARIETY_YIELD_RATES`에 두 줄 추가하면 된다.
- **DB에 남은 유령 키 `yield_rate_찹쌀 = 68`** — millingType `'찹쌀'`이 폐기됐는데 설정값은 남아 있다.
  화면(MILLING_TYPES 기준)에는 안 보이므로 무해하나, 정리하면 깔끔하다.
