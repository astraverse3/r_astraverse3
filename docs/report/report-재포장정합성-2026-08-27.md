## 1. 이 작업은 원래 계획과 다르다

원안 R3는 「재포장 배지 + 되돌리기 진입점」이었다. 계획서를 다 쓰고 나서
**「되돌리기가 꼭 필요한 기능인가」**를 사용자가 물었고, 따져보니 **아니었다.**
대신 그 과정에서 **이미 숫자를 틀리게 하고 있던 버그**가 드러나 작업 내용이 통째로 바뀌었다.

| | 원안 | 실제로 한 것 |
|---|---|---|
| 되돌리기 화면 | 만든다 | **기각** (#57) |
| 재포장 배지 | 만든다 | **기각** (#57) |
| 생산 통계 | — | 🔴 **이중 계상 수정** (#58) |
| 결과 행 삭제 | — | **차단** (#59) |

## 2. 되돌리기를 기각한 근거 (#57)

**① 역방향 재포장이 정식 우회로다.** 결과(20kg×3)를 다시 소스로 골라 원래 규격으로 합치면 된다.
`getRepackSources`는 `repackId`를 **아예 보지 않는다**(조건 = 가용>0 + 품종 + 동질성).
막혀 있지 않다.

처음엔 이 경로를 「행이 늘어 지저분하다」고 봤는데 **그 근거가 틀렸다** —
소진된 행은 목록에서 아예 빠진다(`packages.ts:204`). 화면상으로는 지저분해지지 않는다.

**② 되돌리기가 유효한 창이 애초에 짧다.** `cancelRepack`은 결과 행에 movement가 하나라도 있으면 거부한다.
그런데 **재포장의 재포장은 정상 동선이다** — 톤백 → 20kg → 5kg는 실물 작업과 일치하고,
코드도 막지 않는다. 20kg을 5kg으로 쪼개는 순간 첫 재포장은 되돌릴 수 없게 된다.
즉 「재포장 직후 ~ 팔리거나 다시 재포장되기 전」에만 쓸 수 있다.

**③ 빈도가 낮다.** 되돌릴 일 = 실수·착오뿐이고 아주 가끔이다.

**④ 배지는 되돌리기의 부속품이다.** 추적은 로트로 이미 된다. 배지의 실제 쓸모가
「되돌릴 대상 찾기」였으므로 되돌리기를 안 만들면 배지도 의미가 없다.

→ `cancelRepack`은 **지우지 않고 의도적 미연결**로 둔다. 함수 주석에 이 결정과 재연결 시
함께 고칠 것(#60)까지 적어 뒀다 — 다음에 읽는 사람이 죽은 코드로 오해하지 않도록.

## 3. 🔴 대신 나온 것 — 생산 통계가 이미 틀어져 있었다 (#58)

**원인은 하나다.** 재포장 결과 행이 원본의 `batchId`를 승계하는데(`repack.ts:394`,
로트·농가·품종을 이어받으려면 필요하다 — 설계 자체는 옳다), **생산 집계가 `repackId`를 안 본다.**

```ts
// output-statistics.ts — 수정 전
where: { batch: { date: {...} } }          // repackId 조건 없음
totalProductionKg = packages.reduce((s, p) => s + p.totalWeight, 0)
```

톤백 1,004kg을 생산하고 1,000+4로 재포장하면 **생산 2,008kg**으로 잡힌다.
체인이 길수록 배로 커진다(톤백→20kg→5kg이면 같은 쌀이 3번).

**실측 (2026-08-27 Neon)**

```
Repack 2건 · 결과 6행(전부 batchId 보유) · 이중 계상 85kg
규격별: 10kg 50 · 4kg 24 · 5kg 10 · 1kg 1
```

| 위치 | 틀어진 것 |
|---|---|
| `output-statistics.ts:97` | 총 생산량 + **규격별 집계**(톤백을 쪼갠 20kg이 「20kg 생산」으로) |
| `dashboard.ts:32` | 총 생산량 + **수율 분자** — 산출이 부풀면 수율까지 틀어진다 |

→ 두 쿼리에 **`repackId: null`** 추가. 재포장은 생산이 아니라 재배치다.
원본(톤백)은 소진돼도 생산 통계에 남는다 — 실제로 생산했으니 맞고, 이 조건이 정확히 그 선을 긋는다.
**백필 불필요** — 쿼리 시점 조건이라 기존 데이터가 자동으로 정상화된다.

**영향 없음을 확인한 곳**: 제품재고 목록(가용 0 제외) · 발주서 차감(`productTypeId` + movements) ·
`admin.ts:126`·`product-type.ts:215`(존재 확인 count) · `package-movement.ts:44`(단건 조회).
오직 **「batch로 긁어 totalWeight를 합산하는」 두 곳**만 문제였다.

## 4. 결과 행 삭제 차단 (#59)

`deleteMiscPackage`는 결과 행만 지우고 원본의 REPACK movement를 그대로 둔다.
원본은 영원히 소진 상태로 남고 결과는 사라져 **재고가 증발한다.** `deleteMiscPurchase`도 같다.

**실질 위험은 낮다** — 처음엔 과대평가했다가 실측으로 정정했다:

```
전체 제품재고 — 벼 613행 712,772kg / 잡곡 1행 100kg
재포장 결과 6행 — 전부 RICE/MILLED
현재 잡곡 재포장 결과 행: 0개
```

삭제는 잡곡 탭에만 있고(벼 탭은 행 삭제 기능 자체가 없다) 잡곡 재고는 1행뿐이다.
그래도 막은 이유는 **조건 한 줄이면 되고**, 잡곡이 늘면 실제 위험이 되기 때문이다.

차단 메시지가 역방향 재포장을 안내한다 — 되돌리기 화면이 없으므로 그게 정식 경로다.

> 재포장으로 만든 재고는 삭제할 수 없어요. 되돌리려면 이 재고를 다시 재포장해 원래 규격으로 합쳐주세요.

## 5. 🔴 더 큰 게 나왔다 — `batch.outputs` 전수 정리 (#61)

**#58을 고치고 나서 발견했다.** 사용자가 eslint 결과를 그냥 넘기지 않아 드러났다.

### 내 첫 조사가 불완전했다

`millingOutputPackage`를 **직접** 조회하는 곳만 grep했다. 그런데 `millingBatch`를 조회하며
**`outputs` 관계로 접근**하는 경로가 따로 있었고, 그쪽이 더 많고 더 위험했다.
`statistics.ts` 전체가 여기 있었다.

### 수율 분자를 잘못 짚었다

1차 수정 때 `dashboard.ts` 3번 쿼리 주석에 「이 값이 수율 분자」라고 적었는데 **틀렸다.**
그 값(`totalOutputWeight`)은 카드의 총 생산량 전용이고, **수율은 9번 쿼리가 따로 계산한다.**
주석을 정정하고 9번 쿼리를 고쳤다. (`totalInputWeight`는 쿼리만 하고 아무 데도 안 쓰인다 — 별건)

**실측 — 수율이 실제로 부풀어 있었다:**

| 배치 | 투입 | 수율 (지금 → 정정) |
|---|---:|---|
| #145 서농22호 | 2,408kg | 63.50% → **62.67%** |
| #56 서농22호 | 1,747kg | 66.17% → **65.66%** |
| #102 새청무 | 19,627kg | 72.01% → **71.73%** |
| #140 새청무 | 1,615kg | 71.21% → **71.15%** |

### 공용 상수로 묶었다 (사용자 확정)

지점마다 손으로 `repackId: null`을 붙이면 **또 누락된다** — 이번에 두 번 놓쳤다.
`lib/batch-outputs.ts`에 조각을 두고 모든 지점이 그것을 쓴다.

```ts
export const MILLED_OUTPUT_ONLY = { repackId: null }   // where 조각
export const MILLED_OUTPUTS = { where: MILLED_OUTPUT_ONLY }  // 관계용
```

### 정리한 지점

| 위치 | 고친 것 |
|---|---|
| `statistics.ts` ×3 | 통계 요약 `totalOutputKg`·`avgYieldRate` · 버킷×품종별 집계 |
| `dashboard.ts` 9번 | **수율 분자** |
| `dashboard.ts` 3번 · `output-statistics.ts` | 총생산·규격별 (공용 상수로 통일) |
| `dashboard.ts:63` | 최근 도정 10건 목록 |
| `milling-excel.ts` | 수율 필터 — 화면과 엑셀이 어긋나지 않게 |
| `milling.ts` `getMillingLogs` | **도정관리 포장 내역** — 재포장 결과가 도정 포장인 척 다이얼로그에 복원되던 것 |
| `milling.ts` `updatePackagingLogs` deleteMany | 재포장 결과를 삭제 대상에서 제외 |

### 일부러 안 고친 두 곳

필터를 붙이면 **오히려 위험해진다.** 주석으로 이유를 남겼다.

| 위치 | 왜 |
|---|---|
| `milling.ts` 배치삭제 `_count` | 「포장이 있으면 삭제 금지」 판정이다. 재포장 결과를 빼면 그것만 남은 배치가 삭제를 통과해 재포장 결과가 함께 지워진다 |
| `milling.ts` `deleteMillingBatch` deleteMany | 배치를 통째로 없애는 자리다. 재포장 결과만 남기면 batch 없는 고아가 된다. FK가 막는 게 올바른 동작 |

## 8. 확인이 필요한 사항 (사용자 브라우저)

1. 통계 화면 생산량이 **85kg 줄었는지** · 규격별에서 `10kg 50 · 4kg 24 · 5kg 10 · 1kg 1`이 빠졌는지
2. 대시보드 총 생산량과 **수율**이 함께 정정됐는지 (배치 #145는 63.50% → 62.67%)
3. **도정관리 포장 내역에 재포장 결과가 안 보이는지** — 원본 도정 포장만
4. 잡곡 탭에서 **일반(재포장 아닌) 행은 여전히 삭제되는지**

⚠️ **통계 숫자가 바뀝니다.** 지금까지 보던 값보다 85kg 적게 나오는 게 정상입니다.

## 9. 🔴 이번에 못 고친 것 — 포장 수정이 막혀 있다

```
전체 배치 181개 · 포장 수정이 FK로 막히는 배치 16개 (9%)
  ├ REPACK만 원인: 16개
  └ SALE 포함:      0개
```

`updatePackagingLogs`에 `repackId: null`을 붙여도 **안 풀린다.**
막는 건 재포장 *결과*가 아니라 *소스(원본)* 행이고, 원본은 `repackId`가 null이라 필터를 통과한다.
거기 REPACK movement가 붙어 있어 `deleteMany`가 FK(Restrict)에 걸린다.

**진짜 원인은 저장 전략이다** — 「전부 지우고 다시 만들기」가 참조당하는 행과 양립할 수 없다.
