## 1. 한 줄

매트릭스에서 **행(수령처)을 여러 개 골라 한 번에 차감**하는 흐름을 붙였다. 차감 직전

UI보다 **쓰기 경로**가 이번 작업의 알맹이였다(§3).

## 3. 만든 것

### `lib/purchase-order-batch.ts` (순수, 테스트 16개)

`planBatchAllocations(lines, pools, weights)` — 고른 라인들의 FIFO 배분 계획.

- 🔴 **가용 풀을 깎아가며 `itemId` 오름차순으로 순차 배분**한다(#6). dry-run과 확정이 같은 함수·같은 순서를 쓰므로 게이트에 적힌 숫자가 그대로 결과가 된다.
- 제외 3종 — 매칭실패 · 톤백 · 이미 전량 차감. 재고부족은 제외가 아니다(가능한 만큼 뺀다).
- `fingerprintBatchPlan(plan)` — 게이트에서 본 계획과 확정 직전 재계산이 같은지 대조하는 지문. **수량뿐 아니라 어느 로트에서 나가는지까지** 넣는다.

### `app/actions/purchase-order-batch.ts`

| 액션 | 왕복 | 내용 |
|---|---|---|
| `previewBatch(orderIds)` | 3 | dry-run. **쓰지 않는다** |
| `confirmBatch(orderIds, fingerprint)` | ≤8 | 한 트랜잭션: 조회 4 → 메모리 배분 → `createMany` 1 → 건 상태 `updateMany` ≤3 |

- 🔴 **라인 루프로 짜지 않았다**(#7). 라인 수와 무관하게 왕복이 고정이다.
- `applyAllocations`의 검증 3종(SKU 일치·가용 초과·주문 초과)은 배치 경로에서 **순수함수가 구조적으로 보장**한다 — 사람이 고른 배분을 받지 않고 FIFO 자동 배분만 하기 때문에 가능한 단순화다. 셀 팝오버(사람이 로트를 고르는 경로)는 지금처럼 `applyAllocations`를 계속 쓴다.
- 지문이 어긋나면 **아무것도 쓰지 않고** 새 계획과 함께 돌려준다(부분 커밋 없음).
- 🔴 `revalidatePath` 호출 없음 — 부르면 매트릭스가 1.4초 통째로 다시 그려진다.

### 화면

- `review-gate-dialog.tsx` 신규 — 시안 컴팩트 v2(결과값 → 스택 바 → 차단 배너 → 이슈 목록). **조건부 마운트**라 열 때마다 새로 계산한다(낡은 검토 화면으로 확정하는 일이 구조적으로 없다).
- `matrix-client.tsx` — 좌측에 체크박스 칸 추가(sticky 좌표 상수만 고침), 전체선택, 하단 선택 바, 이슈 줄 클릭 → 해당 셀로 스크롤+강조.
- 셀 팝오버와 게이트가 **같은 `lineIndex`** 로 이름을 붙인다 — 표기 규칙이 한 곳이다.

## 4. 🔴 실측이 잡아낸 결함 1건 — 「부분 차감」이 아니었다

실데이터로 `previewBatch`의 조회·계산을 그대로 재현해 보니, 택배 묶음(#15)의
**부족 18라인이 전부 가용 0**이었다. 처음 구현은 이걸 전부 「부분 · 재고부족」으로 셌다.

가용이 0이면 **부분 차감이 아니라 아무 일도 일어나지 않는다.** 「부분 차감된다」고 읽히면
사용자는 조금이라도 나간 줄 안다. 그래서 `partial`(일부만 채움)과 `none`(차감 0)을 갈랐다 —
스택 바도 4구간이 됐고, 색은 매트릭스 셀과 같은 어휘를 쓴다(재고없음=주황, 매칭실패=빨강).

시안이 3갈래였던 건 시안의 예시 데이터가 「4라인이 조금씩 모자란」 경우였기 때문이다.
**실제 데이터는 그렇게 생기지 않았다.**

### 확인 중 잡은 결함 — 「셀로 이동」이 아무 반응이 없었다

🔴 **`Th`가 props를 명시적으로만 받아 `data-cell`이 DOM까지 가지 않았다.**
`data-*`는 JSX에서 임의 허용이라 **타입이 잡아주지 않는다** — 넘긴 쪽도, 받는 쪽도 에러가 없고
`querySelector`는 못 찾으면 조용히 아무 일도 안 한다. 셋이 겹쳐 완전히 침묵했다.
📌 **교훈: 커스텀 래퍼에 `data-*`를 넘길 땐 그 래퍼가 DOM까지 흘려보내는지 먼저 본다.**

같은 자리에서 방어 2건을 더 넣었다.

- **한 프레임 미뤄 스크롤한다** — 이 effect가 도는 시점은 게이트가 언마운트되는 커밋이고,
  Radix가 그 뒤 포커스를 선택 바 버튼으로 되돌린다. 바로 스크롤하면 그 복원이 원위치시킨다.
- **선택자 값 이스케이프** — 매칭실패 열 키는 엑셀 원본 문자열(`raw:품목명|규격|포장지`)이라
  따옴표·역슬래시가 들어올 수 있다.

### 확인 중 잡은 결함 2 — 가로 스크롤 시 소계·가용 줄만 튀어나왔다

🔴 **`width`만으론 칸 폭이 지켜지지 않는다.** 테이블 auto 레이아웃은 내용(`whitespace-nowrap`)에
맞춰 칸을 늘리는데 sticky `left`는 상수라, 둘이 어긋나면 **가로 스크롤할 때만** 드러난다 —
상태·진행 칸이 왼쪽으로 당겨져 겹치고, 소계·가용 줄의 라벨(`colSpan`이라 실제 열 합 폭)만
튀어나와 보인다. 스크롤 0에서는 sticky가 원래 자리라 멀쩡하다.

**실측**(사용자 콘솔): 이름칸을 184로 지정했는데 **201로 렌더** → 좌측 4칸 합 387,
sticky가 기대한 영역 370. 17px 어긋남.

- `fixedW(w) = { width, minWidth, maxWidth }` 헬퍼로 좌측 4칸 + 헤더 코너 + 소계 라벨 **6곳**을 고정
- `W_NAME` **184 → 204** — 실측이 원한 폭이 201이다. 184로 억지로 묶으면 정렬은 맞아도
  이름 잘림만 심해진다(`이마트본사 김보훈`·`롯데백화점 평촌점`)
- 📌 **교훈: sticky `left` 상수와 칸 폭은 한 쌍이다. 폭을 `width`로만 주면 상수 쪽이 조용히 틀려진다.**
  D3 이전(좌측 3칸)에도 같은 어긋남이 있었고, 칸이 하나 늘며 눈에 띈 것이다.

## 7. 판단하고 **안 고친 것** — 매트릭스를 열어둔 사이 바뀐 가용재고

사용자 확인 중 나온 것: 매트릭스를 띄운 채 **다른 창**에서 재포장하고 왔더니 가용재고가 그대로였다.

- **재매칭 버튼으로는 안 된다.** `rematchUpload`는 `productTypeId: null`인 라인만 조회하고
  (매칭실패가 없으면 즉시 `patches: []`), 가용재고도 **새로 매칭된 SKU에 한해서만** 읽는다.
  재포장한 SKU가 이미 매칭돼 있었다면 아예 손대지 않는다. 재매칭은 「매칭실패를 푸는」 버튼이지
  「재고를 다시 읽는」 버튼이 아니다.
- 이는 D2c 결정 C(서버 재조회 안 함 = 1.4초 회피)의 대가다.
- **결론: 고치지 않는다(사용자 판단 2026-09-16).** 한 사람의 실제 작업 흐름에서는 이 페이지를
  나갔다 다시 들어오면 서버 컴포넌트(`page.tsx`)가 `getUploadMatrix`를 새로 돌린다 — 동적 렌더라
  라우터 캐시도 붙지 않는다. 이번 건은 **다른 창을 띄워 작업한** 예외적 경우였다.
- 나중에 필요해지면: 가용재고만 다시 읽는 가벼운 액션(`loadAvailability` 왕복 1회 ~200ms) +
  탭 포커스 복귀 시 자동 호출. 전체 재조회(1.4초)는 라인 차감량까지 맞춰야 할 때만.
