## 13. [임시 코드] ✅ 해소 — `getPackages` 2달 cutoff 제거됨 (2026-09-02 확인)

> **해소**: 2026-09-02 §22 작업 중 실측. `lib/package-where.ts`에 cutoff 조건이 **없다** —
> 검색 필터 확장(`f8228ab`)·기본 생산연도 제거(`77d2703`) 과정에서 정식 필터로 대체되며 사라졌다.
> 아래는 당시 기록. `app/actions/packages.ts`에 남아 있던 낡은 주석 1줄도 함께 정리했다.

- **발견일**: 2026-05-04 (잡곡 #6b 검수 중, 사용자 피드백)
- **현상**: 제품재고 목록(`/packages`)에 누적 데이터가 너무 많이 노출됨. 실제로는 오래된 도정산 포장은 대부분 이미 판매되어 사라진 재고지만, 판매처리 기능이 미구현이라 `MillingOutputPackage`에 `status` 필드가 없어 차감 불가
- **임시 처리**: [app/actions/packages.ts](../app/actions/packages.ts)의 `getPackages` where 절에 cutoff 추가
  - `source=MILLED`만 `createdAt >= 오늘 - 1개월` 조건 적용 (초기 2개월에서 데이터가 충분히 안 줄어 1개월로 단축)
  - `source=PURCHASED`는 데이터가 적어 그대로 유지 (영향 거의 없음)
- **제거 시점**: **상위 계획서 작업 단계 #9 이후 — 판매관리 기능 구현 시**
  - 옵션 A: `MillingOutputPackage`에 `status`(`AVAILABLE`/`SOLD`) + `count` 차감 로직
  - 옵션 B: 별도 `Sale` 테이블에 판매내역 기록, 잔여 = `count - sum(sale.qty)`
  - 어느 쪽이든 결정되면 본 cutoff 블록 삭제하고 정식 필터로 대체
- **부수 효과**: 2026-04-04 이전 도정산 포장은 현재 화면에서 안 보임. 사용자가 옛 데이터 검색을 원할 경우 연도 필터(#6c 검색 다이얼로그)로도 우회 불가 — cutoff가 우선 적용. 정식 처리 후엔 자동 해소

## 14. [기능] ✅ 해소 — 제품재고 비판매 차감 처리 (2026-09-01 `95527a7`)

> **해소**: 2026-09-01 재고차감 화면 D1~D7(`47b77ad`·`95527a7`)이 구현체다.
> 설계대로 `PackageMovement` 단일 모델(type=SALE/DEDUCTION + reason), stock 미복원, 화면 분리까지 반영.
> 남은 후속은 §23(모바일 확인)·§24(묶음 되돌리기). 아래는 당시 설계 기록.

- **발견일**: 2026-05-06 (잡곡 #7 작업 중 사용자 요청)
- **요구**: 정상 판매가 아닌 사유(증정/분실/파손/기타)로 포장된 제품재고를 차감. **stock(원물재고)은 복원하지 않음** (포장은 실제로 만들어졌고 사용·소실됨)
- **#7c 수정/삭제와의 차이**: #7c 삭제는 "포장 자체가 없었던 것으로 되돌림(stock 복원)" — 정정 용도. 본 차감은 "포장은 있었으나 비판매로 소비됨" — stock 미복원
- **사용자 결정 (2026-05-06)**: 본 #7 범위에서 별도 모델/UX 만들지 않고, **판매처리(#9 이후)와 같은 흐름으로 통합 설계**. 판매도 결국 "포장 수량 차감 + 사유(=판매)" 패턴이라 본질이 동일. 항목(reason)만 다른 형태로 일반화
- **추천 데이터 모델**: `PackageMovement { id, packageId, count, type, reason?, note?, occurredAt }` 같은 일반화 모델
  - type: SALE / DEDUCTION
  - reason (DEDUCTION 시): GIFT / LOST / DAMAGED / OTHER
  - 표시 잔량 = `package.count - sum(movements.count)`
- **UX 제안**: 행 메뉴에 "판매" / "차감" 분리 또는 통합 "출고" + 사유 선택. 사이드바 "판매관리"와 별개로 제품재고 행에서 직접 트리거 가능

## 29. [타입 안전] 서버 액션 반환 타입이 판별 유니온이 아니다 — `as any`의 뿌리

- **발견일**: 2026-09-03 (§26 처리 중)
- **현상**: 액션이 `return { success: true }` / `return { success: false, error }` 두 갈래를 반환하는데,
  객체 리터럴의 `success`가 `boolean`으로 넓어져 **판별 유니온 내로잉이 안 된다.**
  그래서 호출부가 `if (!result.success)`로 좁힌 뒤에도 `result.error`에 접근하지 못하고 `as any`를 쓰게 된다.
- **예**: `app/actions/milling.ts`의 `updateMillingBatchStatus`(:864) · `removeStockFromMilling`(:334)
- **영향**: 지금 깨진 것은 없다. 앱 곳곳의 `(result as any).error`가 전부 여기서 나오고,
  액션이 `error`를 안 주게 바뀌어도 컴파일러가 못 잡는다.
- **권장 조치**: 공용 `ActionResult<T>` 판별 유니온을 정의하고(`{ success: true; data?: T } | { success: false; error: string }`)
  액션에 **명시적 반환 타입**을 붙인다. 그러면 호출부의 `as any`가 전부 사라진다.
- **범위 주의**: 액션 파일 전체에 걸치는 작업이라 §26(파일 2개)에 섞지 않고 분리했다. 착수 시 `/plan` 선행.
- **우선순위**: 낮음~중간. 부채이되 지금 새는 곳은 없다.
