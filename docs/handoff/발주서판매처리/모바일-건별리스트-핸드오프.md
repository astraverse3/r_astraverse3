### 2.0 데이터 원시 — **B안(`BuildMatrixInput` 파생)** 확정

건목록·건상세·소계 **전부** `page.tsx:20`이 내리는 `BuildMatrixInput` 하나에서 파생한다.

| | A안 `OrderDetail` 확장 | **B안 파생 ✅** |
|---|---|---|
| 톤백 kg | 필드 추가 필요 | `items[].unitWeightKg` 이미 있음 |
| 「다음 건」 왕복 | 건마다 2×N | **0** |

A안은 톤백 중량 필드를 어차피 추가해야 하므로 장점 없이 왕복만 남는다.
`getPurchaseOrderDetail`(`purchase-order.ts:186`)은 라인당 쿼리 2회로 16라인 = 32왕복이다. §4.2 「다음 건 ›」으로 67건을 넘기면 건마다 쌓인다 — 이 프로젝트에서 이미 같은 모양으로 터진 적이 있다(적재 트랜잭션 타임아웃 = 루프 안 쿼리).

**단, 로트는 파생 대상이 아니다.** `BuildMatrixInput`에 SKU별 가용 로트가 없다.
- 리스트 · 헤더 · 푸터 · 소계 → **파생(0왕복)**
- 로트 목록 → **FIFO 시트를 여는 시점에만** 조회(온디맨드)

그러면 「다음 건 ›」 67번이 0왕복으로 남는다.

### 2.0.1 선행 조건 — 상태 판정 통합 (B안 **이전**에)

`kindOf`(패널)와 `cellStatusOf`(매트릭스)는 **이미 같은 판정을 다른 이름으로** 하고 있다.
한 함수로 합치는 일을 **B안 뒤의 정리 작업이 아니라 선행 단계**로 넣는다. 파생 기간 동안 두 벌로 굳으면 §9-13 검증을 통과하지 못한다.

### 2.1 권한은 `OPERATION_MANAGE`

발주서 액션은 전부 **`OPERATION_MANAGE`**다(`purchase-order-matrix.ts:80,291,418,475`). 2026-06-22 권한 단순화 때 정해진 것.
모바일 신규 화면도 **같은 키**를 쓴다. ~~`SUPPLY_MANAGE`~~가 아니다 — 그걸 쓰면 정작 차감하는 담당자가 화면을 못 쓴다.

## 3. 화면 1 — 건 목록

### 3.1 발주처 그룹 헤더

실측 결과 택배 67건의 발주처가 **소수로 반복**된다 — 땅끝황토친환경 9 · 쿠팡wing 5 · 서대문마을생협 4 · 우리아이행복밥상 2 …
그래서 평평한 67줄 대신 **발주처로 묶는다.**

```tsx
// 새 조회 없이 buildMatrix().rows를 그대로 발주처로 묶는다
// row가 vendor·수령인·라인수·주문/차감·상태점·needsWork를 이미 갖고 있다
const grouped = useMemo(() => {
  const m = new Map<string, MatrixRow[]>()
  for (const r of sortMatrixRows(rows, sort)) {
    const k = r.vendor ?? '일반판매'
    if (!m.has(k)) m.set(k, [])
    m.get(k)!.push(r)
  }
  // 건수 많은 발주처 먼저 — 작업 덩어리가 위로 온다
  return [...m.entries()].sort((a, b) => b[1].length - a[1].length)
}, [rows, sort])
```

| 요소 | 스펙 |
|---|---|
| 그룹 헤더 | `px-4 pt-3 pb-1.5 bg-slate-50` · 발주처명 `text-[10.5px] font-bold text-slate-400 tracking-wider` + 건수 배지 |
| 건 행 | `px-4 py-2.5` · 좌측 상태 점 6px · 수령인 `text-[13px] font-bold` · 라인수 `text-[10.5px] text-slate-400` |
| 우측 | `주문/차감` 수량 `text-[12px] font-bold mono` (완료 emerald · 부분 amber · 실패 red · 대기 slate) |
| 터치 | 행 전체 44px — `stretched-link` 패턴 유지 |

- **그룹이 1개뿐이면 헤더를 렌더하지 않는다** (이마트·급식·시아스는 발주처 단일이라 헤더가 노이즈)
- 택배처럼 발주처=개인이 섞이면 그룹 「일반판매」로 모은다
- 정렬은 **`sortMatrixRows` 그대로** 쓴다 — 기존 3종(가나다·최신·작업필요)이 §3.2 요구와 정확히 일치한다. 새로 짜지 말 것

### 3.2 헤더·필터

- 상단: 채널 배지 + 파일명 + 업로드 일시 + `67건 · 96라인`
- 상태 요약 미니칩: 완료 / 부분 / 대기 / 매칭실패(우측 정렬, red 보더)
- 필터 칩: `작업 필요 41` (기본) / `전체 67` — **단일 선택**
- 정렬 드롭다운: 발주처별(기본) / 수령인 가나다 / 작업 필요 먼저

### 3.3 규격별 소계 진입

건이 2개 이상이면 목록 상단에 링크 카드를 둔다.

```
[📊 규격별 소계 보기        17규격 · 253개 ›]
```
`rounded-xl bg-blue-50 border border-blue-200` · 건이 1개면 숨김(소계 = 건상세와 동일).

## 4. 화면 2 — 건 상세

### 4.0 이미 있는 것 — `OrderDetailPanel` 확장

**새 파일을 만들지 않는다.** `order-detail-panel.tsx`가 §4 스펙을 거의 다 구현해 뒀다:

| §4 요구 | 현재 코드 |
|---|---|
| 헤더 `발주처 → 수령인` + 진행바 + `9/16` | ✅ `:88-129` |
| 라인 행(상태점·품종·규격·가용·부족배지·차감/주문) | ✅ `LineCard :170` |
| 작업/완료 2그룹 | ✅ `:82-83` |
| 폰 전체폭 | ✅ `w-full sm:max-w-[468px]` |

없는 것은 **4개뿐**이다 — 이것만 얹는다:
1. 완료 그룹 **1줄 접기**
2. 푸터 **일괄차감 버튼**
3. 라인 탭 → **FIFO 바텀시트**(§6)
4. **「다음 건 ›」**(§4.2)

> 상태 판정(`kindOf`)·라인 카드·2그룹 분리는 **데스크탑과 공유**된다. 모바일을 별도 파일로 뜨면 상태 판정이 두 벌 되고 데스크탑만 낡기 시작한다 — 이 프로젝트에서 반복해서 사고 난 지점이다.

### 4.1 화면 스펙

`건상세-C안-간결` 기준. **전부 접힘 기본 + 작업/완료 2그룹.**

| 요소 | 스펙 |
|---|---|
| 헤더 | `발주처 → 수령인` + 진행바 한 줄 (완료 emerald / 부분 amber) + `9/16 · 작업 7` |
| 라인 행 | 상태 점 + 품종·도정 `text-[12.5px] font-bold` + `규격 · 가용 n` + 부족 배지 + `차감/주문` mono |
| 부족 배지 | `부족32` — `bg-red-50 text-red-600 text-[9.5px] font-bold` |
| 라인 탭 | → FIFO 바텀시트 (§6) — **신규** |
| 완료 그룹 | 1줄로 접음 — `새청무 5kg 외 8건 · 전부 차감 완료 · 932kg` — **신규** |
| 푸터 | `작업 필요 7라인 · 남은 401kg` + **`6라인 FIFO 일괄차감`** (실패 라인 제외) |
| 푸터 숫자 정의 | kg은 **남은 수량**(주문−차감) × 규격중량. 라인수는 실패 포함, 버튼 수는 실패 제외 |
| 🔴 규격중량 출처 | `DetailLine`에 `unitWeightKg`가 **없다**(`purchase-order.ts:138`). 일반 규격은 `normalizeSpec(packageType)`으로 뽑히지만 **톤백은 못 뽑는다** — 자루중량이 규격 문자열이 아니라 라인 필드(`#34`)다. 그래서 **§2.0 B안으로 `items[].unitWeightKg`를 쓴다.** `DetailLine`을 원본으로 삼으면 시아스(톤백) 푸터가 통째로 틀린다 |
| 중량 미산정 | `unitWeightKg`가 `null`인 라인이 섞이면 kg 옆에 **`일부 규격 중량 미산정` 배지** (§8-1) |

### 4.2 「다음 건 ›」

**1라인 건이 많은 택배에서 핵심이다.** 실측상 67건 중 48건이 1라인이라, 건상세가 카드 한 장으로 끝난다.
푸터에 `다음 건 ›`을 두어 목록으로 돌아가지 않고 연속 처리한다.

```tsx
// 목록의 현재 필터·정렬 순서를 그대로 이어받아야 한다
const next = siblingIds[siblingIds.indexOf(orderId) + 1]
```
- 마지막 건이면 버튼을 `목록으로`로 바꾼다
- 매트릭스에서는 불가능했던 동작이다(행 이동 시 가로 스크롤 위치가 리셋됨)

### 4.3 실패 라인

수동지정은 제거됐다(`plan-발주서-수동지정-제거.md`). 실패 라인은 **「재매칭」 + 안내**다 — 「SKU 지정」 아님.
문구: `품종을 못 찾았습니다. 품종 관리에서 별칭을 추가한 뒤 재매칭하세요.`

## 5. 화면 3 — 규격별 소계 (신규, 읽기 전용)

매트릭스가 하던 일 중 **하나만** 살아남았다 — 「은평+서대문 합쳐 새청무 10kg 몇 개 도정하나」.
작업 화면을 표로 만드는 대신 **읽기 전용 화면**으로 분리한다. 규격당 한 줄이므로 표가 필요 없다.

| 요소 | 스펙 |
|---|---|
| 범위 | **묶음 1개**(발주서 1장)의 전 건 합계 |
| 데이터 생산 | ⚠️ **새로 누적하지 말 것.** `buildMatrix().columns`가 규격별 `orderedQty`·`availableQty`·`unitWeightKg`를 이미 갖고 있고 부족 판정은 `isColumnShort`다. **그걸 그대로 읽어 표시만 한다** — 누적을 다시 지으면 부족 판정이 두 벌 된다 |
| 정렬 | 수량 내림차순 |
| 행 | 품종·도정 + `규격 · 가용 n` + `n개 도정 필요`(부족 시 amber) / 우측 수량 `text-[15px] font-bold mono` + kg |
| 부족 강조 | 행 배경 `bg-amber-50/40` · 상단 경고 띠 `5규격이 재고 부족합니다` |
| 푸터 | `17규격 · 308개 · 1,949.5kg` + `부족 5규격 · 도정 필요 205kg` + **공유** 버튼 |
| 합계 산정 | `buildMatrix().columns`에서 **파생**한다(자체 누적·하드코드 모두 금지). ⚠️ **부족 개수와 도정 필요 kg의 분모가 다릅니다** — 부족 5규격은 `fail` 행(녹두 · 품종 미등록)을 **포함**하고, 도정 필요 205kg은 그 행을 **제외**합니다(도정으로 해결되는 부족이 아니다). 의도한 분기이며 버그가 아닙니다 |
| 액션 | 없음 — **차감 버튼을 두지 않는다.** 도정 지시를 뽑는 화면이다 |

채널 무관하게 같은 화면을 붙인다.

## 6. FIFO 배분 바텀시트 (M1-5 유지)

```tsx
<Sheet open={open} onOpenChange={setOpen}>
  <SheetContent side="bottom" className="max-h-[80svh] flex flex-col rounded-t-2xl p-0">
```

| 항목 | 값 |
|---|---|

## 7. 검토 게이트 — `ReviewGateDialog` 확장

**신규가 아니다.** `review-gate-dialog.tsx` 380줄이 이미 있고, 그 **4갈래 구성(정상 / 부분 / 재고없음 / 실패)은 실측에서 얻은 것**이다 — 부족 18라인이 전부 가용 0이었다.
새로 지으면 「부분 차감」이라고 거짓말하는 화면으로 되돌아간다. §4.0과 같은 논리로 **확장**이다.

§7이 더하는 것은 **선택 UI뿐**이다:
1. 기본 **전부 체크됨** (빼는 UI)
2. 발주처 **그룹 헤더 + 「그룹 해제」**
3. 제외 행 `opacity-45`

| 항목 | 값 |
|---|---|
| 진입 | 건 목록 푸터 `작업 필요 41건 검토` |
| 조건 | **건이 5개 이상일 때만** 노출. 급식·이마트·시아스는 건상세 일괄차감으로 충분 |
| 체크박스 | `20×20` `rounded-[5px]` · 기본 **전부 체크됨** (빼는 UI) |
| 그룹 | 발주처 헤더 + **「그룹 해제」** — 개별 체크 여러 번을 대체 |
| 제외 행 | `opacity-45` |
| 4갈래 구성 | 기존 **정상 / 부분 / 재고없음 / 실패** 그대로 유지 — 시안의 3갈래 표기보다 이것이 정확하다 |
| 실패 | 별도 섹션 `매칭 실패 · 2건 — 차감 대상 아님` + 행별 「재매칭」 |
| 푸터 | `38건 차감 · 1,284kg` + `제외 3 · 실패 2` + `38건 차감 확정` |

**목록·상세에는 체크박스를 두지 않는다.** 선택은 이 화면에서만 한다.

> ⚠️ 시안 ⑦ 프레임은 상태를 3갈래(정상·부분·실패)로 그렸다. 그것은 시안의 단순화이고, **구현은 기존 4갈래를 따른다** — 「재고없음」을 「부분」으로 합치면 0개 넣고 「부분 차감」이라고 적는 거짓말 화면이 된다.

## 8. 데이터 주의 — 실측에서 나온 것

1. **단위 없는 규격은 kg 합계에서 조용히 빠진다** — `normalizeSpec`(`purchase-order-parser.ts:121`)은 g→kg 변환을 이미 하고 있다(`n/1000`). 변환은 문제가 아니고, **`500`처럼 단위가 없는 것이 `weightKg: null`로 남는 것**이 문제다.
   틀린 값이 아니라 **분모에서 말없이 사라지는 값**이라 더 안 보인다. 소계·푸터 kg에 `null` 규격이 섞이면 **`일부 규격 중량 미산정` 배지를 반드시 표시**한다.
   (시안 HTML에서 난 1,000배 오류는 시안 자체의 버그였고 파서와 무관하다.)
2. **0인 행·열이 선언돼 있다** — 이마트 6규격 중 2개, 해남 4발주처 중 2개가 전량 0.
   목록·소계 모두 **0은 렌더하지 않는다.**
3. **택배 발주처는 개인이 아니라 판매채널이다** — 땅끝황토친환경→이마트○○점, 쿠팡wing→개인, 서대문마을생협→어린이집.
4. **`여유`는 발주처 하나로 그대로 온다** — 특별 UI 없이 정상 데이터. 뱃지만 `여유분`.
5. 톤백(시아스)은 **자루 개수가 무의미**하다 — kg 축으로 표시·차감.

## 9. 검증

1. 택배 묶음 → 건 목록: 발주처 그룹 4개, 건수 많은 순, 67건
2. 이마트 묶음 → **그룹 헤더 없음**(발주처 단일)
3. 택배 1라인 건 → 건상세가 카드 1장 · 푸터 `다음 건 ›` → 목록 안 거치고 이동
4. 급식 은평구 건 → 16라인이 **작업 7 + 완료 1줄**로 접힘
5. 라인 탭 → 바텀시트 · 푸터 버튼이 시트 안에 보임(잘리지 않음) · 건상세 푸터 = `작업 필요 7라인 · 남은 401kg`, 버튼 `6라인`
6. 부족 라인(새청무 10kg 91주문/59가용) → `32개 부족` · 부분 차감 후 **부분완료**
7. 규격별 소계 → 17규격 · **308개 · 1,949.5kg** · 부족 **5규격** · 도정 필요 **205kg**. **차감 버튼 없음**
   (합계는 `buildMatrix().columns`에서 파생. 부족 5규격은 `fail` 포함, 도정 필요 205kg은 `fail` 제외 — 분모가 다르다)
8. 시아스(1건) → 소계 링크 **숨김**, 건상세 직행
9. 실패 라인 → 「재매칭」(「SKU 지정」 아님)
10. 검토 게이트: 건 4개 이하 묶음에서 **버튼 미노출**
11. **`OPERATION_MANAGE` 없는 계정** → 차감 버튼 전부 없음, 목록·상세·소계는 정상 (§2.1 — `SUPPLY_MANAGE` 아니다)
12. 단위 없는 규격(`500`)이 섞인 묶음 → kg 합계에 **`일부 규격 중량 미산정` 배지**가 뜨는지 (§8-1)
13. 모바일 상태·부족 배지가 데스크탑과 **동일한 판정**을 쓰는지 — `kindOf`가 한 벌인지 (§4.0)

## 10. 남는 결정

- 규격별 소계를 **묶음 단위**로 뒀다(발주서 1장 = 소계 1장). 날짜 단위로 여러 묶음 합산이 필요하면 진입점이 제품판매 목록으로 올라가야 한다
- 검토 게이트 노출 기준 「건 5개 이상」은 임의값이다 — 실사용에서 조정
- 택배 67건을 연속 처리할 때 `다음 건 ›`만으로 충분한지, 아니면 건상세에 스와이프 전환이 필요한지
- `getPurchaseOrderDetail`(라인당 2왕복)을 **언제 정리할지** — B안이면 건상세가 그것을 안 쓰게 되어 사용처가 줄어든다. 남는 곳도 파생으로 넘길지는 별도 결정
- `cell-allocation-popover.tsx`를 `allocation-sheet.tsx`로 개명할지 — 데스크탑은 계속 팝오버이므로 **파일명을 유지하고 내부에서 분기**하는 편이 안전할 수 있다
